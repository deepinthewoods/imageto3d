# Papercraft outfit concepts and Tripo Studio workflow

## Current pipeline

- Use Tripo Studio with the **studio plain paper** source-image look. The chosen reference export and reduction experiments are recorded in `tools/tripo_pipeline/pipeline_decisions.json` and `experiments/tripo_method_gallery_01/`.
- The old `pixal3d-armor-queue` service was disabled on 21 October 2026. Do not restart it or use its old `approved/` contract for new work. Its code and past outputs remain under `tools/pixal3d_queue/` and `models/` for recovery.
- See `tools/tripo_pipeline/README.md` for the folder contract, processing commands and current Tripo website automation. Convert a staged job with `python3 tools/tripo_pipeline/convert_job.py <set>--<job-id>` (Tripo submit → collect → reduction for each module in turn; resumable, never resubmits a module that has a submission record). An unattended queue watcher that calls it is not yet connected. Never claim a conversion ran or move a job to `completed/` without its Tripo output and low-poly/material artifacts.
- New front concepts belong under `concepts/<set_id>/<race_gender>/<module>_front.png` (all modules of a set side by side in the one `<race_gender>` folder, e.g. `body_armor_front.png` and `right_gauntlet_boot_front.png`; `outfit_front.png` for a regular outfit). Keep prompts, design records and rejected attempts in the same folder with the module name as prefix (`<module>_prompts.json`, `<module>_front_rejected_NN.png`); `workflow.py claim` moves them to `.concept_notes/` and creates the per-module `<module>/front.png` folders used from `processing_views/` onward. Generate fronts for the entire requested set in one pass. A set is either both `body_armor` and `right_gauntlet_boot`, or one `outfit`, per character.
- The user selects a complete front set by moving it to `approved/`. Do not move a set into `approved/` without explicit approval. Process `approved/` only when the user asks in chat.
- For each approved set, preserve the chosen `front.png`, generate `front_three_quarter.png`, `back.png`, and `back_three_quarter.png` from the same design and matching base views, then place the complete four-view set in `multiview_ready/`. The user chose automatic Tripo conversion once views are complete; do not add a second image-review gate. Until the queue watcher is connected, run `convert_job.py` on each job in `multiview_ready/` when its views are staged.
- `convert_job.py` calls `studio.mjs` with **Triangle** topology by default, H3.0, 2K texture, PBR off, Remove Lighting on, and a 2,000,000-face Studio *ceiling*. It exports the high-poly model under `models/` (plus `highpoly.blend`: textured, detected materials, seen/unseen) and runs three automatic low-poly options (geometry error 0.4%, 0.2%, 0.1% of normalized height). The 0.4% result is the default candidate; retain the other two as fallbacks. Each output must pass mesh/part checks or be marked for review. Low-poly polygon counts are outcomes, never fixed targets.
- After reduction, label each low-poly face base/primary/secondary from the source texture for later engine recoloring (`tools/tripo_pipeline/face_labels.py`): classify texture samples by **hue** (never by saturation distance), weight them by pixel saturation/brightness and by whether a concept camera actually saw that surface, and settle faces with little usable evidence from the mirror face (symmetric modules), crease-aware neighbours and a soft module prior. The prior's body zones come from the base's per-face body parts (`base_views/<race>/parts.npz`, made by `tools/tripo_pipeline/base_parts.py` from `assets/marker_bases/<race>.blend`): the base is fitted to the mesh by a trimmed scale+translation ICP, every face takes the part of the nearest base surface (normal-aware, small islands merged, left/right never mirrored), and soft part membership gives the zones, so A-posed and legless bases work; without a parts file the T-pose landmarks of `regions.json` are used. A face clearly outside the fitted base body (beyond that part's bare-mesh clearance from `base_views/<race>/clearance.json` plus a margin, only where the module lets the garment be) cannot be bare base, so Tripo's red-baked armour-edge slivers become `primary`/`secondary` (label source `off_body`). A conservative hem-riser rule (label source `riser`) also flips base faces that touch a wear face, lie where garment is allowed and face along the limb (normal more than 60 degrees off the nearest base normal), at most 2 rings deep. Both rules need `clearance.json`, which `human_male` lacks until it has a bare Tripo base. Sources whose area is mostly enclosed (a second inward-facing body shell) are audited and stripped of enclosed faces before reduction; see `tools/tripo_pipeline/README.md`. Store the transferred part per face as the `body_part` attribute in the review/wearable/high-poly blends and in the `_colors.npz` evidence. The prior only says where the base must be bare per the module definitions below; visible texture can still extend a garment past the nominal boundary. Record per face which of texture/symmetry/prior/neighbours decided it, and flag a level for review when more than 20% of its area was decided without seen texture. Retain source texture and color evidence, including `highpoly.blend` beside the source GLB. Material assignment follows whole-geometry reduction. When swatches identify the bare base, remove those faces **after** assignment to export a separate wearable mesh; keep the colored full model as evidence. Review cut boundaries and mixed faces.
- Move all view images with prompts and provenance records to `completed/` only after successful conversion, low-poly variants and material output. On failure, keep a job recoverable in its current stage or `failed/`; never overwrite prior attempts or frozen input snapshots.

## Concepts and views

- For new raster references use the local imagegen skill and built-in image generation tool. No CLI/API fallback without user authorization. Read `PROMPTING_GUIDE.md` before generation.
- Use `base_views/<race>_<gender>/<view>.png` as the edit target for each view. The active human-male base is a native **1254 × 1254** render with 45° three-quarter cameras (front-left from above, back-right from below; see `base_views/human_male/NOTES.md`); the previous level-camera 1254 set is archived at `archive/base_views_studio_plain_markers_1254_level_20261021/human_male/`; the former 1024 set is archived at `archive/base_views_studio_plain_markers_1024_20261021/human_male/`. The existing staged armor job remains 1024 and validates against its frozen `.base_views/` snapshot. A 2048 experiment remains separate. Never overwrite base images. Preserve proportions, faceted anatomy, T-pose, camera angle, framing, alpha and uncovered base material/color. The active human male views are studio-plain **semantic marker** views: red body, yellow head, magenta anatomical-left hand, cyan anatomical-left foot. Keep those uncovered colors intact. The old kraft-paper base views are archived at `archive/base_views_kraft_20261021/`; since 2026-10-22 every other race has a matching active marker set in `base_views/<race>/` (same scene, cameras and size; see `base_views/README.md`).
- For the active marker base, use broad green `primary` and blue `secondary` garment/armor regions, distinct from every base marker. The red base is not a final character color; it identifies body surfaces for later removal.
- Style: simple papercraft, broad polygon planes, crisp folds, matte cardstock, and large readable primary/secondary color regions. Avoid smooth anatomy, photoreal metal, fine noise and excessive ornament. Concept colors encode later material regions, not final engine colors.
- No weapons, props, hats, capes, labels or unrelated garments unless requested. Headwear/hood handling is deferred; keep the head bare for now.

### Armor set

1. `right_gauntlet_boot`: exactly one gauntlet on anatomical RIGHT hand/forearm and one boot on RIGHT foot/lower leg. Leave torso, upper arms, thighs and the opposite side as the base.
2. `body_armor`: torso including back, shoulders/upper arms and both upper legs. Stop above elbows and knees. Leave forearms, hands, lower legs, feet, neck and head as the base.

Right means anatomical right, never a fixed picture side: viewer-left from front, viewer-right from back. Follow that limb through three-quarter views. Both outputs show the full base wearing only their own module, not floating parts or the combined outfit.

### Regular outfit

- One `outfit` module covers the clothing as a whole, including the right foot if the design has footwear. Keep the **head, both hands and anatomical LEFT foot bare** for alignment and future separation. Do not add gloves or headwear. The bare left foot is viewer-right in front and viewer-left in back.
- Keep the covered/uncovered boundary consistent across views. Do not split a regular outfit into armor modules.

## Output and review

- Delivered images must match the pixel width and height of their corresponding base and retain alpha. The current human male bases are 1254 × 1254; inspect each future base rather than assuming that size. **Do not resize, crop, pad or stretch generated images or rendered bases to make dimensions match.** Ask imagegen for the native base dimensions, inspect the actual saved pixels, and reject/retry any mismatch.
- Use `front.png`, `front_three_quarter.png`, `back.png`, `back_three_quarter.png`. Do not crop/pad views or infer camera matrices as an approval condition.
- Record exact prompts, reference paths, design/color details and review notes; retain earlier versions when revising a concept. Do not edit frozen models or active `processing/` inputs.
- Review all views for module boundaries, anatomical side, pose/camera drift, silhouette, dimensions, alpha and panel/color continuity. These are concept references, not guaranteed pixel-registered overlays.
- Use `experiments/` only for explicitly requested experiments. Past `pending/`, `completed/` and model records are historical and must not be cleaned up for the new workflow.
