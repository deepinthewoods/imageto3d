# Papercraft outfit concepts and Tripo Studio workflow

## Current pipeline

- Use Tripo Studio with the **studio plain paper** source-image look. The chosen reference export and reduction experiments are recorded in `tools/tripo_pipeline/pipeline_decisions.json` and `experiments/tripo_method_gallery_01/`.
- The old `pixal3d-armor-queue` service was disabled on 21 October 2026. Do not restart it or use its old `approved/` contract for new work. Its code and past outputs remain under `tools/pixal3d_queue/` and `models/` for recovery.
- See `tools/tripo_pipeline/README.md` for the folder contract, processing commands and current Tripo website automation. Convert a staged job with `python3 tools/tripo_pipeline/convert_job.py <set>--<job-id>` (Tripo submit → collect → reduction for each module in turn; resumable, never resubmits a module that has a submission record). An unattended queue watcher that calls it is not yet connected. Never claim a conversion ran or move a job to `completed/` without its Tripo output and low-poly/material artifacts.
- **New concept batches use one folder per concept.** Write `concepts/<set_id>/<race_gender>/<module>_front.png` with `<module>_prompts.json` and a design record beside it. An armour set has `body_armor_front.png` and `right_gauntlet_boot_front.png` side by side in the same race folder; an outfit has `outfit_front.png`. Generate the entire requested set in one pass. Rejected generation attempts are not kept; record the attempt count in each prompts JSON. View retries in `processing_views/` still keep earlier versions. The two existing flat batches (`plate_armor_batch_01` and `plate_armor_pauldron_batch_01`) stay in their original layout and remain browseable in the preview site; `workflow.py promote concepts/<batch_id> <NN> [--set <set_id>] [--race <race_gender>] [--approve]` is retained for them and fails closed on incomplete or invalid entries.
- The user reviews concepts at `python3 tools/preview/serve.py --open` and approves or rejects them there. Approval moves a complete per-set folder into `approved/`; rejection moves it into `trash/concepts/` with a restore action. Never approve a set without the user's explicit action. Process `approved/` only when the user asks in chat. `workflow.py claim` reads the per-set fronts, moves prompt/design records into `.concept_notes/`, and creates the per-module `<module>/front.png` folders used from `processing_views/` onward.

- For each approved set, preserve the chosen `front.png`, generate `front_three_quarter.png`, `back.png`, and `back_three_quarter.png` from the same design and matching base views, then place the complete four-view set in `multiview_ready/`. The user chose automatic Tripo conversion once views are complete; do not add a second image-review gate. Until the queue watcher is connected, run `convert_job.py` on each job in `multiview_ready/` when its views are staged.
- **Backend policy (2026-10-22): use the Tripo backend by default for now** (about 25 Tripo credits per module); switch to `--backend hyper3d` only when Tripo credits run out (Hyper3D about 0.5 credits per model).
- Optional alternative backend: `convert_job.py <job> --backend hyper3d` runs Hyper3D Rodin (browser runner in `tools/hyper3d_pipeline/`, high-poly textured GLB, no Smart Low-poly) instead of Tripo; Tripo stays the default. Its paid steps need `--allow-paid --accept-preview` and a configured expected credit cost; its live UI is only partly verified, 0.5 credits per model on the default path (see `tools/hyper3d_pipeline/README.md`).
- `convert_job.py` calls `studio.mjs` with **Triangle** topology by default, H3.0, 2K texture, PBR off, Remove Lighting on, and a 2,000,000-face Studio *ceiling*. It exports the high-poly model under `models/` (plus `highpoly.blend`: textured, detected materials, seen/unseen) and runs three automatic low-poly options (geometry error 0.4%, 0.2%, 0.1% of normalized height). The 0.4% result is the default candidate; retain the other two as fallbacks. Each output must pass mesh/part checks or be marked for review. Low-poly polygon counts are outcomes, never fixed targets.
- After reduction, label each low-poly face base or one of the palette's garment roles (`primary`, `secondary`, and with the active white-anchor palette `tertiary`, `accent`; in **separable mode** also `joint`, cyan #14DCEB) from the source texture for later engine recoloring (`tools/tripo_pipeline/face_labels.py`; the colours come from the base's `palette.json`, `tools/tripo_pipeline/palette.py`; a base without one is legacy `tricolor_v1`): classify texture samples by **hue** (never by saturation distance; the shared white anchor is the one achromatic class: saturation < 0.25 and value > 0.45), weight them by pixel saturation/brightness and by whether a concept camera actually saw that surface, and settle faces with little usable evidence from the mirror face (symmetric modules), crease-aware neighbours and a soft module prior. The prior's body zones come from the base's per-face body parts (`base_views/<race>/parts.npz`, made by `tools/tripo_pipeline/base_parts.py` from `assets/marker_bases/<race>.blend`): the base is fitted to the mesh by a trimmed scale+translation ICP, every face takes the part of the nearest base surface (normal-aware, small islands merged, left/right never mirrored), and soft part membership gives the zones, so A-posed and legless bases work; without a parts file the T-pose landmarks of `regions.json` are used. A face clearly outside the fitted base body (beyond that part's bare-mesh clearance from `base_views/<race>/clearance.json` plus a margin, only where the module lets the garment be) cannot be bare base, so Tripo's red-baked armour-edge slivers become a garment role (label source `off_body`). A conservative hem-riser rule (label source `riser`) also flips base faces that touch a wear face, lie where garment is allowed and face along the limb (normal more than 60 degrees off the nearest base normal), at most 2 rings deep. Both rules need `clearance.json` (every active base has one). Sources whose area is mostly enclosed (a second inward-facing body shell) are audited and stripped of enclosed faces before reduction; see `tools/tripo_pipeline/README.md`. Store the transferred part per face as the `body_part` attribute in the review/wearable/high-poly blends and in the `_colors.npz` evidence. The prior only says where the base must be bare per the module definitions below; visible texture can still extend a garment past the nominal boundary. **Separable mode** (only when the user asks for separable parts; `palette.json` `separable_garments`, `reduce_model.py`/`convert_job.py` `--separable`, switched on automatically for jobs whose `prompts.json`/`.tripo-job.json` say `joint_bands`): the palette gains the fifth garment role `joint` (cyan) reserved for continuous joint bands; without the switch the labelling is identical to before (the base `palette.json` files only carry the optional block). Separable reductions (and palettes that list a `joint`/`quinary` role) also fit the hue centres to the model's own texture (`palette.py` `fit_hues`, `reduce_model.py --adaptive-hue auto|on|off`; per colour at most 30 degrees, never two colours on one cluster, ambiguous clusters flagged in the manifest `hue_fit`), because image generators repaint colours slightly (the magenta accent has come back hot pink, ~322-329 degrees); `tools/check_concept_colours.py` flags that on the concept image beforehand. Ordinary reductions keep the fixed palette hues. `body_armor` pieces are mirrored/handled as before (no mirroring for body armour). **Mirroring (wearable only):** concepts keep the anatomical-left hand/foot bare as anchors, so after labelling each LOD the wearable gets mirrored copies (reflected across the base's sagittal plane, mapped into mesh space by the ICP fit; winding flipped; same garment role; left `body_part`; label source `mirrored`, FACE attribute `mirrored`) of the right-side wear faces on the parts named by `config.json` `mirror_to_anchor_side` (`outfit`: foot; `right_gauntlet_boot`: hand, foot; `body_armor`: none; foot = foot + lower leg, hand = hand + forearm) whose mirrored position is bare base; a face whose left counterpart is already wear (a robe hem on both shins) is not copied, patches under 3 faces are dropped and the module prior limits growth. The full labelled LOD, its `_colors.npz` label arrays and the review blend are unchanged; the manifest records the plane, the base symmetry and the copied faces/area per level. Record per face which of texture/symmetry/prior/neighbours decided it, and flag a level for review when more than 20% of its area was decided without seen texture. A face no evidence decides (unseen, no neighbours) takes the garment role with the most seen area on that mesh (legacy `tricolor_v1` keeps `primary`). Retain source texture and color evidence, including `highpoly.blend` beside the source GLB. Material assignment follows whole-geometry reduction. When the palette identifies the bare base (red body and all anchors = `base`), remove those faces **after** assignment to export a separate wearable mesh; keep the colored full model as evidence. Review cut boundaries and mixed faces.
- **Split step for separable armour** (after reduction; the default for plate armour with per-piece base colours is **segment-first**, run by `convert_job.py` for `piece_colours` `body_armor` jobs: `segment_first_prep.py` (Blender) then `segment_first.py` (venv python) write `<job models dir>/<race>/body_armor/segment_first/{prep,levels,pieces}` (`--split-method segment-first|per-face|none` overrides; the method used is recorded in `.tripo-job.json` `module_conversion.<key>.split`); it classifies and cleans labels on the high-poly faces, cuts the sections there (seam fix on, cross-joint shelf on, overlap off) and reduces each section on its own, see the README section "Segment first, simplify second". If it fails, `convert_job.py` falls back to the per-face path below and records why. Optional per-face path / manual use: `tools/tripo_pipeline/split_pieces.py <reduced> [--rigid bands|snap|auto|colour|seam|zones|regions] [--overlap] [--pose-test]`, see its README section): the wearable is cut by face colour label into rigid pieces. Pauldrons first (`accent` rim/decoration, or the `roles` style), then, for plate mail, chest, pelvis, thigh_l/r and arm_l/r. `bands` (the default for a separable reduction, `--rigid auto`) uses the `joint` faces as bands at the armpits, waist and hips (each band a skinned `soft_<joint>` piece or split to the nearest rigid pieces); any joint without a usable band falls back to `snap` (colour/crease min-cut around the body-part zone boundary), and a model with no cyan at all is cut by `snap` on all joints. **Rigid sections with per-piece base colours** (`--rigid regions`, the per-face path for plate mail, the fallback of segment-first; `PROMPTING_GUIDE.md` has the colour table: chest/thighs green, arms/pelvis blue, pauldrons magenta, decoration yellow inset from the edges, standard 4-colour palette, no cyan): large connected same-colour regions of the non-pauldron faces are the sections, assigned by body part and expected colour (`config.json` `piece_split.body_armor.rigid.regions.expected`), the decoration they enclose is absorbed, and a joint whose cut is not a colour boundary (or lies inside one region spanning two sections) falls back to `snap`, reported per joint. `--rigid auto` (the default when the manifest has `hue_fit.active` or a joint palette) picks: `bands` with `joint` faces, `colour` with `quinary` faces, `regions` with at least 3 large same-colour regions of the expected section roles covering at least half the non-pauldron area, else `snap`. Jobs that say `piece_colours` run `reduce_model.py --adaptive-hue on` (`convert_job.py --piece-colours`). Default pose settings: pauldron convention `half`. **Overlap strips are off by default (2026-10-22; `--overlap` adds them: mode `both`, 6%, `config.json` `piece_split`).** **Cross-joint reassignment (on by default for rigid splits with a pelvis, `--no-cross-joint` to skip; `config.json` `rigid.cross_joint`, mode `shelf` since 2026-10-22):** a shelf/cap is a group of faces of section A next to the A|B boundary whose normals point along the joint axis back into A (e.g. the up-facing ledge at the bottom of the chest); it is geometrically the lid of B, so it moves to B and the cut follows the fold at its inner edge (validated on the user's P_29 selection; waist only by default). The older plane-distance rule (`mode plane`) moved vertical bands (abdomen band, baldric) and is superseded. Single-edge spike triangles standing >6% of height off a piece are dropped (`rigid.flaps`, `--keep-flaps`). Every move, drop and near miss is reported in `pieces.json` `rigid.cross_joint` / `rigid.flaps`. The pieces are rigid: nothing is closed or remeshed, only cut, with hidden overlap strips at cuts between pieces that move relative to each other. Outputs (`pieces/lod_<lv>/*.glb`, `pieces_<lv>.blend`, `pieces.json`, renders) live beside `reduced/` (segment-first: under `segment_first/pieces/`); they are derived data, never moved into `completed/` instead of the reduction.
- Move all view images with prompts and provenance records to `completed/` only after successful conversion, low-poly variants and material output. On failure, keep a job recoverable in its current stage or `failed/`; never overwrite prior attempts or frozen input snapshots.

## Concepts and views

- For new raster references use the local imagegen skill and built-in image generation tool. No CLI/API fallback without user authorization. Read `PROMPTING_GUIDE.md` before generation.
- Use `base_views/<race>_<gender>/<view>.png` as the edit target for each view. The active human-male base is a native **1254 × 1254** render with 45° three-quarter cameras (front-left from above, back-right from below; see `base_views/human_male/NOTES.md`); the previous level-camera 1254 set is archived at `archive/base_views_studio_plain_markers_1254_level_20261021/human_male/`; the former 1024 set is archived at `archive/base_views_studio_plain_markers_1024_20261021/human_male/`. The existing staged armor job remains 1024 and validates against its frozen `.base_views/` snapshot. A 2048 experiment remains separate. Never overwrite base images. Preserve proportions, faceted anatomy, T-pose, camera angle, framing, alpha and uncovered base material/color. The active views of every race are studio-plain **semantic marker** views with the **white-anchor** palette (`white_anchor_v2`, since 2026-10-22; `base_views/<race>/palette.json`): red body #E61923 and ONE shared achromatic anchor #EDEDED on the head, anatomical-left hand and anatomical-left foot. Keep those uncovered colors intact. The previous tri-colour bases (yellow head, magenta left hand, cyan left foot; `tricolor_v1`) are archived with their `palette.json` at `archive/base_views_markers_tricolor_20261022/`; a concept drawn on one must not be mixed with the white bases (`workflow.py claim` detects the base from the concept's anchor colours and snapshots the matching archived set, or take `--base-views <dir>`). The old kraft-paper base views are archived at `archive/base_views_kraft_20261021/`; since 2026-10-22 every other race has a matching active marker set in `base_views/<race>/` (same scene, cameras and size; see `base_views/README.md`).
- For the active marker base, use up to four broad garment/armor colours: green `primary` (#19D228, dominant), blue `secondary` (#1E41EB), and optionally yellow `tertiary` (#F5DC14, trim) and magenta `accent` (#E119DC, small motifs), all distinct from the red body and the white anchors. The red base is not a final character color; it identifies body surfaces for later removal.
- Style: simple papercraft, broad polygon planes, crisp folds, matte cardstock, and large readable garment color regions (primary/secondary, optional tertiary/accent). Avoid smooth anatomy, photoreal metal, fine noise and excessive ornament. Concept colors encode later material regions, not final engine colors.
- No weapons, props, hats, capes, labels or unrelated garments unless requested. Headwear/hood handling is deferred; keep the head bare for now.

### Armor set

1. `right_gauntlet_boot`: exactly one gauntlet on anatomical RIGHT hand/forearm and one boot on RIGHT foot/lower leg. Leave torso, upper arms, thighs and the opposite side as the base in the concept views. The reduced **wearable** mirrors the gauntlet and boot onto the bare left hand/forearm and foot/lower leg (so the engine gets a pair); the labelled LOD keeps the concept's one-sided labels.
2. `body_armor`: torso including back, shoulders/upper arms and both upper legs. Stop above elbows and knees. Leave forearms, hands, lower legs, feet, neck and head as the base.

Right means anatomical right, never a fixed picture side: viewer-left from front, viewer-right from back. Follow that limb through three-quarter views. Both outputs show the full base wearing only their own module, not floating parts or the combined outfit.

### Regular outfit

- One `outfit` module covers the clothing as a whole, including the right foot if the design has footwear. Keep the **head, both hands and anatomical LEFT foot bare** for alignment and future separation. Do not add gloves or headwear. The bare left foot is viewer-right in front and viewer-left in back. The reduced **wearable** mirrors the right footwear onto the bare left foot (where the left foot/lower leg is bare base); hands stay bare.
- Keep the covered/uncovered boundary consistent across views. Do not split a regular outfit into armor modules.

## Output and review

- Delivered images must match the pixel width and height of their corresponding base and retain alpha. The current human male bases are 1254 × 1254; inspect each future base rather than assuming that size. **Do not resize, crop, pad or stretch generated images or rendered bases to make dimensions match.** Ask imagegen for the native base dimensions, inspect the actual saved pixels, and reject/retry any mismatch.
- Use `front.png`, `front_three_quarter.png`, `back.png`, `back_three_quarter.png`. Do not crop/pad views or infer camera matrices as an approval condition.
- Record exact prompts, reference paths, design/color details and review notes; retain earlier versions when revising a view (rejected concept generation attempts are not kept; record their count). Do not edit frozen models or active `processing/` inputs.
- Review all views for module boundaries, anatomical side, pose/camera drift, silhouette, dimensions, alpha and panel/color continuity. These are concept references, not guaranteed pixel-registered overlays.
- Use `experiments/` only for explicitly requested experiments. Past `pending/`, `completed/` and model records are historical and must not be cleaned up for the new workflow.
