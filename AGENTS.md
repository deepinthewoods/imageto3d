# Papercraft outfit concepts and Tripo Studio workflow

**Read `CLAUDE.md` as well, at the start of every task (user rule 2026-10-30).** It is the companion to this file: it splits the pipeline between Claude and Codex (Codex jobs generate concept fronts, views and view retries; Claude runs `workflow.py` state changes, folder moves, conversions and `completed/`), says how Codex job prompts are written and what they must contain, and lists the review steps after a job. A job prompt's own scope limits still apply on top of it. Where the two files disagree, the newer dated user rule in this file wins.

## Current pipeline

- Use Tripo Studio with the **studio plain paper** source-image look. The chosen reference export and reduction experiments are recorded in `tools/tripo_pipeline/pipeline_decisions.json` and `experiments/tripo_method_gallery_01/`.
- The old `pixal3d-armor-queue` service was disabled on 21 October 2026. Do not restart it or use its old `approved/` contract for new work. Its code and past outputs remain under `tools/pixal3d_queue/` and `models/` for recovery.
- See `tools/tripo_pipeline/README.md` for the folder contract, processing commands and current Tripo website automation. Convert a staged job with `python3 tools/tripo_pipeline/convert_job.py <set>--<job-id>` (Tripo submit → collect → reduction for each module in turn; resumable, never resubmits a module that has a submission record). The convert worker (`tools/convert_queue.py`, run by the preview app, see below) calls it for every staged job of a listed set (superseded 2026-11-25: "an unattended queue watcher is not yet connected"). Never claim a conversion ran or move a job to `completed/` without its Tripo output and low-poly/material artifacts.
- **New concept batches use one folder per concept.** Write `concepts/<set_id>/<race_gender>/<module>_front.png` with `<module>_prompts.json` and a design record beside it. An armour set has `body_armor_front.png` and `right_gauntlet_boot_front.png` side by side in the same race folder; an outfit has `outfit_front.png`. Generate the entire requested set in one pass. **Concept generation is one-shot with no checks (user rule 2026-10-28):** never run `check_framing.py`/`check_concept_colours.py` on concept art, never inspect or regenerate a concept for framing, pose, colours or style — generate each concept once and save it (regenerate only a file that saved at the wrong pixel size or without alpha, once). Framing drift is accepted at concept stage because approved concepts are re-drawn from the bases as views (next bullet). Rejected generation attempts are not kept; record the attempt count in each prompts JSON and write `"skipped"` for the check fields. View retries in `processing_views/` still keep earlier versions. The two existing flat batches (`plate_armor_batch_01` and `plate_armor_pauldron_batch_01`) stay in their original layout and remain browseable in the preview site; `workflow.py promote concepts/<batch_id> <NN> [--set <set_id>] [--race <race_gender>] [--approve]` is retained for them and fails closed on incomplete or invalid entries.

View framing checks still apply to all four generated views. `workflow.py claim` and `view_batch.py add-views` implement this (the views task's outputs include a freshly generated `front.png`; the concept front moves to `.concept_notes/` as reference). Then place the complete four-view set in `multiview_ready/`. The user chose automatic conversion once views are complete; do not add a second image-review gate. The convert worker the app manages converts each staged job of a listed set (superseded 2026-11-25: "until the queue watcher is connected, run `convert_job.py` on each job in `multiview_ready/` by hand").

This applies going forward: views already generated with trimmed hems are not regenerated. - **Backend policy (2026-10-22): use the Tripo backend by default for now** (about 25 Tripo credits per module); switch to `--backend hyper3d` only when Tripo credits run out (Hyper3D about 0.5 credits per model). An unreadable balance holds the job (`HOLD`, not a failure) and is read again later; it never switches to Hyper3D.

Its remesh makes a double-walled skin that the reduction's interior strip removes; levels come out denser than Tripo's and are flagged for material review. See `tools/pixal3d_pipeline/README.md`. **Do not use `--backend formy3d` (user, 2026-11-18: save those credits).**
- `convert_job.py` calls `studio.mjs` with **Triangle** topology by default, H3.0, 2K texture, PBR off, Remove Lighting on, and a 2,000,000-face Studio *ceiling*. It exports the high-poly model under `models/` and runs three automatic low-poly options (geometry error 0.4%, 0.2%, 0.1% of normalized height). The 0.4% result is the default candidate; retain the other two as fallbacks. Each output must pass mesh/part checks or be marked for review. Low-poly polygon counts are outcomes, never fixed targets.
- After reduction, label each low-poly face base or one of the palette's garment roles (`primary`, `secondary`, and with the active white-anchor palette `tertiary`, `accent`; in **separable mode** also `joint`, cyan #14DCEB) from the source texture for later engine recoloring (`tools/tripo_pipeline/face_labels.py`; the colours come from the base's `palette.json`, `tools/tripo_pipeline/palette.py`; a base without one is legacy `tricolor_v1`): classify texture samples by **hue** (never by saturation distance; the shared white anchor is the one achromatic class: saturation < 0.25 and value > 0.45), weight them by pixel saturation/brightness and by whether a concept camera actually saw that surface, and settle faces with little usable evidence from the mirror face (symmetric modules), crease-aware neighbours and a soft module prior. The prior's body zones come from the base's per-face body parts (`base_views/<race>/parts.npz`, made by `tools/tripo_pipeline/base_parts.py` from `assets/marker_bases/<race>.blend`): the base is fitted to the mesh by a trimmed scale+translation ICP, every face takes the part of the nearest base surface (normal-aware, small islands merged, left/right never mirrored), and soft part membership gives the zones, so A-posed and legless bases work; without a parts file the T-pose landmarks of `regions.json` are used. A face clearly outside the fitted base body (beyond that part's bare-mesh clearance from `base_views/<race>/clearance.json` plus a margin, only where the module lets the garment be) cannot be bare base, so Tripo's red-baked armour-edge slivers become a garment role (label source `off_body`). A conservative hem-riser rule (label source `riser`) also flips base faces that touch a wear face, lie where garment is allowed and face along the limb (normal more than 60 degrees off the nearest base normal), at most 2 rings deep. Both rules need `clearance.json` (every active base has one). Sources whose area is mostly enclosed (a second inward-facing body shell) are audited and stripped of enclosed faces before reduction; see `tools/tripo_pipeline/README.md`. Store the transferred part per face as the `body_part` attribute in the review/wearable/high-poly blends and in the `_colors.npz` evidence. The prior only says where the base must be bare per the module definitions below; visible texture can still extend a garment past the nominal boundary. **Separable mode** (only when the user asks for separable parts; `palette.json` `separable_garments`, `reduce_model.py`/`convert_job.py` `--separable`, switched on automatically for jobs whose `prompts.json`/`.tripo-job.json` say `joint_bands`): the palette gains the fifth garment role `joint` (cyan) reserved for continuous joint bands; without the switch the labelling is identical to before (the base `palette.json` files only carry the optional block). Separable reductions (and palettes that list a `joint`/`quinary` role) also fit the hue centres to the model's own texture (`palette.py` `fit_hues`, `reduce_model.py --adaptive-hue auto|on|off`; per colour at most 30 degrees, never two colours on one cluster, ambiguous clusters flagged in the manifest `hue_fit`), because image generators repaint colours slightly (the magenta accent has come back hot pink, ~322-329 degrees); `tools/check_concept_colours.py` flags that on the concept image beforehand. Ordinary reductions keep the fixed palette hues. `body_armor` pieces are mirrored/handled as before (no mirroring for body armour). **Mirroring (wearable only; method `faces`, in `cut` the left piece is the exact reflection of the cut right piece instead):** concepts keep the anatomical-left hand/foot bare as anchors, so after labelling each LOD the wearable gets mirrored copies (reflected across the base's sagittal plane, mapped into mesh space by the ICP fit; winding flipped; same garment role; left `body_part`; label source `mirrored`, FACE attribute `mirrored`) of the right-side wear faces on the parts named by `config.json` `mirror_to_anchor_side` (`outfit`: foot; `right_gauntlet_boot`: hand, foot; `body_armor`: none; foot = foot + lower leg, hand = hand + forearm) whose mirrored position is bare base; a face whose left counterpart is already wear (a robe hem on both shins) is not copied, patches under 3 faces are dropped and the module prior limits growth. The full labelled LOD, its `_colors.npz` label arrays and the review blend are unchanged; the manifest records the plane, the base symmetry and the copied faces/area per level. Record per face which of texture/symmetry/prior/neighbours decided it, and flag a level for review when more than 20% of its area was decided without seen texture. A face no evidence decides (unseen, no neighbours) takes the garment role with the most seen area on that mesh (legacy `tricolor_v1` keeps `primary`). Retain source texture and color evidence (the source GLB and the `_colors.npz` arrays). `highpoly.blend` (textured, detected materials, seen/unseen) is no longer kept (user, 2026-10-26: ~150 MB per module filled the disk); `reduce_model.py --highpoly-blend` or `make_highpoly_blend.py` builds one on demand. **One high-poly model per module (user rule 2026-11-14, after the disk filled again):** `source.glb` is the only stored copy; the backend download beside it is a hard link to the same file, and `reduced/source_import.blend` (an unread Blender re-import, ~40 MB per module) is deleted at the end of the reduction unless `--highpoly-blend` is given. **Heavy working files live on the Toshiba drive (user, 2026-11-18):** `review.blend`, `prep.npz`, `source_geometry.npz`, old `highpoly_v1_*.blend`, `source_import.blend` and `obj_*.zip` of modules converted before that date were moved to `D:\godot_characters_3d\imageto3d\models\<same relative path>` (README there); copy a module's files back before running `rewear.py`, `apply_feature_labels.py`, `relabel_module.py` or `segment_first.py` on it. The high-poly GLBs (`source.glb` and the backend download GLBs) moved too; a symlink stays at each `source.glb`. **New sets follow automatically:** while a set is being processed its files stay on the SSD; when `finish_sets.py` moves the set to `completed/`, the conversion worker runs `tools/tripo_pipeline/offload_models.py` on its jobs (config.json `offload`; event `OFFLOAD`; each file SHA-256 verified before removal; a missing drive only skips the move, and `offload_models.py --completed --apply` catches up later). Material assignment follows whole-geometry reduction. When the palette identifies the bare base (red body and all anchors = `base`), remove those faces **after** assignment to export a separate wearable mesh; keep the colored full model as evidence. Review cut boundaries and mixed faces.
- **Wearable method (2026-10-24, default `cut`; `reduce_model.py --wearable-method cut|faces`, `convert_job.py --wearable-method`)**: the wearable is no longer the reduced level minus its base faces (that stays as method `faces`, the automatic per-level fallback, and keeps its files as `lod_error_<lv>__wearable_faces.glb` / `lod_error_<lv>_colors_wearable_faces.npz` / `wearable_faces.blend`). `cut` works on the high-poly mesh (`wearcut.py`, `wearcut_blender.py`, README "Wearable by cut"): the mesh's winding is made consistent and outward, every face is classified from the texture with the palette **the reduction used** (its hue shifts are kept unless they lose most of the garment colour on the high-poly mesh), evidence is pooled with the mirror partner across the fitted mirror plane where both sides agree locally and the design is symmetric there, the off-body and hem-riser rules of this section run on the high-poly faces, a Potts clean-up and a smooth vertex field give a clean 0.5 iso-line, the mesh is **cut** along it (triangles split, nothing deleted whole), the garment alone is reduced at 0.4/0.2/0.1% with its open boundary simplified as a polyline, and flap triangles are dropped. For `right_gauntlet_boot` (and the outfit's right footwear when it is a separate component) only the right piece is cut; **the left piece is its exact reflection** (welded, mirror error ~1e-6 % of height) with the left counterpart `body_part` and label source `mirrored`; an outfit without separable right footwear falls back to `faces` for the module. The labelled levels and their evidence are unchanged. The cut wearable's sidecar arrays are in the new GLB's face order (`wearable_body_part_glb_order`, `wearable_label_source_glb_order`, `wearable_mirrored_glb_order`; `wearable_face_order` is -1 because the faces have no review-mesh counterpart); manifest `wearable` and `levels.<lv>.wearable` record the method, plane, rules, hue decision and any fallback reason. Backfill with `tools/tripo_pipeline/rewear.py`.
- **Opt-in feature label passes (2026-10-25; `tools/tripo_pipeline/feature_hooks.py`, README "Feature label passes")**: off unless chosen per set (`config.json` `feature_labels.sets`, a job record's `feature_labels`, or `--feature-labels studs|rings:secondary|rings:void` on `convert_job.py` / `reduce_model.py` / `rewear.py` / `relabel_module.py` / `segment_first.py`). They correct the HIGH-POLY labels after the normal cleaning and before the cut / section reduction: `studs` keeps round tertiary studs whole (and removes their spill), `rings` classifies chain-mail ring tubes vs centres from the geometric relief and gives the centres their own role or removes them (`void`). Only garment roles change (void aside), so the garment/base cut does not move; the cut wearable, the labelled full LODs (GLB, colours npz, review.blend) and the rigid pieces all get the corrected labels, and the choice is recorded in `reduced/manifest.json` `wearable.feature_labels`. Already converted modules are updated with `apply_feature_labels.py`, which backs up what it replaces and re-runs `body_fit.py`.
- **Split step for separable armour** (after reduction; the default for plate armour with per-piece base colours is **segment-first**, run by `convert_job.py` for `piece_colours` `body_armor` jobs: `segment_first_prep.py` (Blender) then `segment_first.py` (venv python) write `<job models dir>/<race>/body_armor/segment_first/{prep,levels,pieces}` (`--split-method segment-first|per-face|none` overrides; the method used is recorded in `.tripo-job.json` `module_conversion.<key>.split`); it classifies and cleans labels on the high-poly faces, cuts the sections there (seam fix on, cross-joint shelf on, overlap off) and reduces each section on its own, see the README section "Segment first, simplify second". If it fails, `convert_job.py` falls back to the per-face path below and records why. Optional per-face path / manual use: `tools/tripo_pipeline/split_pieces.py <reduced> [--rigid bands|snap|auto|colour|seam|zones|regions] [--overlap] [--pose-test]`, see its README section): the wearable is cut by face colour label into rigid pieces. Pauldrons first (`accent` rim/decoration, or the `roles` style), then, for plate mail, chest, pelvis, thigh_l/r and arm_l/r. `bands` (the default for a separable reduction, `--rigid auto`) uses the `joint` faces as bands at the armpits, waist and hips (each band a skinned `soft_<joint>` piece or split to the nearest rigid pieces); any joint without a usable band falls back to `snap` (colour/crease min-cut around the body-part zone boundary), and a model with no cyan at all is cut by `snap` on all joints. **Rigid sections with per-piece base colours** (`--rigid regions`, the per-face path for plate mail, the fallback of segment-first; `PROMPTING_GUIDE.md` has the colour table: chest/thighs green, arms/pelvis blue, pauldrons magenta, decoration yellow inset from the edges, standard 4-colour palette, no cyan): large connected same-colour regions of the non-pauldron faces are the sections, assigned by body part and expected colour (`config.json` `piece_split.body_armor.rigid.regions.expected`), the decoration they enclose is absorbed, and a joint whose cut is not a colour boundary (or lies inside one region spanning two sections) falls back to `snap`, reported per joint. `--rigid auto` (the default when the manifest has `hue_fit.active` or a joint palette) picks: `bands` with `joint` faces, `colour` with `quinary` faces, `regions` with at least 3 large same-colour regions of the expected section roles covering at least half the non-pauldron area, else `snap`. Jobs that say `piece_colours` run `reduce_model.py --adaptive-hue on` (`convert_job.py --piece-colours`). Default pose settings: pauldron convention `half`. **Overlap strips are off by default (2026-10-22; `--overlap` adds them: mode `both`, 6%, `config.json` `piece_split`).** **Cross-joint reassignment (on by default for rigid splits with a pelvis, `--no-cross-joint` to skip; `config.json` `rigid.cross_joint`, mode `shelf` since 2026-10-22):** a shelf/cap is a group of faces of section A next to the A|B boundary whose normals point along the joint axis back into A (e.g. the up-facing ledge at the bottom of the chest); it is geometrically the lid of B, so it moves to B and the cut follows the fold at its inner edge (validated on the user's P_29 selection; waist only by default). The older plane-distance rule (`mode plane`) moved vertical bands (abdomen band, baldric) and is superseded. Single-edge spike triangles standing >6% of height off a piece are dropped (`rigid.flaps`, `--keep-flaps`). Every move, drop and near miss is reported in `pieces.json` `rigid.cross_joint` / `rigid.flaps`. The pieces are rigid: nothing is closed or remeshed, only cut, with hidden overlap strips at cuts between pieces that move relative to each other. Outputs (`pieces/lod_<lv>/*.glb`, `pieces_<lv>.blend`, `pieces.json`, renders) live beside `reduced/` (segment-first: under `segment_first/pieces/`); they are derived data, never moved into `completed/` instead of the reduction.
- **Everything idles with the user at the PC (user rule 2026-10-29, after a GPU crash under full pipeline load):** the supervisor's user-active pause now covers BOTH image generation and conversions (`SCREEN_ON_SCOPE` = conversions + views). The whole pipeline - view generation included - runs only when the PC is idle (5 min no input or screen locked). **Superseded for image generation (user, 2026-11-13: "resume the image generation even if we're non-idle"):** the supervisor runs in mode `views-run`, where the user-active pause covers conversions only. Image generation (concepts, fronts, views) runs whether or not the user is at the PC; the supervisor's PAUSE file is the only authority on pausing, so a Codex image job never declines or waits because the PC is in use. ## Output and review

- Delivered images must match the pixel width and height of their corresponding base and retain alpha. The current human male bases are 1254 × 1254; inspect each future base rather than assuming that size. **Do not resize, crop, pad or stretch generated images or rendered bases to make dimensions match.** Ask imagegen for the native base dimensions, inspect the actual saved pixels, and reject/retry any mismatch.
- Use `front.png`, `front_three_quarter.png`, `back.png`, `back_three_quarter.png`. Do not crop/pad views or infer camera matrices as an approval condition.
- **Three-view modules are a fallback only** after repeated generation refusals of one non-front view: mark the module folder with `views_omitted.json` (`{"omitted": ["back"], "reason": ..., "date": ...}`, exactly one non-front view, `front.png` always required); gnome modules made before 2026-10-26 instead omit both three-quarter views (front + back only); `workflow.py`, the backends and `convert_job.py` then convert from the three views that exist (see `tools/tripo_pipeline/README.md`).
- Record exact prompts, reference paths, design/color details and review notes; retain earlier versions when revising a view (rejected concept generation attempts are not kept; record their count). Do not edit frozen models or active `processing/` inputs.
- Review all views for module boundaries, anatomical side, pose/camera drift, silhouette, dimensions, alpha and panel/color continuity. These are concept references, not guaranteed pixel-registered overlays.
- Use `experiments/` only for explicitly requested experiments. Past `pending/`, `completed/` and model records are historical and must not be cleaned up for the new workflow.
