# Front concepts → four views → Tripo Studio → low-poly materials

This is the current parent-project workflow. The user chose the **studio plain paper** source-image look and local cleanup plus geometry reduction at **0.4% of body height** as the default. Also retain **0.2% and 0.1%** variants so a reviewer can switch when a garment or armor panel needs more detail. None of these settings asks for a polygon count. On the reference character the results were 436, 626 and 1,352 triangles, with about 0.45–0.49 seconds of simplification and about 0.17–0.19 seconds of measurement/export per variant after shared preparation. New assets will have different counts and times.

The selected reference and decision record are at `pipeline_decisions.json`; the eight-scene comparison and metrics are under `../../experiments/tripo_method_gallery_01/`. Studio's original reference model version is unknown. New submissions use confirmed H3.0, 2K texture, PBR off, Remove Lighting on, and **Triangle by default**; `config.json` records those choices.

## Folder states

```text
concepts/<set>/<race_gender>/{body_armor,right_gauntlet_boot}_front.png   (new armor concept, one folder per set)
concepts/<set>/<race_gender>/outfit_front.png                            (new outfit concept)
              │ user approves in the local preview site; rejection goes to restorable trash/concepts/
              ▼
approved/<set>/... same flat <module>_front.png layout
              │ chat request: process approved outfits
              ▼
processing_views/<set>--<job-id>/<race_gender>/<module>/ front.png + generated other views
              │ (claim unflattens the fronts; notes/rejects go to <race_gender>/.concept_notes/)
              │ all four views verified per module
              ▼
multiview_ready/<set>--<job-id>/... four views + frozen hashes
              │ Firefox Playwright submit/collect; queue watcher pending
              ▼
processing/<set>--<job-id>/... website conversion in progress
              │ Tripo GLB + 0.4/0.2/0.1% low-poly GLBs + flat material review
              ├── models/<set>/<job-id>/<race_gender>/<module>/...
              └── completed/<set>--<job-id>/... images, prompts, job record
```

An armor set has **both** `body_armor` and `right_gauntlet_boot` fronts for each character. A regular outfit has one `outfit` front. They are separate jobs/set types; do not combine them into a single image. The outfit leaves head, both hands and anatomical left foot bare. Headwear and hoods await a later decision. Use large, matte garment color regions (up to four: primary green, secondary blue, tertiary yellow, accent magenta; never white) plus the unchanged exposed base so the generated texture can later be assigned to engine materials.

Concept generation produces fronts in `concepts/`; it does not move anything to `approved/`. The user approves or rejects in the local preview site (`python3 tools/preview/serve.py --open`), which moves the whole set or sends it to restorable `trash/concepts/`. `archive/concepts/<set>/` (same layout) holds sets kept for reference but out of the review queue, restorable from the site (Unarchive, or Approve straight to `approved/`). The two existing flat batches remain visible in that site (in `concepts/` or, once archived, `archive/concepts/<batch>/`); `workflow.py promote` is retained only to approve their legacy entries. The assistant processes approved sets when asked in chat. It preserves each selected front, generates the three other views from corresponding base views, checks all images, and stages the completed set with `workflow.py ready`. The active base views (all races) are native 1254 × 1254 studio-plain semantic-marker renders with the `white_anchor_v2` palette: red body and ONE shared white anchor on the head, anatomical-left hand and anatomical-left foot (the former yellow/magenta/cyan anchors, scheme `tricolor_v1`, are archived at `archive/base_views_markers_tricolor_20261022/`). The prior 1024 set is archived at `archive/base_views_studio_plain_markers_1024_20261021/human_male/`. The old brown views and other races are archived at `archive/base_views_kraft_20261021/`; since 2026-10-22 all eleven races have matching active marker views (`build_marker_base.py` + `render_marker_base.py`). The user chose conversion to run automatically after the four views exist, without a second review stop. `studio.mjs` now provides reusable Firefox Playwright submission and collection for a four-view module. It is not yet connected to a background queue watcher; `multiview_ready/` jobs remain staged until that connection and its recovery rules are tested. The approved arcane plate mail job has not yet been uploaded.

Past Pixal3D results remain in `models/` and `completed/`. The Pixal3D user service was disabled and stopped before this contract was installed. Do not reactivate it while `approved/` has front-only Tripo selections.

## Validator and staging commands

From the parent project directory:

```bash
python3 tools/tripo_pipeline/workflow.py status
python3 tools/tripo_pipeline/workflow.py check approved/<set>
python3 tools/tripo_pipeline/workflow.py promote concepts/<batch_id> <NN> [--set <set>] [--approve]   # existing legacy flat batches only
python3 tools/tripo_pipeline/workflow.py claim <set>
# Generate the three other views for each module in processing_views/<set>--<job-id>/.
python3 tools/tripo_pipeline/workflow.py ready <set>--<job-id>
# Convert: moves the job to processing/, then per module Tripo submit -> collect -> reduce.
python3 tools/tripo_pipeline/convert_job.py <set>--<job-id>            # --dry-run: fill Studio's form only
```

Before generating or staging views run `python3 tools/check_framing.py <base view> <image...>` (palette-aware: white-anchor blobs or legacy hue markers, see `PROMPTING_GUIDE.md`) and open every imagegen prompt with `python3 tools/framing_lock.py <base view>`; both read `palette.json` beside the base view. `tools/test_check_framing.py` checks all 44 active base views against themselves.

**Optional backend:** `convert_job.py <job> --backend hyper3d` swaps the Tripo submit/collect for Hyper3D Rodin (high-poly textured GLB, no Smart Low-poly, credit-guarded, no free-retry loop); Tripo stays the default and is unchanged. Setup, flags and what is still unverified: `../hyper3d_pipeline/README.md`.

**Optional backend: formy3d.** `convert_job.py <job> --backend formy3d [--dry-run] [--allow-paid]` swaps the Tripo submit/collect for formy3d.com's Tripo3D H3.1 multi-view generator (browser runner `../formy3d_pipeline/`, cookies copied from ordinary Firefox, hidden X display; all four views in the Front/Left/Right/Back slots, Texture HD, Detailed geometry, PBR off, triangle mesh, GLB). Generate (167 credits per module) is the only paid click: it needs `--allow-paid` and a displayed price equal to `expected_costs.generate`; collect and the GLB download are free; no free-retry loop. Tripo stays the default. Probe findings (incl. formy3d's Part tool: FBX input, 150 credits) and what is unverified until a supervised paid run: `../formy3d_pipeline/README.md`.

`convert_job.py` runs modules strictly one at a time (Studio greys out Generate while another model of the account is generating; `studio.mjs` waits up to `TRIPO_QUEUE_WAIT_MIN`, default 30). Collection polls until Studio shows the finished model (`TRIPO_COLLECT_WAIT_MIN`, default 30) and retries a blocked export click. It is resumable: a module with a submission record is only collected, a reduced module is skipped. It leaves the job in `processing/` with state `converted` and lists the levels needing review; move it to `completed/` after that review.

**Split step (2026-10-22).** After the reduction a `piece_colours` `body_armor` module (job records say so, or `--piece-colours`) is cut into rigid pieces by **segment-first** (section "Segment first, simplify second" below): `segment_first_prep.py` in Blender -> `<module>/segment_first/prep/` (skipped when `prep.npz` exists), then `segment_first.py` with the venv python (numpy + scipy + Pillow: `$SEGMENT_FIRST_PYTHON`, else `config.json` `segment_first.venv_python`, else `<imageto3d>/../.venv/bin/python`; a clear message when none exists) -> `<module>/segment_first/{levels,pieces,segment_first.json}` (skipped when `pieces/pieces.json` exists). Cameras, regions and palette are the ones `reduced/manifest.json` records, so prep sees exactly what `reduce_model.py` saw (the palette is frozen as `segment_first/palette_used.json`). Logs: `segment_first/prep.log`, `segment_first/segment_first.log`. If segment-first fails for any reason the step falls back to `split_pieces.py <module>/reduced --rigid auto` (output `<module>/pieces/`, log `pieces_per_face.log`), prints a WARNING and records why; the split step never fails the conversion. `--split-method segment-first|per-face|none` overrides the choice (default segment-first for `piece_colours` `body_armor`, `none` for every other job; joint-band separable jobs are not split by `convert_job.py`, run `split_pieces.py --rigid bands` by hand). The method used is recorded in `.tripo-job.json` `module_conversion.<race>/<module>.split` (`requested`, `method`, `status` done|fallback|failed|skipped, `outputs`, `fallback_reason`) and in `<module>/split_step.json`.

**Align step (2026-10-26).** After the split (and before the job record is updated) `convert_job.py` runs `align_body.py <module>` and, when that wrote `fit/align.json`, `body_fit.py <module> --source aligned` (section "Alignment to the base body" below; about 2 minutes per module, the venv python of the split step; both logged to `<module>/align_step.log`, body_fit's summary file goes to a temp folder so `experiments/` is untouched). The two scripts skip a module whose `.module_locks/<race>__<module>.lock` is held by a live process, and `convert_job.py` holds exactly that lock while it converts, so it passes its own pid in `$MODULE_LOCK_OWNER`; `rewear.module_busy()` returns False for a lock held by that pid and stays True for any other live holder. The step never fails the conversion: any error, skip or failure is recorded, not raised. Record: `<module>/align_step.json` and `.tripo-job.json` `module_conversion.<race>/<module>.align` = `{status done|failed|skipped, align: {status, residual_mm: {before, after}, warnings}, fit: {status, warnings, levels: {<lv>: {poke_after_cm2, max_displacement_mm}}}, error?}` (`done` = both scripts done or fresh; a script that skips, e.g. no cached base for the race, makes the step `skipped`); the console gets one `== <race>/<module>: align <status> (...)` line. `--no-align` skips it (record `{status: skipped, why}`), as does `config.json` `"align": {"enabled": false}`; `--dry-run` never reaches it. Modules converted before this (or with `--no-align`) are backfilled with `align_body.py --all` then `body_fit.py --all --source aligned`.

**Redo a bad Tripo result with a free retry first.** Every Studio project offers "Free Retry (×3)": it regenerates from the same inputs and settings without charging credits (verified 2026-10-22: balance unchanged, counter 3 → 2; the previous version stays in the project's model history). `node tools/tripo_pipeline/studio.mjs retry <previous_output_dir> <new_output_dir>` clicks it (the click starts the retry immediately, no confirmation; `TRIPO_DRY_RUN=1` only reads the counter) and writes a submission record that `studio.mjs collect <new_output_dir>` then fetches; collect waits while the retry is still generating. Keep the failed attempt beside the module (e.g. `<module>_attempt01_<reason>/`), put the retry in the module folder, and reduce it. `convert_job.py` does this automatically for a broken mesh (currently a doubled interior shell): it keeps each failed attempt as `<module>_attemptNN_interior_shell/` and retries until the mesh is clean. When all three free retries are used it does **not** pay for another generation: the last attempt stays as the module output, the module is flagged `free_retries_exhausted` / `needs_manual_review` in `.tripo-job.json`, the job state becomes `converted_with_errors`, and the script prints an ERROR line and exits 1. A paid resubmission is a manual decision after looking at why every attempt failed.

The validator requires matching native base and generated-view dimensions, nonempty RGBA with transparency, and either both armor modules or one outfit module. Newly approved sets use active `base_views/<race_gender>/`; claiming freezes all four base views (plus transforms/regions/parts/clearance/**palette.json**) in the job’s hidden `.base_views/<race_gender>/` snapshot. `claim` first checks which base the approved fronts were drawn on: the share of the base's bare-anchor pixels that are still anchor-coloured in each concept front (`workflow.anchor_match`, threshold 0.5). A front made on the old tricolor base is therefore snapshotted with `archive/base_views_markers_tricolor_20261022/<race>/` (an archived set is eligible only when it carries a `palette.json`), never with the white base; several different matching archives, or a front matching nothing, is an error (fail closed). `claim <set> --base-views <folder of race bases>` overrides the detection. The job record keeps `base_view_sources` (path, scheme, scores). Ready/staged jobs validate against that snapshot, so a later active-base resolution change cannot invalidate an older set. It rejects symlinks and extra/missing PNG views. Claiming records SHA-256 hashes of user-approved fronts. Staging verifies those hashes again and writes hashes for all four views before the folder move. The tool never generates images, invokes Tripo or marks a job completed. Preserve prompt/color records alongside the images. Do not edit an active/frozen job behind the worker's back.

**Three-view modules (fallback only).** When imagegen repeatedly refuses one non-front view of a module (e.g. the back view of a female base), the module folder may carry `views_omitted.json` (`{"omitted": ["back"], "reason": "...", "date": "..."}`; validated by `views_omitted.py`) instead of that PNG. `front.png` is always required and exactly one of the other three views may be omitted; a marker that omits front, omits more than one view or names a view whose PNG exists is rejected. Without the file nothing changes. `workflow.py check --complete`/`ready` then expect the three present views, hash them, and record the marker under `modules[].views_omitted` in `.tripo-job.json` (a marker edited after staging is rejected). `studio.mjs submit` uploads only the present views by Studio's slot label (Front/Left/Right/Back; the omitted slot stays empty, verified by dry run 2026-10-24: Studio accepts Front+Left+Right or Front+Back+Right and still shows Generate 25), waits until every upload has stayed in its slot (Studio's "Upload failed" empties a slot later while Generate stays enabled) and records `views_omitted` in `studio_submission.json`; the Hyper3D and formy3d backends skip the omitted slot the same way. `convert_job.py` passes the omission to `reduce_model.py --omit-views <view>` (and `segment_first_prep.py`), which leaves that camera out of the texture-visibility weighting (`face_labels.load_cameras(..., omit)`), so surfaces only the omitted camera would have seen count as unseen and are settled by symmetry/prior/neighbours; the manifest records `omit_views`, `module_conversion.<key>.views_omitted` records it in the job record. Use this only after repeated refusals; a four-view module is always preferred.

## Conversion and material contract

The planned queue worker will use one Tripo multi-image conversion for each `race_gender/module`, with the tested H3.0, no-PBR, 2K texture and Triangle settings. Export the original high-poly GLB unchanged. Apply the same local-cleanup + geometry-error reduction at 0.4%, 0.2% and 0.1% of normalized body height and keep all three. Audit boundaries, non-manifold edges, winding, duplicate/degenerate faces, significant components, and geometric/silhouette changes. Flag any failed option for manual review rather than silently selecting it. Do not force an alternative algorithm merely because an asset has more detail; first inspect the finer 0.2%/0.1% outputs. Normal-aware reduction remains an experiment because it introduced odd arm geometry on the reference.

Then label each reduced face from the original texture (`face_labels.py`, 2026-10-21):

- **Palette** (`palette.py`, `palette.json` beside the base views, copied into job snapshots): `white_anchor_v2` = red body + one achromatic anchor #EDEDED (head, left hand, left foot) + garments primary green #19D228, secondary blue #1E41EB, tertiary yellow #F5DC14, accent magenta #E119DC; legacy `tricolor_v1` = red body + yellow/magenta/cyan hue anchors + green, blue. Class 0 is `base` (body and every anchor), classes 1..K the garments in palette order (K = 2 or 4), K+1 unusable. A base, snapshot or swatches file without `palette.json` is legacy `tricolor_v1` and labels exactly as before (verified: re-reduction of the plain plate mail modules is face-for-face identical). Achromatic anchors: a sample is anchor (class 0) when saturation < 0.25 and value > 0.45 (weight fades in from value 0.45-0.6 and out from saturation 0.15-0.25); the red bounce light on the red surfaces next to the white anchors stays saturation >= 0.25 and is still base by hue. The garment materials are named by role (`primary`, `secondary`, `tertiary`, `accent`) in the review/wearable/high-poly blends, then `uncertain` (orange) and, in `highpoly_detected` only, `off_body`.
- **Hue, not chromaticity distance.** Each texture sample takes the nearest swatch hue within 20°. The earlier r:g:b-ratio distance rejected Tripo's body red for being *more* saturated than the swatch (0.131 vs a 0.13 cutoff), which produced the orange patches on bare torsos and most "uncertain" counts. Averaging a face was dropped too: green+blue straddles average to teal and read as cyan.
- **Sample weight** ramps with saturation (0.2→0.45) and brightness (0.08→0.25), so murky pixels count little and grey/black ones nothing.
- **Visibility.** With `--cameras` (the `transforms.json` the concept views were made with) and `--regions`, every high-poly face gets its best unoccluded view angle; texture on unseen surfaces counts 5% (Tripo invented it). Note that the diagonal views do see the spread inner legs at a steep angle, so visibility alone does not fix inner-leg bleed.
- **Module prior** (`--module`): soft base/wear bias from body zones. `body_armor`: forearms, lower legs and head lean base. `right_gauntlet_boot`: right forearm and right lower leg lean wear, right thigh stays possible (tall boots), everything else leans base. `outfit`: head, hands and left foot lean base. Clear visible texture can override it. The zones (forearm = `forearm_stretch.*` + `hand.*`, hand = `hand.*`, head = `head.x`, lower leg = `leg_stretch.*` + `foot.*`, thigh = `thigh_stretch.*`, right = `.r` parts, left foot = `foot.l`) come from the **body parts** below when a `parts.npz` exists, so A-posed orcs and the legless gnome work; without one they fall back to the T-pose landmarks of `regions.json` (`face_labels.landmark_zones`), which are wrong for those bases. The module formulas are the same either way.
- **Body parts.** Every marker base scene (`assets/marker_bases/<race>.blend`, `build_marker_base.py`) carries a FACE attribute `body_part` (names in the mesh property `body_part_names`: `head.x`, `hand.l`, `forearm_stretch.r`, `spine_01.x`, ...). `base_parts.py` writes it with the vertices in the normalized frame to `base_views/<race>/parts.npz` (`blender -b --python tools/tripo_pipeline/base_parts.py -- <marker_scene.blend> <out parts.npz>`; `human_male` uses `assets/marker_bases/human_male.blend`, vertex-identical to the frozen render scene). `reduce_model.py` finds `parts.npz` next to the resolved `regions.json` (job snapshot first, then `base_views/<race>/`; `--parts` overrides, `--no-parts` disables). Transfer: (1) trimmed ICP of the base onto the high-poly mesh with uniform scale + translation only (15 iterations, closest 70% of correspondences in both directions; identity is kept when no iterate improves the residual), because armour bulk shifts the mesh's bounding-box normalization; (2) each face takes the part of the nearest base surface (centroid plus three corner points for low-poly levels), with a flipped normal costing 0.04 of extra distance; (3) cleanup merges isolated faces and small islands into the neighbouring part they share most edges with. Left/right is never mirrored. The prior's zones use a distance-weighted vote of base surface samples within 0.07 (height 2) of each face, so the boundaries stay soft. The fit (scale, translation, trimmed residual before/after, in % of height) and the parts file's hash are recorded in `manifest.json` under `parts`; per level `body_parts` lists the part area shares of the full and wearable meshes. Every reduced level in `review.blend`, `wearable.blend` and the high-poly objects in `highpoly.blend` carry the FACE int attribute `body_part` (+ mesh property `body_part_names`); `review.blend` also has one `<level>_parts` object per level (one colour per part, placed below the level) and `highpoly.blend` a `highpoly_parts` object. GLB files cannot hold face attributes: each level's `_colors.npz` has `body_part` (review mesh face order), `body_part_names`, and the parts in each GLB's face order (`body_part_glb_order` for the full GLB, `wearable_body_part_glb_order` for the wearable GLB; the GLB exporter groups faces by material slot, stable, so `glb_face_order` / `wearable_face_order` give the review-mesh index of GLB face `i`).
- **Off-body faces cannot be base.** Tripo bakes the body's red onto thin armour-edge slivers (the hems of cuisses at the knees), and hue alone calls them base. A face that reaches clearly **outside the fitted base body** is not bare skin: `face_labels.off_body_excess` takes the largest signed distance over a face's corners and centroid to the ICP-fitted base surface and compares it with a per-part threshold = the p99.9 of the same part on the **bare** Tripo mesh of that race (`base_clearance.py`, stored as `base_views/<race>/clearance.json`, copied into job snapshots by `claim`) + 0.02 (1% of height; never below 0.03); the base role then loses score (up to 3, more than clear texture, ramping over a further 0.02) and the face takes primary/secondary from its other texture votes, mirror face or neighbours. The rule only applies where the module prior is at least 0.4, so head, hands, feet, forearms and lower legs of `body_armor` (and everything but the right limbs of `right_gauntlet_boot`) stay base however far Tripo's reconstruction strays from the marker base. It needs a module and a parts file; without a `clearance.json` it is off (`human_male` has none until it gets a bare Tripo base, so neither off-body rule runs for it). Flipped faces get the label source `off_body` (`label_source`, `_colors.npz`, manifest `material.off_body`); `highpoly.blend` marks such high-poly faces magenta (`off_body`). A second, conservative **hem riser** rule (`face_labels.hem_risers`, label source `riser`) handles slivers flush with the skin: a base face that shares an edge with a wear face, lies where the prior is at least 0.4, and whose normal differs from the nearest base normal by more than 60 degrees (it faces along the limb, not out of it) takes the neighbouring wear role, at most 2 rings deep. Limits: a flush sliver that still faces outward is not caught; Tripo reconstructions of the same character differ in pose, which is why the thresholds are per part and not one number.
- **Mirroring one-sided wear (wearable only; this is the `faces` wearable method, see "Wearable by cut" for the default `cut` method, which reflects the finished right piece exactly).** The concepts keep the anatomical-left hand and foot bare as alignment anchors, so the wearable would carry a shoe/gauntlet on the right only. `face_labels.mirror_wear` (called by `reduce_model.py` per level, after labelling) copies the right-side wear faces whose mirror position on the left is bare base onto the left: the parts come from `config.json` `mirror_to_anchor_side` (default `outfit`: foot, `right_gauntlet_boot`: hand + foot, `body_armor`: none; `--mirror foot,hand|off` overrides per run; foot = `foot.r` + `leg_stretch.r`, hand = `hand.r` + `forearm_stretch.r`). Mirror plane = sagittal plane of the base (mean x of its `.l` and `.r` part samples) mapped through the ICP fit (scale + translation, normal stays X); the manifest `mirror` records it with the base symmetry (reflected right samples vs the base surface: all 11 races measure p95 <= 0.4% of height with >= 98% landing on the matching left part; a base that fails the check (share < 0.8, p95 > 2% of height or right not -X) is not mirrored and the reason is recorded). Candidates: wear faces (any garment role) on those parts where the module prior allows wear (>= 0.4), skipped when a wear face lies within 0.05 (2.5% of height) of the mirrored centroid on the labelled mesh (a robe hem on both shins is not duplicated), patches under 3 faces dropped, then grown over 2 rings into neighbouring right-side wear faces that are not worn on the left. Copies are reflected vertices with reversed winding (normals face out), the same material/garment role, the left counterpart `body_part`, label source `mirrored` and the FACE attribute `mirrored` (`wearable.blend`; the npz has `wearable_mirrored_glb_order`, `wearable_label_source_glb_order`, `mirror_source_face`, `mirror_left_part`, `mirror_plane_x`, and `wearable_face_order` = -1 for copies). The full labelled level, review.blend and every label array are unchanged; only the wearable GLB/blend, `wearable_triangles`, and the `wearable_*` arrays grow. Measured 2026-10-22 at 0.4%: Tripo robe 57 faces copied (2.5% of area; 202 shin/hem faces skipped because the left already had them), Hyper3D robe 38 (1.9%), plate-mail `right_gauntlet_boot` 186 (18%; 93% of its wear), `body_armor` none.
- **Resolution.** Weighted votes + prior + mirror face (body armour only) + crease-aware neighbours, iterated; each face records its deciding source (`label_source` face attribute and `_colors.npz`). A level is flagged when more than 20% of its area was decided by prior/neighbours. The prior only says garment-or-base, so a wear face nothing else decides (unseen, no decided neighbours) takes the **garment with the most seen area on that mesh** (`default_garment` in the manifest's `material`; a 1e-6 tie bonus, so texture/symmetry/neighbour evidence always wins); legacy `tricolor_v1` keeps `primary`, as the old tie-break did. `manifest.json` records the `palette` (scheme, hexes, source), `material.palette_scheme/garment_roles/default_garment`, and each `_colors.npz` has `palette_scheme`, `palette_garment_roles`, `palette_garment_hex`. Known and unchanged: `material.uncertain_faces` is always 0 (no face ever gets the uncertain class in this mode), so the `uncertain_share > 10%` review trigger cannot fire; fixing it would alter the review flag of already converted legacy modules, so it was left (`no_texture_evidence_faces` is reported instead, informational).

With the standard `models/<set>/<job-id>/<race>/<module>/source.glb` layout no flags are needed: the module comes from the folder name, the palette from `--palette`, else `swatches.json` beside the source (legacy), else the job's frozen `.base_views/<race>/palette.json` (a snapshot without one is legacy `tricolor_v1` even after the active base was recoloured), else `palette.json` of the folder the regions come from (for a source outside `models/`, the folder of `--regions`, else `base_views/<race>/`), else legacy defaults from `config.json`'s `marker_palette_srgb`; regions (and `parts.npz` beside them) from the job snapshot or `base_views/<race>/regions.json`, and cameras from the job's frozen `.base_views/<race>/transforms.json` (`workflow.py claim` freezes it). For jobs claimed before that, the cameras come from whichever active/archived base set has the same three-quarter view hashes as the job's frozen images. The manifest records each choice under `input_sources`. The repaired source mesh is put into a canonical order before reduction, so runs are reproducible. `base_regions.py` measures `regions.json` for a marker base (`base_views/human_male/regions.json` from `assets/studio_plain_input.blend`). Use semantic roles `base` and the palette's garment roles only where the source colors make that assignment reliable; keep `uncertain` visible for review. Red body and every anchor (white head/left hand/left foot; legacy yellow/magenta/cyan) classify as `base` for removal; yellow `tertiary` and magenta `accent` garment faces are kept in the wearable. Preserve the original texture, per-face evidence, source GLB, each low-poly option and materials in `models/`. The reducer reuses area-weighted texture sampling from `../lowpoly/polygon_materials05.py` and reads the palette described above (`polygon_materials05.py`'s own 6-colour PALETTE is stale and not used here).

**Interior (enclosed) surface.** Some Tripo exports contain a second, inward-facing copy of the body welded to the outer skin (the first elf_female `right_gauntlet_boot` attempt: 42% of its area enclosed, 31 components, two layers in wireframe, 2,460 triangles at 0.4% vs ~740 for a clean module). `reduce_model.py` audits every source: it casts 14 rays over the outward hemisphere of each of 5,000 area-weighted faces (first ray along the normal, none flatter than 20°) and counts a face as enclosed when none escapes the mesh, which concavities (inner thighs, armpits) do not trigger. The manifest `interior` block holds `interior_area_share` (all rays blocked), `interior_area_share_loose` (at most one escapes), `normal_blocked_share` (the simple normal-ray test) and the median gap. Calibration over 30 sources (2026-10-22): bare bases 0.000-0.005, plate-mail modules 0.0002-0.044, the double-shell source 0.415, so `INTERIOR_THRESHOLD` is 0.15. `--interior auto` (default) strips the enclosed faces from the welded working mesh before reduction when the share is above the threshold (the source GLB is never changed; the removed faces are kept in `interior_removed.npz`, the texture lookup ignores them too) and marks every level for review with the reason in `source_review_reasons`; `--interior strip` always strips, `--interior flag` only measures and flags. Stripping a fold leaves open edges where the outer layer continued into the inner one, so check boundary edges after a strip.

The reusable three-level Blender processor is now `reduce_model.py`. It was run on the selected studio plain paper GLB and reproduced the 436 / 626 / 1,352 triangle results with mesh checks passing. It preserves an exact imported backup, exports three native-coordinate full-model GLBs with flat face materials, stores sampled face-color evidence, and saves an editable `review.blend`. With recorded swatches, it also removes all `base` marker faces **after** classification and exports a `__wearable.glb` at each level; these intentionally open garment surfaces need fitting review. Its no-swatch fallback uses neutral `COLOR_00/01/02` labels and cannot safely remove the body. For production the palette comes from the base (`--palette <palette.json|base dir>` overrides it). The legacy `swatches` form still works, e.g. `{"base":"#E61923","base_markers":{"head":"#F5DC14","left_hand":"#E119DC","left_foot":"#14DCEB"},"primary":"#19D228","secondary":"#1E41EB"}`, as a second positional argument or beside the source; it means legacy `tricolor_v1`. The original three-color swatch form still works for older inputs. Example:

```bash
/usr/local/bin/blender -b -t 6 --python tools/tripo_pipeline/reduce_model.py -- \
  models/<set>/<job-id>/<race_gender>/<module>/source.glb \
  models/<set>/<job-id>/<race_gender>/<module>/reduced \
  [swatches.json] [--cameras transforms.json --regions regions.json --module <module> --parts parts.npz --palette palette.json --interior auto|strip|flag]
```

Each run also writes `reduced/wearable.blend` (the three `__wearable` levels side by side, base and anchors removed, one-sided wear mirrored onto the bare left side (see Mirroring), with the garment-role (primary, secondary, tertiary, accent)/uncertain face materials). `make_wearable_blend.py -- <reduced_dir>` rebuilds it from existing wearable GLBs. With swatches and `--highpoly-blend` (off by default since 2026-10-26: about 150 MB per module; the existing ones were deleted to free disk, `make_highpoly_blend.py -- <source.glb> <palette.json> ...` rebuilds one on demand) it also writes `highpoly.blend` beside the source GLB: the full Tripo mesh twice, `highpoly_detected` (each triangle's material detected from the texture at its UV centre, orange = uncertain) and `highpoly_textured` (original texture, packed); `make_highpoly_blend.py -- <source.glb> <swatches.json>` backfills it and never overwrites. The output directory must be empty to protect earlier attempts. The processor currently expects one textured mesh with direct base-color UV texture; it stops with a clear error for an unfamiliar Tripo export. It records material review status when swatches are absent, more than 10% of faces are uncertain, texture projection is too far from the original surface, or no confidently labeled primary/secondary faces remain. A bare-base sample with the four-marker palette correctly produced no confident wearable faces and was flagged for review. Color-role thresholds, body removal and fit on genuinely new outfit textures still need visual validation before automatic completion. Automatic queue invocation of the browser script and processor is the remaining integration step.

`rereduce_job.sh <models/<set>/<job-id>> <tag>` re-runs the reduction of every module of a converted job after the labelling changed: it moves `reduced/` to `reduced_<tag>/` and `highpoly.blend` to `highpoly_<tag>.blend` (nothing is deleted or overwritten) and runs `reduce_model.py` again with the standard inputs (`JOBS`, `THREADS` set the parallelism).

Once conversion and all derived outputs succeed for every module, move the four-view image set and its prompt/job metadata to `completed/`. Keep failed/retryable jobs and partial model attempts distinct; do not overwrite older exports. No automatic queue watcher is currently enabled, so `multiview_ready/` is a safe holding state until it is implemented and verified.

## Finishing sets (`finish_sets.py`, 2026-10-26)

`python3 tools/tripo_pipeline/finish_sets.py [--root DIR] [--set SET ...] [--apply] [--json]` decides when a set leaves the pipeline (user rule: converted for every race, gnomes included since 2026-11-14) and moves it from `processing/` to `completed/`. Dry run by default; it prints `[complete]` / `[incomplete]` per set with the missing `module: races`, the in-progress jobs and what would move.

- Required races: folders of `base_views/` with a `palette.json`, gnomes included. Jobs are grouped by set id; a trailing `_<race>` (`plain_plate_mail_01_gnome`) is stripped. `failed/` and `archive/` are never read.
- A (race, module) is done when a job of the set in `processing/` or `completed/` has a `state` starting with `converted` and `models/<model set>/<job id>/<race>/<module>/reduced/` holds `manifest.json`, `lod_error_0p4|0p2|0p1.glb` and `lod_error_0p4__wearable.glb` (all 58 converted jobs on 2026-10-26 have them, outfits, armour, segment-first plate and two-view gnome alike). The modules of a set are the union over its jobs.
- A set is complete when every module is done for every required race and no job of the set is in `processing_views/`, `multiview_ready/` or unconverted in `processing/`.
- `--apply` moves each converted `processing/` job of a complete set whose own modules all have artifacts to `completed/<same name>` (refused if it exists) and adds `"completed": {time, by, reason}` to `.tripo-job.json` through `convert_job.update_record`. A converted job missing artifacts stays and is reported. The pass runs under `.codex_jobs/_batch/finish_sets.lock` (flock), so concurrent workers cannot move the same folder; a folder already gone is reported as an error line, not a crash.
- `tools/convert_queue.py` calls it after each converted job (for that job's set) and once before an idle exit; failures there are only logged (`FINISH` events).
- Tests: `python3 -m pytest tools/tripo_pipeline/test_finish_sets.py -q`.

## Pipeline supervisor (`tools/pipeline_supervisor.py`, 2026-10-26)

A single-instance daemon (flock `.codex_jobs/_batch/supervisor.lock`) that watches the two runners (`view_batch.py run`, `convert_queue.py` workers). `python3 tools/pipeline_supervisor.py run` (loop), `status`, `mode auto|pause|pause-conversions|run`, and `run --dry-run` (one pass: prints what the screen gate and gates 1/2 would do, changes nothing). Every action is one `SUPERVISOR ...` line in `.codex_jobs/_batch/events.log`; errors are logged and never stop it.

- **User gate (every 30 s).** The user is *away* when the screen is locked or blanked (`gdbus ... org.gnome.ScreenSaver.GetActive` = `(true,)`), or when there has been no keyboard/mouse input for 5 minutes (`AWAY_AFTER`; `org.gnome.Mutter.IdleMonitor.GetIdletime`). Away = run; at the computer = pause (reason `user active`). A playing video counts as away, because it is not input. This rule changed on 2026-10-27: under the screen-only rule a video player kept the screen from locking, so conversions stayed paused all night. If both calls fail, the previous state is kept (logged once). `mode` stores a manual override in `supervisor_mode.json` (`pause` / `run` regardless of the screen; `auto` = follow the screen).
- **Pausing is "finish, then freeze".** It writes `.codex_jobs/_batch/PAUSE` (json: since, reason, scope). While it exists `convert_queue.py` starts nothing new, and `view_batch.py run` too when the scope lists `views` (`PAUSED ...` once per episode; running Codex jobs finish and are collected). A screen-on pause has scope `["conversions"]` (user, 2026-10-26: image generation runs remotely; measured with 4 parallel image jobs: ~0.3 of one core on average, 2-core bursts of a few seconds while `check_framing.py` runs at ~3.4 CPU-s per image, ~3 GB RAM for the Codex sessions), so views keep generating while the user works; a manual `mode pause` writes `["conversions", "views"]` and `mode pause-conversions` (2026-10-27) `["conversions"]`, and a PAUSE file without a scope pauses both and `convert_job.py` does not start a new submission (a module with a `studio_submission.json` keeps collecting). Each tick the supervisor SIGSTOPs every descendant of a running `convert_job.py` that is `blender` or a python running a script under `tools/tripo_pipeline/` (not `convert_job.py` itself); it never freezes `tools/hyper3d_pipeline/`, node (`studio.mjs`), firefox, geckodriver, Xvfb, codex or the runners. Frozen pids with their start times (so a reused pid is never continued) are in `paused_pids.json`. On resume (screen blanks/locks), on exit and on SIGTERM it removes `PAUSE` and SIGCONTs them (plus any stopped heavy descendant). If the supervisor was killed hard: delete `PAUSE` and `kill -CONT` the pids in `paused_pids.json`, or just start it again with the screen blanked. The runners read `PAUSE` only in new code: a runner started before 2026-10-26 needs a restart to honour it (`convert_job.py` is a fresh process per job, so it picks the wait up by itself).
- **Automatic review gates (every 3 min), only for sets opted in by `.codex_jobs/_batch/advance.json`** (`{"sets": [{"pattern": "ragged_outfit_*", "extra_file": ".codex_jobs/_batch/briefs/ragged_views_rules.txt", "views_priority": 2}]}`; patterns are fnmatch on the set id; unlisted sets are never advanced). Anything flagged is reported once as `SUPERVISOR HOLD <set or job>: <reasons>` and waits for a human (`supervisor_state.json` remembers reported holds; a hold is re-reported when the files or reasons change). A colour drift that a human has reviewed and accepted goes into advance.json `accepted_drift` (`pipeline_supervisor.py accept-drift --note ... IMAGE...`) (`[{"sha256": ..., "image": ..., "note": ..., "date": ...}]`). It is matched by the image's sha256, so it follows the front into `processing_views/`. A regenerated image is checked again, and adding an entry re-opens the hold.
  - Gate 1 (other-race fronts): when every `fronts--<set>--<race>` task is `done` (any `failed` = hold) and every front has empty framing flags in the task status (a `POSE: body_red shifted` note is allowed for `right_gauntlet_boot`), no `check_concept_colours.py --palette base_views/<race>` DRIFT, base size and RGBA, a non-empty parsable `<module>_prompts.json` and a `<module>_design_record.md` with a `Design:` line, it moves `concepts/<set>/<race>` into `approved/<set>/` (skipped with a hold if that exists), runs `workflow.py claim <set>` and `view_batch.py add-views <job> --extra-file <extra> --priority <p>`, and logs `AUTO-CLAIM <set> -> <job>`. A failed add-views is retried every pass; a failed claim is logged (`FAILED claim`) and left for a human. Races already in a claimed job of the set (`processing_views/` .. `completed/`) are ignored, and gnome fronts are gated and claimed separately (state key `<set>#gnome`; add-views gets the entry's `gnome_extra_file` instead of `extra_file`, since the series rules carry hem/left-foot lines that do not fit the footless gnome), so a gnome front added to a set whose other races moved on long ago neither waits for nor blocks them (2026-10-26).
  - Gate 2 (finished views): for each `processing_views/` job of an opted-in set in state `generating_other_views` whose `views--*` tasks (outputs under the job) are all `done`, every module has its four views (or a valid `views_omitted.json`) and nothing else, each PNG is the frozen base size and RGBA, the task framing flags are clean (same allowance) and there is no colour DRIFT, it runs `workflow.py ready <job>` and logs `AUTO-READY <job>`.
- Tests: `python3 -m pytest tools/test_pipeline_supervisor.py -q` (temp roots, gdbus and subprocesses mocked, fake process table, view_batch PAUSE check).

## Splitting body armour into rigid pieces (pauldrons)

`split_pieces.py` cuts a reduced `body_armor` **wearable** into three independent meshes by face colour label: `pauldron_l` (anatomical left, +X), `pauldron_r` (-X) and `rest`. Plain python3 (numpy + Pillow); the `.blend` step starts Blender itself (or runs in-process under `blender -b --python`). Faces are only split, never closed, remeshed or moved; the pieces share no vertices.

```bash
python3 tools/tripo_pipeline/split_pieces.py models/<set>/<job>/<race>/body_armor/reduced [--style roles|rim] [--levels 0p4,0p2] \
  [--output-dir DIR] [--roles accent,tertiary] [--region-parts shoulder,arm_stretch] [--seed-in-region] [--min-island 6] \
  [--close-rings 1] [--max-field-share 0.2] [--plane-x X] [--no-blend] [--no-render]
python3 -m unittest tools/tripo_pipeline/test_split_pieces.py   # synthetic armour + the plate-mail orc_male, ~3 s
```

Defaults come from `config.json` `piece_split[<module>]` (module from the manifest / folder name). Output goes to `<reduced>/../pieces/` (refuses to overwrite; use `--output-dir` for experiments): per level `lod_<lv>/{pauldron_l,pauldron_r,rest}.glb` (materials/roles kept), `pieces_<lv>.blend` (three named objects, object colour per piece), `pieces_render.png` (front, back, exploded: pauldrons offset 15% of height outward, flat colours L orange / R blue / rest grey), `faces.npz` (per wearable face: piece, side, role, body part, flag bits), plus one `pieces.json` (per piece: faces, area, area share, connected components, bbox, centroid; `symmetry`: plane, L/R area ratio, centroid mirror error in % of height, share of each side's faces that have a mirror twin within 2.5% of height; `absorbed_islands`, `stray_seed_components`, `rim_fields` (every candidate with its accept/reject reason), `ambiguous_faces` (side conflict, centreline, weak label source prior/neighbours, changed by clean-up), `warnings`).

- **roles style** (`S6`, 2+2): pauldron = faces whose garment role is in `roles` (`tertiary`, `accent`); the rest of the armour only has primary/secondary.
- **rim style** (`S4`, `S2`): pauldron = the `accent` rim plus the wear faces it encloses, i.e. connected components (shared edges, welded vertices) of the non-accent wear faces that are not connected to the main body (largest component). A rim with a gap leaks, so a second pass erodes the non-accent faces `close_rings` rings away from the rim, finds the cores that separate from the main body, and floods the eroded faces back to the nearest core. A candidate field must have at least `min_region_share` of its area on the shoulder/upper-arm parts, at most `max_field_share` of the wear area, and `min_enclosure` of its perimeter against rim faces; rejected candidates are listed with the reason. A side with no field faces gets a warning (closed ring missing).
- **both**: a seed component mostly outside `region_parts` (`shoulder`, `arm_stretch`, names without `.l/.r`) stays in `rest` (a stray speck is not a pauldron). Sides come from the body part suffix, `.x`/unknown from the sagittal plane (manifest mirror plane, else the base `parts.npz` x mapped through the manifest ICP fit, else the mid of the wearable's `.l`/`.r` faces; all candidates are recorded). Islands under `min_island_faces` go to the neighbouring piece with most shared edges (a 2-face hole inside a pauldron joins it, a speck in the region joins rest), a detached second patch of a pauldron under `extra_component_share` of its main patch goes to rest; each is listed in `absorbed_islands`. More than one remaining patch per pauldron is a warning.
- Body parts of the wearable faces come from the full GLB (`body_part_glb_order`, matched by face **centroid**, since some wearable GLBs have a different face count than the npz `wearable_*` arrays; `body_parts.wearable_array_agreement` reports how often the two agree). Garment roles come from the wearable GLB material names. Without an npz or parts the region test is skipped (warning) and sides use the plane only. GLB frame: X lateral (right = -X), Y up, front +Z.
- Legacy two-colour plate mail has no pauldron colours; as a test use `--roles secondary --seed-in-region` (secondary faces on the shoulder/upper-arm parts). The `human_male` plate-mail reduction predates body parts (no `body_part` in its npz); use e.g. `orc_male`. Dev outputs: `experiments/pauldron_pipeline_20261022/split_dev/`.

### Rigid sections for plate mail (torso / arms / pauldrons), overlap and pose test

`split_pieces.py --rigid zones|snap` additionally cuts everything that is not a pauldron into `torso` (chest, back, upper legs: one piece), `arm_l` and `arm_r` (upper-arm plates down to the elbow edge; `config.json` `piece_split.body_armor.rigid`). Default behaviour (no `--rigid`) is unchanged. Extra output per level: `pose_render.png` (with `--pose-test`) and `rigid` in `pieces.json` (cuts, snap stats, overlap strips, pose metrics); `faces.npz` gets `<piece>__overlap` (per face in GLB order) and the `.blend` objects the FACE int attribute `overlap`.

```bash
python3 tools/tripo_pipeline/split_pieces.py <reduced> --style rim --rigid snap --overlap --pose-test --output-dir <new dir>
python3 tools/tripo_pipeline/compare_rigid.py out.jpg S6=<reduced>:roles S4=<reduced>:rim   # M1 vs M2 + posed sheet (<= 2400 px wide)
```

- **M1 `zones`**: pauldrons first (roles/rim logic), then every other face on the `arm_stretch`/`forearm_stretch`/`hand` body parts (`rigid.arm_parts`, side from the `.l/.r` suffix) is the arm of that side, the rest is torso. Without body parts the arm is everything lateral of the shoulder joint. Islands under `min_island_faces` and detached patches (arm patches under `extra_component_share` of the main patch go to torso, every detached torso patch joins its neighbour) are cleaned up, so each piece is one patch where the mesh allows it (otherwise a warning).
- **M2 `snap`**: M1 is the first guess, then per side the torso/arm boundary is re-cut inside a band of +-`snap.band` (8% of height) around the guess by a minimum cut (own Dinic max-flow, no scipy). Terminals = torso and arm faces outside the band; edge cost = edge length x 0.15 on a colour/label boundary x 1/(1+(dihedral/30 deg)^2) on creases (floor 0.03); a weak pull (`snap.prior`) holds free faces to their zone label, growing with distance from the guess. It keeps open-mesh boundaries (armpit holes) as free cut ends and is skipped for a side with nothing to cut. Cut length, share on colour edges, share on creases and the snap cost are in `rigid.cuts` (M1 values in `cuts_zone_guess`).
- **M3 `seam`** (`--rigid seam [--soft piece|nearest]`): the soft under-layer (`rigid.seam.soft_roles`, secondary/blue) separates rigid plates. Rigid plates = connected components of the other wear faces; each goes wholly to the arm or torso by area-weighted body-part majority (a plate with more than `mixed_share` on the minority side is split by body-part zone). Only blue components with at least `soft_min_arm_share` (25%) of their area on the arm parts count as the shoulder/arm band; other blue (hip cloth) stays rigid (a band joined to other blue regions loses that share, so the concept must keep the band blue-only). `--soft piece` = separate piece `soft` (label 5, to be skinned smoothly; the pose test blends it by inverse-squared distance to the rigid pieces and reports `soft_stretch_max`), `--soft nearest` = each blue face joins the nearest rigid piece by rings (the cut then runs through the middle of the band, no colour edge). Cuts to the soft piece never get strips.
- **M4 `colour`** (`--rigid colour`): the arm plates carry their own garment role (`rigid.colour.roles`, default `quinary` = cyan #14DCEB, palette `experiments/rigid_sections_20261022/palette_cyan5.json`, reduce with `--palette`): arm = those faces plus the wear faces they enclose (same erosion/flood rim logic as the pauldron, `colour.close_rings/max_field_share/min_enclosure`), restricted to the arm body parts (a stray cyan speck stays torso, listed in `rigid.colour.stray_components`). Errors out when the wearable has no such role.
- **Overlap** (`--overlap`, `rigid.overlap`; **off by default since 2026-10-22**: the yellow strips made the visual review hard to read, `rigid.overlap.enabled` is `false`, `--no-overlap` is kept as a no-op; `--pose-test` then only measures the no-strip variants and `pose_render.png` has no strip columns): at every cut between two pieces that move relative to each other one strip is added: the cut loop is stepped `length` (6% of height by default, was 3%) along the other piece's surface, projected back onto it, sunk `offset` (0.4%) below it along its outward normals, one quad per cut edge (2 triangles), attached to the owner's own cut vertices with the material of the adjacent owner face, face attribute `overlap`. **Owner modes (`--overlap-mode`; default `both` since 2026-10-22, config `rigid.overlap.mode`)**: `parent` (the cheaper option, about half the strip faces): the piece that moves less owns the strip and tucks it under the piece that moves more (the strip stays where the mover was and fills the opening); `child`: the mover owns it and tucks it under the static piece; `both`: both pieces own one (a gap sample counts as closed when either bridges it; doubles the strip faces); `cover` (inner piece by `cover_order` tucks under the outer one) is kept for comparison: a strip that rotates with the moving piece cannot fill a hinge opening unless it is longer than the cut's distance from the pivot, and measured worse. **Pauldron convention (`--pauldron-convention`, `pose.convention`)**: `half` (default since 2026-10-22: a clavicle/shoulder parent that turns half the arm angle about the same pivot), `arm` (pauldron follows the arm), `torso`; the old cheaper combination is `--pauldron-convention arm --overlap-mode parent --overlap-length 0.03`. Strip owners follow the motion hierarchy `piece_depth`/`piece_body` (pelvis < chest, thigh < arm, pauldron by convention).
- **Pose test** (`--pose-test`): rigid rotation about the shoulder joint (centre of the arm_stretch ring shared with the torso part, from `parts.npz` mapped through the manifest ICP fit into the GLB frame; `--joint-l/--joint-r x,y,z` override) around the frontal axis, arms down 45 deg and up 30 deg, pauldrons following the arm or the torso, with and without strips. Metrics per cut (`rigid.pose.variants`): `separation` = plain motion of the cut, `gap` = distance of the boundary points of the piece the strip tucks under (cut vertices and edge midpoints, in their own pose) to the strip owner's posed surface including its strip; `gap_max`/`gap_mean` in % of height. `pose_render.png`: rows = pauldron follows arm / torso, columns = down/up x without/with strips (yellow).
- **Measured, M1 vs M2** (0p4; outputs `experiments/pauldron_pipeline_20261022/*/pieces_rigid_m1|m2/`, sheet `experiments/rigid_sections_20261022/compare_m1_m2.jpg`, numbers `compare_m1_m2.jpg.json`): M2 lowers the torso|arm snap cost 5-8x on S6/S2 (S6 cut on colour edges 61/41% -> 82/100%, cut 22.6/25.5 -> 19.8/21.1% of height) and equals M1 on S4, where the part boundary already lies on a colour edge. Strips (parent, 3%) cut the mean gap for arms up 30 deg by 28-61% and for arms down 45 deg by 1-35%; the max gap (4.6-7.2% of height down, 2.5-3.3% up) is the pauldron|torso opening.
- **Measured, M3/M4** (outputs `experiments/rigid_sections_20261022/<concept>/pieces_rigid_<method>/`, sheets `compare_m3_m4.jpg` and `compare_m3_m4_pose.jpg`): see the report in the task log; the numbers are in `compare_m3_m4.jpg.json`.

### Separable mode: cyan joint bands, all joints (chest / pelvis / thighs / arms)

Palette: every `base_views/<race>/palette.json` carries an optional block `"separable_garments": [{"role": "joint", "hex": "#14DCEB"}]` (fallback `config.json` `separable_garments` for old job snapshots). It is ignored unless a reduction is run with `reduce_model.py --separable` (`Palette(..., separable=True)` appends the garments after the normal ones, scheme gets the suffix `_joint`) or `convert_job.py --separable`; `convert_job.py` also switches it on for a job whose `.tripo-job.json` / `prompts.json` / `<module>_prompts.json` (beside the views or in `.concept_notes/`) has `joint_bands: true`, `separable: "joint_bands"` or the words "joint band". Without the switch nothing changes (regression 2026-10-22: re-reduction of the orc_male plate-mail `body_armor` gives identical `material_id` at 0p4/0p2/0p1, and `--separable` on that cyan-free source changes no label). A hand-made palette that already lists the role (`experiments/joint_bands_20261022/palette_joint.json` `joint`, `experiments/rigid_sections_20261022/palette_cyan5.json` `quinary`) is left as it is; `quinary` is the old name of the cyan role (the M4 data: cyan rerebrace plates, cut with `--rigid colour`), `joint` means joint bands.

Adaptive hue fit (2026-10-22): `Palette.fit_hues(colors)` fits each palette colour's hue centre to the model's own texture. A weighted (saturation x brightness) hue histogram of the 0.4% level's 80k samples is smoothed; peaks above 0.3% of the weight are matched to colours greedily by increasing hue distance (at most 30 degrees, one peak per colour, so a hot-pink peak at 329 degrees that is as near the body red as the magenta accent goes to the accent because the body has its own peak at ~357); since 2026-11-21 a colour then gives up its peak for an unclaimed one in its window that is at least 10 times bigger (`HUE_FIT_SWAP_RATIO`) and that no colour's centre would classify (closest-first had handed a monster's green a 0.4 % sliver at 138 degrees and stranded the real green, a third of the texture, at 102: the manifest records `gave_up_peak` on that colour); shifts under 8 degrees are ignored (a calibrated model is classified by the nominal palette); a peak that a colour without a peak of its own sits within 6 degrees of is flagged `ambiguous` and left nominal. The shifted centres (`Palette.with_hue_shifts`) label all three levels, are written to `manifest.json` `hue_fit` (per colour: nominal, peak, share, shift, note; plus `review`) and `palette.hue_shift`, and are used by the high-poly blend. `reduce_model.py --adaptive-hue auto|on|off`: `auto` (default) is on only for separable palettes (`--separable` or a palette listing a `joint`/`quinary` role), so ordinary reductions are bit-identical to before. Regression (2026-10-22, `experiments/joint_bands_20261022/regress/adapt*`, `--adaptive-hue on` against the old reductions, `material_id` per face at 0p4/0p2/0p1): orc_male plate mail, human_male plate mail, S2, S4, S6, M4_15, M4_46: 0 changes (all fit nominal); Tripo robe (secondary +12.2 degrees): 12/27/42 faces of 1196/2024/3870 changed (accent/tertiary to secondary on violet-blue samples); Hyper3D robe (accent +13.5): 1/4/18 of 1842/3484/7702. J_09 (accent +27.5 degrees): 133 accent faces at 0p4 instead of 1, the pauldrons are found (85/120 faces instead of 0/0). Concept side: `tools/check_concept_colours.py <image> [--palette dir] [--separable] [--max-drift 12]` measures each palette colour's hue in a concept image and reports drift beyond 12 degrees (J_09 front: accent +19 degrees, DRIFT); it is a tool only, nothing calls it.

Band continuity: `compare_rigid.py --continuity <out.json> <name>=<reduced> ...` (`split_pieces.band_continuity`) reports per joint and LOD the fraction of the joint ring covered by joint-role faces (azimuth arcs around the joint axis), the largest gap, the number of edge-connected pieces and the band width. Coverage is a property of the source texture, not of the LOD: 0p4/0p2/0p1 give the same coverage within a few percent (J_09 waist 100%, arms 96-97%, hips 69-81%; J_21 arms 90-99%, waist and hips 100%; J_47 waist 100%, hips 78%, arms 52%); what changes with the LOD is whether the band touches both neighbouring plates (contact edges) and whether a plate spans the joint, so finer levels do not keep bands better.

`split_pieces.py --rigid bands [--soft piece|nearest]`:
- Pieces: `chest` (id 0, everything not below), `pauldron_l/r`, `arm_l/r`, `pelvis` (`root` part), `thigh_l/r` (`thigh_stretch`, `leg_stretch`, `foot`; `rigid.part_groups`), plus, with `--soft piece`, one skinned `soft_<joint>` piece per banded joint (`soft_arm_l/r`, `soft_waist`, `soft_hip_l/r`). Pauldrons are cut first by the `--style` logic.
- Band = joint-role faces (components under `bands.min_band_faces` are dropped); rigid plates = connected non-band wear faces, each wholly assigned to its body-part zone majority. A band component belongs to the joint whose two pieces it touches with at least `bands.min_contact` edges each. **A joint is `band` only if such a component exists and no plate with at least `mixed_min_faces` faces and more than `mixed_share` (3%) of its area in another zone spans it**; otherwise it **falls back**: the plate is split by zone and the cut is re-cut by the M2 snap min-cut (`snap_cut`, now general for any pair: waist = chest|pelvis, hip = pelvis|thigh). Joints with no faces on one side (no legs in the armour) are `absent`. `rigid.bands.joints` / `fell_back` / `absent` in `pieces.json` report this per joint.
- `--soft nearest`: band faces join the nearest rigid piece (rings), the cut runs through the middle of the band and gets overlap strips; `--soft piece` leaves the band skinned (no strips at its cuts, `soft_stretch_max` reported).
- `--rigid auto` (the default for a reduction whose manifest palette has a `joint`/`quinary` garment and no explicit `--rigid`; `--rigid none` switches it off): `bands` when there are at least `bands.auto_min_faces` `joint` faces, `colour` (M4) when there are only `quinary` faces, else `snap` on all joints (`--joints all`; zones/snap default to arms only). `pieces.json` records `auto` and `default_rigid_reason`; overlap strips are NOT added by this default any more (`--overlap` adds them).
- Pose test scenarios (`--pose-test`, each with and without strips): arms down 45 / up 30 about the shoulder joint, `thigh_flex` 45 (forward) and `thigh_abd` 20 (outward) about each hip joint (thighs rotate, pelvis fixed), `spine` 20 (chest, arms and pauldrons pitch forward about the waist joint relative to the pelvis). Hip and waist joints come from `parts.npz` (thigh ring shared with the pelvis; ring between `root` and `spine`), overridable through the spec keys `joint_l`, `joint_r` (shoulders, CLI `--joint-l/--joint-r`), `joint_hip_l`, `joint_hip_r`, `joint_waist`. Gap = opening of rigid-rigid cuts that move relative to each other; banded joints show `soft_stretch_max` instead (the largest edge stretch of the soft piece blended by inverse-distance-squared weights).
- First real joint-band data (2026-10-22, `experiments/joint_bands_20261022/`): at 0p4 the cyan bands survive only as small partial rings (J_09 94 joint faces, J_21 106), so most joints fall back to snap (J_09: waist and right hip banded; J_21: none), which still follows the band edges because they are colour edges; both concepts lost the magenta pauldrons in the labelling (hot-pink hue ~322 deg is outside the 20 deg tolerance of #E119DC at 304 deg: accent 1 / 0 faces). `attach_parts` now aligns an exported GLB that lost a few invalid faces with the npz by face area (`body_parts.aligned_by_area`).

## Rigid sections with per-piece base colours (`split_pieces.py --rigid regions`, 2026-10-22)

The replacement for joint bands (thin cyan bands did not survive Tripo as closed rings, see the bands section above): each rigid
section has ONE large main colour, neighbouring sections differ, so every joint is a boundary between two large colour regions
(`PROMPTING_GUIDE.md` has the concept rules). Standard 4-colour palette; the separable `joint` role is not used (the code stays).
Expected main colours are `config.json` `piece_split.body_armor.rigid.regions.expected`: chest `primary`, arm `secondary`,
pauldron `accent`, pelvis `secondary`, thigh `primary` (CLI `--expect arm:quinary,chest:primary` overrides it, e.g. to sanity-check
data with other colours).

Steps (`sections_regions`; thresholds in `rigid.regions`):

1. **Pauldrons first**, with the rim style (expected pauldron colour = accent seeds + the wear faces they enclose = field and
   decoration), unless `--style` was given. The rest is the candidate set.
2. **Regions**: connected same-role components of the candidates whose role is an expected section colour and whose area is at
   least `min_region_share` (2.5%) of the candidate area. Each is assigned to the section holding most of it by body part (the zone
   guess of M1: arm parts, thigh parts, `root`, else chest; sides from the part suffix) or, when that section expects another colour,
   to a section with at least `role_resolve_share` (25%) of the region whose expected colour is the region's (`whole (role decides)`).
   A second section that holds at least `min_span_share` (4%) of the region with its 90th-percentile face farther than `span_depth`
   (5% of height) from the main zone means the region spans joints (e.g. chest and thigh green joined because the pelvis colour is
   missing): it is split by the zone guess and each such cut is re-cut by `snap`. Spill within `span_depth` of the zone boundary is
   treated as zone-guess error and the region stays whole.
3. **Everything else**, as same-colour components, largest first: enclosed by one section (at least `min_enclosure` = 60% of its
   perimeter on it, counting already-assigned faces) = decoration, absorbed into it; a same-role component of at least
   `min_minor_share` (0.4%) that is not enclosed (a detached tasset) is assigned like a region; anything else goes face by face to the
   nearest assigned section by shared-edge rings. Decoration that ends up on two sections is listed in
   `decoration_touching_two_sections` with its centroid. Components with no assigned neighbour keep the zone guess.
4. **Joints** (arm_l/arm_r = chest|arm, waist = chest|pelvis, hip_l/hip_r = pelvis|thigh): `region` when at least
   `min_boundary_share` (60%) of the cut length lies on a colour boundary; `fallback` (cut re-made by `snap_cut` around the zone guess)
   when it does not, when the two sections do not touch, or when both lie in one spanning region; `absent` when a piece has no faces.
   Reported in `pieces.json` `levels.<lv>.rigid.regions` (regions with zone shares and how they were assigned, other components,
   joints with colour-boundary share, `fell_back`, `absent`) and warned when a region's colour is not the expected one for its section.

`--rigid auto` (the default for a reduction whose manifest has a joint role in its palette or `hue_fit.active`, i.e. separable /
piece-colour jobs) decides per level, in this order: `bands` when at least `bands.auto_min_faces` (10) joint-role faces exist;
`colour` when at least that many `quinary` faces exist; `regions` when the non-pauldron faces hold at least `auto_min_regions` (3)
large same-colour regions of expected section roles that together cover at least `auto_min_share` (50%) of their area; otherwise
`snap` on all joints. The numbers are in `rigid.auto` (`large_regions`, `region_area_share`, `region_roles_present`, `chosen`).
`convert_job.py` runs jobs that say `piece_colours` / `rigid_sections` (or the words "per-piece base colours" in their records, or
`--piece-colours`) with `reduce_model.py --adaptive-hue on` (the hue fit, see above), without `--separable`.

**Clean piece shapes (all rigid methods, after the joints are cut).** (1) Detached patches and islands: besides the shared-edge vote, a patch that hangs on by
corners only (no shared-edge neighbour of another section) goes to the section sharing most vertices, pauldrons included (`vertex_votes`; P_11's chest patches
enclosed by a pauldron, P_40 0p4's arm island on the shoulder top; `absorbed_islands` says "attached by vertices only"). (2) **Flap / spike pruning**
(`prune_flaps`, `rigid.flaps`, `--keep-flaps` to skip): a triangle that hangs off the wearable by ONE edge (or none) and whose free tip stands more than
`min_height` = 6% of the height off that edge is dropped from the exported pieces (chains peeled leaf by leaf, `max_passes` 4; a leaf face opens no hole; the
piece labels are unchanged, `Sections.dropped` / `faces.npz` piece = -1; reported in `rigid.flaps` and as a warning). Cause of the user's "spiky triangle on arm_l"
(P_29, face 630 / 908 / 1638 at 0p4 / 0p2 / 0p1): the reduction leaves a single blue cuff triangle (body part `forearm_stretch.l`, 10-12.5% of the height off
its edge, 3 x 10^-3 H^2) stretched out over the bare forearm; its only neighbour is in arm_l, so there is no other section to give it to. The next largest
single-edge leaf in the three models is 4.5% (P_11 neck), so 6% separates the flaps cleanly; P_29 0p1 arm_r has one too (9.1%), P_11 / P_40 none.

Outputs, overlap (off by default; with `--overlap` mode `both`, 6%; convention `half`) and the pose scenarios (arms, thigh flex, thigh abduction, spine) are
the same as for the other rigid methods (`pieces/lod_<lv>/*.glb`, `faces.npz`, renders, `pieces.json`). Comparison sheets:
`compare_rigid.py --regions <out.jpg> <name>=<reduced>[@<concept front.png>] ...` writes `<out>.jpg` (concept, reduced colours,
regions front/back/exploded, snap front/exploded), `<out>_pose.jpg` and `<out>.jpg.json`; each sheet is scaled to at most 2400 px both ways.

Exercised on data that was not designed for it (2026-10-22, `experiments/piece_colours_20261022/regions_dev/`): S6, S4 and S2 pick
`regions` under `auto`; arms are `region` joints on S2 (left) and S4, the waist on S6, the rest fall back (their pelvis/thigh colours
are not per-section); M4_15/M4_46 with `--expect arm:quinary` find the cyan arm regions, but all five joints fall back (small chest/arm regions merge or the cuts are not colour boundaries).

Real piece-colour concepts (2026-10-22, `experiments/piece_colours_20261022/P_11_knight_errant`, `P_29_hawk_helmless_champion`, `P_40_celestial_orrery`, reduced with `--adaptive-hue on`; `pieces_auto/`, `pieces_snap/` (roles style), `pieces_snap_rimstyle/`, sheets `compare_regions.jpg`, `compare_regions_pose.jpg`): `--rigid auto` picks `regions` on all three at every level. Three rules were added after the first run on this data, no threshold was changed: (1) the rim pauldron step no longer absorbs a large section-colour region as a pauldron field (the blue arm is open at the cuff, and the open mesh boundary does not count against enclosure, so the rim style had swallowed the whole arm); (2) a section that already has a region of its own expected colour never takes part of a region of another colour (blue tassets reaching over the thigh zone stay pelvis; a green plate edge over the pelvis zone stays chest); (3) an arm joint whose arm and chest do not touch (the pauldron sits between them) is `region` when the arm|pauldron cut lies on a colour boundary. Colour-edge share of the joint cuts: regions 100% (P_29 0p1 84%) against snap 13-56%. Mean pose gaps with overlap are about the same as snap (arms, thighs); the spine is worse than snap on P_29 and P_40 (about 1.3 against 0.4-0.9 % of height mean).


### Cross-joint (fringe) reassignment: shelves / caps, and the older plane rule (2026-10-22)

Colour alone can leave faces on the wrong section. `split_pieces.reassign_cross_joint` runs inside `build_sections` for every rigid method that has a
pelvis (and on the high-poly graph in `segment_first.py`, before the reduction). On by default (`rigid.cross_joint.enabled`); `--no-cross-joint`
(split_pieces and segment_first) switches it off; the `given` method (labels computed elsewhere) skips it. `rigid.cross_joint.mode` picks the rule:
`shelf` (default), `plane` (the first rule, described further down) or `both` (shelf, then plane).

**Shelf / cap rule (`mode: shelf`, default).** The user's ground truth (`experiments/segment_first_fringe_20261022/user_truth_P29_chest_ledge.json`): 19 faces of the
P_29 0p4 chest form an up-facing ledge at the very bottom of the chest (2-17 mm above the pelvis top, meeting the chest wall along its inner edge at a 77-96
degree fold, colour boundary along its outer edge); as part of the pelvis they close it into a clean shape, left on the chest they are a disc-like flange.
For a joint between sections A|B (the axis points from A into B; both directions are tried, so a down-facing lip on top of the pelvis goes to the chest):
faces of A whose outward normal points along the axis into A's side (within `shelf.axis_deg` = 35 degrees; up-facing at the bottom of the chest) and that
lie within `shelf.band` (3% of height; distance of a vertex to the A|B boundary polyline) are grown into connected groups over edges up to
`shelf.crease_deg` (45 degrees dihedral). A group that touches B moves to B when it is at most `shelf.max_share` (10%) of A, has at least `shelf.min_faces`,
borders B along at least `shelf.min_contact` (25%) of its outline and is separated from the rest of A by a fold (mean dihedral of its neck at least
`shelf.min_fold_deg` = 30). There is no distance-past-the-plane test, so vertical bands (abdomen, baldric) can never move. `shelf.joints` (default
`["waist"]`) lists the joints it runs on (the cross_joint `joints` list still limits them first): on P_29 the armpit / hip candidates were inward-facing
single faces and a crotch face, no ledges, so they are off by default. `pieces.json` `rigid.cross_joint` lists every move and near miss (`rule: shelf`, faces,
area / share of the section, angle of the normals to the axis, contact share, neck length and dihedral, offset from the pivot, `rejected_because`).
Results (`experiments/piece_colours_20261022/<concept>/pieces_shelf/`, `pieces_shelf.log`; `--rigid auto --pose-test`): P_29 0p4 moves exactly the 19 ground-truth
faces (recall 19/19, no extra; the plane rule moved 66 faces, 19/66), 0p2 / 0p1 move 26 / 32 faces (2.8% of the chest, y 0.540-0.548, all up-facing);
P_11 moves 3 / 8 / 17 single-face to 5-face ledges (0.4-0.6% of the chest), P_40 2 / 4 / 7 (0.2-0.3%); nothing else, in particular no abdomen band or baldric.
Because the abdomen band now stays on the chest, the spine-bend gap is not reduced as it was by the plane rule (P_29 mean 2.19 -> 2.36 / 2.21 -> 2.05 / 2.33 -> 2.11 % of height;
plane rule 0.9).

**Plane rule (`mode: plane`; wrong on real data: it moved P_29's abdomen band, 18% of the chest, and P_11's baldric).** Kept for comparison.
Original description follows.

- Joints (`rigid.cross_joint.joints`): `waist` chest|pelvis (axis down), `hip_l/r` pelvis|thigh (hip -> knee), `armpit_l/r` chest|arm (shoulder ->
  elbow); `shoulder_l/r` pauldron|arm exists but is off (pauldrons legitimately cover the upper arm: on P_29 it would move 21-23% of the pauldron). Pivots are the
  pose-test pivots (base `parts.npz` through the ICP fit). Every joint is checked in both directions (`directions: both`).
- For a direction `from -> to` every face centroid gets a signed distance `s` (fraction of height) along the axis from the pivot, positive = into
  `to`'s side. The section `from` is cut into **planar patches** (`planar_patches`: region growing, flattest faces first, normals within
  `patch_deg` = 30 degrees of the seed normal). Per-edge dihedral thresholds were tried first and do not work on the Tripo high-poly meshes: their
  folds are bevelled over several faces, so at 25 / 35 / 50 degrees the whole P_40 chest stayed one 99.5% patch.
- A patch (patches joined through the small bevel patches beyond the plane form a group) moves when: >= `beyond_share` (85%) of its area has `s > 0`
  and its area-weighted mean `s` is >= `margin` (per joint family: waist 2.5%, hip / armpit 4%, shoulder 5% of height; this is the guard that keeps
  legitimate overhang, a breastplate edge just over the fauld or tassets just over the thighs, where they are); it is not the largest patch and a plate
  that continues across the plane is one patch that is only partly beyond it, so it stays (that is the "distinct from the main body: bounded by a
  fold or flange" test); the group is >= `min_share` (0.5%) / `min_faces` and <= `max_share` (30%) of the section; it touches the target section along
  >= `min_contact` (10%) of its boundary. `complete_to_cut`: the rest of the section beyond the group's own upper edge (5th percentile of `s`) that hangs together with it
  (side walls, bevels) moves too, so the seam is one clean line instead of a ragged one.
- `pieces.json` `rigid.cross_joint` lists every move (faces, area, share of the section, mean / max distance past the plane, neck dihedral,
  mean angle of the patch normals to the joint axis, contact share, cut level, completed / bevel faces) and every near miss with the reason
  (`rejected`); `segment_first.json` / `pieces.json` carry the same record for the high-poly run.

## Mirror-symmetry scan (`symmetry.py`, `symmetry_scan.py`, 2026-10-24; read-only, nothing in the labelling changes)

The marker bases are exactly left/right symmetric (anatomical right = -X) but an image-to-3D mesh and its texture are not. `symmetry.py` (numpy + mathutils, Blender-python compatible; the plane fit and the statistics also run in plain python) measures how much, so symmetry can later become a second source of evidence (pool the texture votes of mirror partners where they agree; spot designs that are asymmetric on purpose, e.g. a diagonal strap). `reduce_model.py` / `face_labels.py` are not touched: they still mirror about x = 0 of the normalized mesh (bbox centre) or, for `mirror_wear`, the base plane mapped through the ICP fit.

* **Plane fit** (`fit_plane`): a full plane (unit normal from yaw + pitch, plus offset) minimising the *trimmed* mean (closest 80%) distance between mirror-reflected surface samples and the surface, so one-sided gear and unseen inventions do not pull it. Starts: the base's sagittal plane mapped into mesh space through the existing base fit (`symmetry_plane` + the manifest's ICP scale/translation), and the best of a coarse x = const scan (which includes the pipeline's x = 0); each is refined by coordinate pattern search with halving steps. `symmetry_scan.py` runs it on the 0.1% low-poly level (about 5x cheaper nearest-surface queries; within 0.1% of height of the source) and measures everything else on the full source GLB, in the same normalized frame `reduce_model.py` uses (the manifest's `normalization_*`).
* **Correspondences** (`measure`): 24,000 area-uniform samples; each is reflected across the plane and the nearest surface point (BVH) is its partner. Recorded: geometric distance (reported in % of height), normal agreement (reflected normal . partner normal), texture role of both sides (`Palette.classify` of the module's own palette incl. fitted hue shifts; class 0 = base including the achromatic white anchors) and the best concept-camera view cosine of both sides (`face_labels.visibility`, the manifest's cameras and `omit_views`). A partner counts as a real counterpart when it is within 1.5% of height and the normals agree (dot >= 0.5). Colour is compared only where both sides are confidently classified (classify weight >= 0.5) and the partner is a real counterpart; "well seen" = both sides at view cosine >= 0.25 (`face_labels.GRAZING_COS`, full visibility weight), so "both sides seen and disagree" (a real asymmetric design) is separate from "one side unseen".
* **Regions**: samples are grouped by the nearest fitted base body part's family (`arm_stretch.l` + `.r` = `arm_stretch`; `head`, `neck`, `shoulder`, `spine_01`, `root` (pelvis), `thigh_stretch`, `leg_stretch`, `foot`, `forearm_stretch`, `hand`, `skirt`), by height band (0.2 steps) and by coarse (|x|, z) cell (0.2) for hot spots. **Expected asymmetric** regions (`symmetry.EXPECTED_ASYMMETRIC`: `right_gauntlet_boot` = hand, forearm, foot, lower leg; `outfit` = foot, lower leg; `body_armor` none) are summarised separately (`expected_asymmetric`) and excluded from `global`, the headline numbers and the flagged list. A family is flagged **well-seen asymmetric** when at least 120 well-seen compared samples disagree in colour >= 25%, or the p95 mirror distance of its well-seen samples is >= 2% of height.

```bash
python3 tools/tripo_pipeline/symmetry_scan.py models/<set> [models/<set>/<job> ...] [--out experiments/symmetry_scan_20261024]
    [--threads 2] [--samples 24000] [--no-render] [--stratify N] [--force] [--summary-only] [--dry-run]
blender -b -t 2 --python tools/tripo_pipeline/symmetry_scan.py -- --module-dir models/<set>/<job>/<race>/<module> --out-dir <dir>   # one module
python3 -m unittest tools/tripo_pipeline/test_symmetry.py     # plane fit on a synthetic symmetric + perturbed point cloud, region logic, ~30 s
```

The batch mode runs one `blender -b -t N` per module, serially, for every module whose `reduced/manifest.json` lists three finished levels, and writes only under `<out>/<set>/<job>/<race>/<module>/`: `symmetry.json` (plane, comparison with x = 0 and the base-mapped plane, `summary.global / by_family / by_height_band / hotspots / asymmetric_regions`, `headline`), `heat_geometry.png` (mirror distance on the 0.2% level, front | back; blue 0, cyan 0.5, green 1, yellow 2, red >= 4% of height), `heat_colour.png` (grey-green = partners agree, red = disagree with both sides well seen, orange = disagree with a side poorly seen, dark = not compared, blue = disagrees inside an expected-asymmetric region) and `plane_overlay_front.png` / `_top.png` (model in blue and its reflection across the fitted plane in orange, x-ray, so symmetric parts read purple; thin boxes mark the planes: green = fitted, cyan = base-mapped, yellow = pipeline x = 0). Afterwards `<out>/summary.json` / `summary.csv` (per model plus aggregates by module, backend, race, set and region frequency; backend = `studio_submission.json` `backend`, Tripo records have no such key) and `<out>/contact_sheets/` (8 most / 8 least symmetric `body_armor` by `asymmetry_score` = geo p95 % + 20 x garment-colour disagreement, the colour term only with >= 300 compared garment samples, built with `tools/contact_sheet.py`). Limits: the colour comparison uses the hard class of the texture at one point, so a fold or a colour edge a sub-percent of height off reads as a disagreement (the symmetric Tripo models set the floor at about 1-2% disagreement); the interior-shell strip of `reduce_model.py` is repeated from `interior_removed.npz` but no scanned module needed it; garment-only shares are noisy where a model has little garment area (`colour_garment_compared` in the json).

## Wearable by cut (`wearcut.py`, 2026-10-24; default wearable method, `--wearable-method cut|faces`)

The wearable used to be the reduced labelled level minus its base faces (+ mirrored copies): its openings follow whole low-poly faces (sawtooth), the left and right openings differ, and a face is colour-blind to the garment/base boundary. `cut` (default in `reduce_model.py`, `convert_job.py --wearable-method`) does it on the high-poly mesh instead; `faces` is the old behaviour and the automatic fallback.

Pipeline (about 20-35 s of the 1-2.5 min a reduction takes; `reduced/` + `<module>/wearcut/`):
1. `wearcut_blender.build_prep` (Blender, in `reduce_model.py` after the three levels, or by `rewear.py`): the cleaned high-poly mesh with `rules.orient_consistent` (`local_repair` leaves flipped patches or a whole inside-out shell; meshopt locks the vertices of inconsistent edges, so such a patch also doubles the face count: seen on 2 of the first 10 modules, one gnome shell with 74% "unseen" in the labelled level), three texture colours per face, body part, concept-camera visibility (two-sided) and, where the module lets garment be and `clearance.json` exists, the off-body distance and base-normal agreement per face -> `wearcut/prep/prep.npz` (+ `prep.json` with timings, orientation record).
2. `fit_mirror_plane`: `symmetry.fit_plane` on the 0.1% level, started from the base's sagittal plane through the ICP fit (about 1-3 s). A plane tilted more than 10 degrees from X (a yawed Tripo body; one plain-plate-mail elf_male) is refused: that module keeps the `faces` wearable.
3. `wearcut.py` (venv python, numpy + scipy; `$SEGMENT_FIRST_PYTHON` / `config.json segment_first.venv_python` / `characters/.venv`): evidence per face with **the reduction's palette** (`manifest.palette` incl. `hue_shift`; nothing is fitted again; `check_hue_shift` drops a shift for the high-poly step when it leaves 10 points more of the saturated garment-zone colour unclassified than the nominal hues, recorded in `wearable.hue`), pooling of mirror partners (local agreement, blocked where both sides are well seen and disagree and in the module's expected-asymmetric parts), the off-body rule (`face_labels.off_body_excess` thresholds: a face beyond its part's clearance cannot be base, as a base cost of 3 x excess), Potts clean-up, `reflood_unseen` / `absorb_small` / `fill_slivers` of `segment_first.py`, the hem-riser rule at high-poly scale (`riser_rings` 6 ~ the 2 low-poly rings), a crease-aware smooth vertex field, the iso-cut, island drop, garment-only reduction (locked/smoothed boundary), single-edge flap triangles dropped (`split_pieces.prune_flaps` rule, 6% of the height), duplicate faces dropped. Pairs: `right_gauntlet_boot` = the right of the plane only, the left limb of the mesh is discarded and the left piece is the exact welded reflection (winding flipped, part `.r`->`.l`, source `mirrored`); `outfit` = right footwear components (>= 80% on right foot / lower leg) reflected, rest kept (manifest `wearable.footwear` = `component`). **Footwear joined to the leg garment (2026-10-25; a shoe drawn continuous with the hose / trousers, 17 of 28 first outfits):** no separate right footwear component -> `wearcut.ankle_foot_piece`: the right garment stays one continuous piece, the foot part is cut off a copy at the ankle (0.5 iso-line of the smoothed indicator, sigma 1% of the height, of the cut garment faces on the base's `foot.r` body part: same `cut_mesh` as the garment cut, so a clean loop), reduced on its own (locked, smoothed opening) and only its exact reflection is added on the left (part `.r`->`.l`, source `mirrored`, `mirrored` flag); `footwear` = `ankle_cut`. Nothing is added, and there is no fallback, when the right foot has no garment (garment covers < 20% of the foot.r zone: barefoot designs, `footwear` = `none`) or the left foot already has (>= 20% of foot.l; the outfit prior normally keeps it bare); the reason is in `wearable.pair.note`. A cut that is not plausible (no foot.r/foot.l part, < 20 faces, piece area outside 0.5-2.0 x the garment on the foot zone, < 90% right of the plane, nothing separated) -> `faces` for that module (manifest `wearable.fallback_reason`). The left shoe is the exact reflection of the cut foot piece (`pair_check`); the right shoe inside the continuous garment is reduced with the rest, so its tessellation can differ from the piece within the level's tolerance.
4. `wearcut_blender.install`: per level `lod_error_<lv>__wearable.glb` (export_native, the palette's material slots, names checked), the previous one kept as `__wearable_faces.glb`, the sidecar arrays in the new GLB's face order (`lod_error_<lv>_colors.npz`: `wearable_body_part_glb_order`, `wearable_label_source_glb_order`, `wearable_mirrored_glb_order`, `mirror_plane_*`, `wearable_method`; the old `wearable_*`/`mirror_*` arrays go to `lod_error_<lv>_colors_wearable_faces.npz`), manifest `wearable` (method, plane fit, pair check, rules, hue, seconds, fallback reason) and `levels.<lv>.wearable_*` / `mirror`. `make_wearable_blend.build` then gives the FACE attributes `body_part`, `mirrored`, `label_source`. Any failure keeps the `faces` wearable of that level (never raises): `convert_job.py` records `module_conversion.<race>/<module>.wearable` (requested / method / status / per-level methods / fallback reason).
`labels.npz` (the cleaned high-poly labels + sources), `wearcut.json`, `plane.json`, `palette.json`, `wearcut_lod_<lv>.npz` stay in `wearcut/` (about 20-30 MB per module, mostly `prep.npz`; `--force` rebuilds it).

Backfill (no Tripo/Hyper3D/browser, nothing generated): `python3 tools/tripo_pipeline/rewear.py <module_dir>... | --all [--match S] [--jobs 3] [--force] [--dry-run]` re-runs only the wearable step from `source.glb` + `reduced/manifest.json` + the level GLBs (Blender 3 threads per module), keeps `manifest_before_rewear.json`, `wearable_faces.blend`, the `_faces` GLBs / arrays, updates the manifest and `.tripo-job.json` (`module_conversion.<key>.wearable`, `wearable_backfill`), writes `wearcut/rewear_metrics.json` (old vs new: faces, area, boundary loops / length / roughness / sawtooth / sharp turns, left-right opening mismatch, deviation from the high-poly, label change on the high-poly) and a summary json (default `experiments/rewear_<date>/summary.json`). ## Feature label passes (`studs`, `rings`; opt-in, 2026-10-25)

Two opt-in clean-ups of the HIGH-POLY garment labels, for details that the normal cleaning (`absorb_small`, Potts smoothing) loses or smears. Off unless a spec is chosen; without one every output is byte-identical to before (checked on a converted module: wearable GLBs, all arrays, `labels.npz`). They only change garment *roles* (studs) or turn garment faces into void (rings); a base face never becomes garment, so the garment/base boundary and the mirror pooling are those of the plain run.

* **`studs`** (`feature_labels.py`): round studs/rivets painted tertiary (yellow). The texture is yellow on nearly every stud but the labels lose them (a stud is ~0.03-0.07% of the garment area, under the 0.05% speck limit) and Tripo's texture disc is offset from the dome (spill onto the plate). The pass finds the domes by raised height over a heat-smoothed copy of the surface (seeds, opening/closing on the face graph, roundness/size tests, extents grown down to 20% of the peak), relabels each dome tertiary and removes small tertiary spill that is not raised. Trim bands, belts and buckles (big or raised) are kept.
* **`rings`** (`ring_labels.py`): chain-mail rings. Tripo paints ring centres partly green and tubes partly blue; the geometry is reliable (a ring is a raised torus over a recessed undershirt). Faces are classified by relief (a ladder of heat-flow scales, the scale with the best texture-supervised separation wins; local calibration of the ring / centre levels; large non-ring blobs such as belt, buckle and patches are protected), the texture is only a weak prior. Ring tubes become `primary`; centres become `secondary` (`rings:secondary`) or are removed (`rings:void`, label 0: the cut wearable gets real gaps, optionally only above the waist: `rings:void:auto` = above the top of the belt/buckle, `:all`, or `:<z>` in normalised units). Void uses a finer cut-field smoothing (0.3% instead of 0.8% of the height) so the gaps stay open.

Spec syntax (`feature_hooks.py`): `studs`, `rings` / `rings:secondary`, `rings:void[:auto|:all|:<z>]`, `none` (explicit off). Which sets use which spec: `resolve_spec` = command line `--feature-labels`, else the job record (`.tripo-job.json` `feature_labels`: a spec, or `{"default": spec, "<module>": spec}`), else `config.json` `feature_labels.sets[<set id>]` for the modules in `feature_labels.modules` (body_armor, right_gauntlet_boot). The five sets of 2026-10-25 are in the config: `breastplate_07`, `splint_14`, `studded_leather_09` = `studs`, `chain_mail_05` = `rings:secondary`, `chain_shirt_02` = `rings:void:auto`. New conversions of those sets (and `relabel_module.py`) therefore keep the pass without further flags; remove the line to switch it off.

Where it hooks in (a few lines each, all optional):
1. `wearcut.run`: `P['label_hook']` / `params['label_hook']` (CLI `wearcut.py --feature-labels SPEC`) is called on the final high-poly labels, after the hem-riser rule and before the cut field is built. The label sources stay those of the unmodified labels (geometry decided, not a texture/prior guess), so the low-evidence review share does not move; a hook that turns base into garment is an error. Output beside `labels.npz` (which then holds the labels *after* the pass): `feature_labels.npz` (`label_old`, `label_new`, the pass's arrays: stud ids / spill / relief / ring ids ...) and `feature_labels.json` (every number); a plain re-run deletes them.
2. `segment_first.process(label_hook=...)` (CLI `segment_first.py --feature-labels SPEC`, passed by `convert_job.py`): same pass on the cleaned labels of `segment_first/prep` (its own face order), after `fill_slivers`, before the sections are cut and reduced; arrays in `segment_first/feature_labels.npz`, summary in `segment_first.json` `feature_labels`. The per-face fallback (`split_pieces.py`) has no pass (recorded in `split_step.json`).
3. Labelled full LODs (`lod_error_<lv>.glb`): `feature_relabel.py plan` (venv python) transfers the corrected roles to the reduced triangles (studs: majority new role of the high-poly faces a triangle covers, where >= 25% of its covered area changed; rings: majority new label of the ring/centre region where it covers > 50%; void becomes base in the full level), then `feature_relabel.apply` (Blender) rebuilds the GLB from the level's mesh with `reduce_model.export_native` (same exporter, material slots, flat normals), rewrites `lod_error_<lv>_colors.npz` (`material_id`, `glb_face_order`, `body_part_glb_order`; the old ids stay as `material_id_before_feature_labels`), the manifest level (`material_face_counts`, `feature_labels`: rule, triangles changed, role areas before/after) and the `lod_error_<lv>` objects of `review.blend`. Triangle count and geometry never change. A level whose GLB has fewer triangles than its review mesh (the exporter dropped degenerate triangles: 11 of 330 levels of the five sets) keeps its roles and the manifest says why.
4. Entry points: `reduce_model.py --feature-labels SPEC` (new reductions: cut wearable + labelled levels), `rewear.py --feature-labels SPEC` / `wearcut_blender.py rewear --feature-labels SPEC` (converted modules: re-cut with the cached `wearcut/prep`, skipped when the module already ran the spec), `relabel_module.py` (resolves the spec itself), `convert_job.py --feature-labels SPEC|none` (reduction and segment-first split), and `apply_feature_labels.py` (below). Recorded in `reduced/manifest.json` `wearable.feature_labels` (spec, pass summary, per-level transfer), `levels.<lv>.feature_labels`, `levels.<lv>.wearable.feature_labels`, `.tripo-job.json` `module_conversion.<race>/<module>.feature_labels` (+ `split.feature_labels`) and `split_step.json`.
5. `highpoly.blend` (the texture-detected evidence) is not touched.

Shading: every GLB these steps write goes through Blender's glTF exporter exactly like the pipeline's own outputs (flat faces, one NORMAL per corner equal to the face normal, one primitive per material). The smooth look of the first prototype sheets came from the prototype's own minimal GLB writer (`wearcut.write_glb`, no NORMAL accessor, so viewers smooth it): that writer is only used by the analysis CLIs, never for the pipeline files. `apply_feature_labels.py` checks the flat share of every rebuilt GLB (record `flat_shaded_all`).

Batch (converted modules): `characters/.venv/bin/python tools/tripo_pipeline/apply_feature_labels.py [<module_dir> ...] [--sets ...] [--jobs 2] [--phase rebuild|fit|all]` backs each module up to `experiments/feature_labels_20261025/backups/<set>/<job>/<race>/<module>/` (`reduced/` without the two big source files, `wearcut/` and `segment_first/` without `prep/`, `fit/`, `split_step.json`, the job record entry; never overwritten), rebuilds the cut wearable + labelled levels + review/wearable blends + (modules with `segment_first/`) the pieces, restores the module on failure, skips modules held by a conversion worker (`.module_locks`, retried at the end), then re-runs `body_fit.py --method full` and `--method vertex` (`--force`) because the wearables / pieces changed. Per-module records and `table.md` in `experiments/feature_labels_20261025/applied/`. Analysis-only CLIs that write into a scratch folder: `feature_labels.py studs <module_dir> --out DIR [--recut] [--pieces]`, `ring_labels.py <module_dir> DIR [--centre secondary|void] [--void-above-z auto]`. Tests: `test_feature_labels.py`, `test_ring_labels.py`, `test_feature_hooks.py`, the hook test in `test_wearcut.py` (venv python).
Limits: the passes need the cut wearable (no `faces` fallback modules); studs radius is estimated from the yellow texture blobs (0.02 when fewer than 3), so a design with many unpainted domes relies on the "plain dome near a yellow stud" rule; ring void on a hole pattern the relief cannot resolve (dwarf_female shirt only partly) leaves part of the centres coloured, not void; at 0.4% the studs and rings are a few triangles wide, so the labelled level shows them roughly.

## Winding after local repair (`orient_consistent` in `reduce_model.py` and `segment_first_prep.py`, 2026-10-24)

`adaptive.local_repair` leaves patches (sometimes a whole shell) with winding that disagrees with their neighbours, differently from run to run. Everything that reads normals then misbehaves: `face_labels.visibility` (one-sided: a flipped face looks away from every concept camera, so it counts as unseen; the gnome chain shirt's labelled level had 61-74% low-evidence area) and meshopt (it locks the vertices of an inconsistent edge, so the level stays dense; one plain-plate-mail halfling gauntlet came out at 1720 instead of 818 triangles). Since 2026-10-24 both front matters run `wearcut_rules.orient_consistent` right after `local_repair` + `canonical_order` (then `canonical_order` again for the vertex rotation of flipped triangles, so a run stays reproducible): the manifest `cleanup.orient` (`segment_first/prep/prep.json` `cleanup.orient`) records faces, shells, inconsistent edges before/after, flipped faces and the method. `wearcut_blender.build_prep` calls it again and finds nothing to do (its `prep.json` `orientation` then reads 0 flips). `face_labels.visibility` stays one-sided on purpose: with a consistent, outward winding it is correct, and the two-sided variant of `wearcut_blender.visibility_two_sided` would also count the inner side of a genuine second shell as seen; a whole open shell that is consistent but inside out (nothing to infer its side from) is the only case it would rescue, and none turned up in the 218 converted modules.

[--resplit] [--threads 3] [--dry-run]` moves `reduced/`, `wearcut/`, `highpoly.blend` (and with `--resplit` `segment_first/`, `pieces/`, `split_step.json`) to `experiments/relabel_20261024/backups/<set>/<job>/<race>/<module>/`, runs `reduce_model.py` with the flags the old manifest recorded (joint role = `--separable`, `hue_fit.mode`, omitted views), puts the old outputs back when it fails, and updates `.tripo-job.json` `module_conversion.<key>` (`levels_needing_review`, `wearable`, `split`, a `relabel` note) under the job-record flock. ## Body clearance and fit (`body_fit.py`, 2026-10-24; measures and fixes wearables that intersect the game base body)

Tripo rebuilds armour as a skin-tight shell that sits on or inside the low-poly game body, so the wearables poke through it (measured on 216 converted modules: median 37% of the wearable area has a vertex inside the body, median deepest vertex 43 mm, up to 227 mm on a gnome splint cuirass). `body_fit.py` measures that and writes a fitted copy (two methods, see **Methods** below); the originals, their face-order sidecar arrays and everything else in `reduced/` are never touched.

* **Body**: `tools/preview/cache/bases/<race>.npz` (`V` Blender world coordinates of the rest-pose base mesh, `F` triangles, `part` per triangle into `part_names` from the `bone_<part>` material slots like `outfit_studio/blender/importer.py::base_rest_mesh`, plus the `<race>.glb` / `.json` {o, H} rest frame), written by `tools/preview/export_bases.py` (`blender -b --factory-startup -P tools/preview/export_bases.py -- --force`; the .blend files are never saved). The concept base `base_views/<race>/parts.npz` is the same mesh for all 11 races (`body_fit.py --race-check`: vertices, faces and parts equal to 1e-7 m; the gnome only has two unreferenced vertices, so a nearest-surface check on its vertices reads 57 mm).
* **Frames**: a wearable / piece GLB goes native (glTF) -> Blender coordinates (x, -z, y) -> `outfit_studio/core/transform.native_to_world` with the manifest's `rotation_to_review`, `normalization_*` and `parts.fit` and the base's H, o: Outfit Studio's chain and the preview's "on body" view.
* **Signed distance** per welded vertex: exact point-to-triangle distance (Ericson closest point, candidates from a KD-tree of triangle centroids and a bounding-sphere test, so the true nearest triangle is never missed) and, for "inside", the sign of the angle-weighted pseudonormal (Baerentzen & Aanaes 2005) of the closest face / edge / vertex (the barycentrics of the closest point pick the feature; pseudonormals are built once per body from the position-welded topology, sign = sign((p - q) . n), nothing is inside outside the bounding box). The base is not watertight and not clean (feet, hands and some seams are open, three races have non-manifold sliver edges, human_male / gnome / halfling_female have overlapping or self-intersecting limb parts: only elf_female, elf_male and orc_male are closed 2-manifolds), so the old generalized winding number > 0.5 (every point against every base triangle; positive outward after the winding is fixed by the mesh's signed volume) is kept as the reference and decides wherever the pseudonormal sign is unreliable: the closest feature touches a boundary, non-manifold, inconsistently wound or pinched edge / vertex or a triangle collapsed by the weld, the closest triangle crosses a non-adjacent triangle or is buried in another part (winding at its centroid +/- 0.01% of the height is not outside / inside), any triangle within `PN_REACH` = 5 cm of such a defect, and points within 1 micron of the surface. `--inside-test winding` (module constant `INSIDE_TEST`) runs the reference everywhere; both give the same signs (checked on 30+ modules' vertices and random points, see the test file), at a fraction of the cost: the winding pass was 12-30% of a fit and now disappears next to the closest-point search. Negative = inside. Triangle value `d_mm` = smallest of its three vertices. Margin = `--margin-pct` % of the base height (default 0.4%, 7 mm on a 1.8 m human). Metrics per GLB: area (m^2 and %) with d < 0 and 0 <= d < margin, max / p95 depth of the penetrating triangles, min d, a by-body-part breakdown (part of the closest triangle of a triangle's worst vertex) and `centroid_penetrating_area_pct` (triangle centroids, a check that vertex sampling is not hiding interior pokes: it is lower than the vertex figure).
* **Methods (`--method full|vertex`, 2026-10-25)**: `full` (default) = the two-sided fit below (vertex test **and** body-through-armour test); `vertex` = the first version (only armour vertices are measured and pushed / scaled, code path unchanged), kept because the body can instead be hidden under the armour at render time. Output names do not collide: `full` writes `reduced/lod_error_<lv>__wearable_fitted.glb` and `<pieces dir>/lod_<lv>_fitted/` (the names the preview and Outfit Studio read) plus `fit/body_fit.json`; `vertex` writes `reduced/lod_error_<lv>__wearable_fitted_vertex.glb`, `<pieces dir>/lod_<lv>_fitted_vertex/` and `fit/body_fit_vertex.json`. Every output has its `.clearance.json`; every record carries `fit_algorithm` (`full` / `vertex`) at module, wearable and piece level. The clearance sidecars (and the metrics `poke` block) are measured the same way for both methods.
* **Body through armour (reverse test)**: the vertex test cannot see the low-poly body bulging through the middle of a large armour triangle whose corners are all outside it. The body surface is sampled on barycentric sub-triangle grids (spacing at most 0.5 % of H, so a large body triangle is sampled as finely as a small one; about 350k samples on a human), every sample casts a line along its face normal into a uniform grid of the armour triangles (`RayGrid`, 3 cm cells, the line sampled every 1.5 cm, Moeller-Trumbore on the candidates). A sample is covered when armour is hit outward within 0.25 m (for rigid pieces the union of all pieces of the level counts), and it is **poking** when it is uncovered but armour lies behind the surface within 0.12 m. Filters against false positives: the hit point must still be inside the body (the line has not left the body first: `exit` distance of the sample, precomputed once per body, so an arm's far side does not count) and its distance to the body must be at least 0.6 of the depth (an armour back plate 100 mm behind a chest sample but 15 mm from the back surface belongs to the back's samples). The nearest inward hit is attributed to its armour triangle / piece. Metrics `poke` per GLB: `area_cm2`, `depth_mm` {p50, p90, max}, `area_deeper_1mm_cm2`, `by_part`, `samples`, `sample_spacing_mm`. In the clearance sidecar the hit triangles read `d_mm = min(vertex d_mm, -depth_mm)`, so the preview's Clearance overlay shows red where the body comes through (schema unchanged; the `poke` metrics block documents it).
* **Fit A, wearable** (`lod_error_<lv>__wearable_fitted.glb`): vertices are welded by position across primitives/splits (1 micron) so seams never open. Rounds (max 12, stop when every vertex is within 0.5 mm of the margin; 6 left a third of the wearables short because vertices between two body parts ping-pong; vertices still short after the rounds get up to 40 hard, unsmoothed projections along the normal, `push.cleanup_iterations`): measure, constrain every vertex closer than the margin to a displacement of at least `margin - d` along the body normal (angle-weighted pseudo-normal interpolated at the closest point; constraints are kept once active), then 80 iterations of a screened, inverse-edge-length weighted Laplacian smoothing of the displacement VECTORS (`KAPPA` 0.03: the field decays about 20% per hop) with the normal component of the constrained vertices raised again after each pass. The field is smoothed, not the geometry, so low-poly panels move as a whole. Only the POSITION accessors (and NORMAL: flat-shaded primitives get the exact new face normals, smooth ones the original normal shifted by the change of the faces around it) are patched in the GLB; JSON (except accessor min/max), indices, primitives, face order, materials, node names are identical, so `lod_error_<lv>_colors.npz` and the preview's marks stay valid. Corners that do not move stay bit-exact. In method `full` every round also measures the reverse test and every poking sample demands that its armour triangle moves outward along the body normal at the sample by depth + margin: each of the triangle's three welded vertices gets that as a required displacement (max-merged with the vertex constraints, same screened smoothing; `POKE_LIFT = 'vertex'`, the alternative `'tri'` = minimum-norm barycentric split along the triangle normal is kept for experiments), then both directions are re-measured. Done when every vertex is within 0.5 mm of the margin and the poking area is below 0.5 cm^2 or no sample is deeper than 1 mm; a poke that does not go away is capped at 0.15 m + margin of poke-driven lift per vertex and at 8 hard cleanup projections (`push.poke_residual` records what is left and the level is flagged `needs_review`). Record per level: displacement (max / mean / p95, mm), bend (face-normal change, change of the dihedral angle across edges that were within 5 degrees of flat).
* **Fit B, rigid pieces** (`<pieces dir>/lod_<lv>_fitted/<piece>.glb`, only a split with chest or pelvis counts, as in `pipeline_source.pieces_output`): the body parts a piece covers (those that are the closest part of at least 15% of its vertices; limb parts win over trunk parts), pivot = centroid of their vertices, axis = principal axis (PCA) of those vertices plus the next part down the limb (a stubby thigh's own PCA is its thickness); trunk-only pieces (chest, pelvis) use the up axis because the PCA of a T-posed trunk is the shoulder width. An affine scale s >= 1 perpendicular to the axis about the pivot (nothing along the axis, so flat panels stay flat): the smallest s <= 1.35 (bisection) that clears the margin **and the reverse test against the other pieces** (method `full`), method `scale`; a piece that is clear already is copied (`none`); a piece that would need s > 1.35 falls back to Fit A on that piece (method `push`, `needs_review`). In method `full` a level pass follows (up to 3 passes): with all pieces moved, pieces that still have poking samples (the cuts between pieces, a push fallback next to a scaled piece) are pushed again with the extended Fit A against the current other pieces (`level_pass` per piece, `poke_passes`, group `poke_before` / `poke_after`). Reported: s, method, covered parts, and `gaps` = the largest distance between vertices of different pieces that coincided before the fit (the cuts between pieces; there are no overlap strips by default, so a scale opens the cuts by up to that much).
* **Outputs (contract of the preview viewer)**: next to every measured GLB (original / fitted wearable, original / fitted piece) `<stem>.clearance.json` = `{"model": repo-relative path, "margin_mm", "metrics", "meshes": [{"mesh_index", "name", "d_mm": [per triangle, 0.1 mm]}]}`; mesh_index and triangle order follow three.js GLTFLoader traversal (scene nodes depth first, a node's mesh before its children, one Mesh per primitive in primitive order, triangle t = t-th index triple or vertex triple). `<module>/fit/body_fit.json` (params, per level before/after, displacement, bend, pieces table, gaps, warnings, timings, input mtimes) and the summary (default `experiments/body_fit_<date>/summary.json` + `summary.md`, worst first). A fitted GLB is redone when its source GLB, the manifest or the body cache is newer (or `--force`); `--measure-only` writes only the originals' sidecars. Modules locked by a conversion worker are skipped.

```bash
python3 tools/tripo_pipeline/body_fit.py <module_dir>... | --all [--method full|vertex] [--source original|aligned] [--match S] [--levels 0p4,0p2,0p1] [--margin-pct 0.4] [--measure-only] [--jobs N] [--force] [--inside-test pseudonormal|winding] [--summary FILE]   # --source aligned: see "Alignment to the base body"
python3 tools/tripo_pipeline/body_fit.py --race-check            # concept base vs game base, per race
python -m unittest tools/tripo_pipeline/test_body_fit.py         # venv python; synthetic capsule body and GLBs, < 1 s
```
Limits: method `vertex` only constrains vertices, so a long triangle whose vertices clear the body can still cut through a bulge between them (method `full` removes that; the poke area, not the vertex figure, is the number to read); the reverse test costs about 2 s per measurement of a wearable (a `full` fit takes minutes per module) and a poke that keeps coming back (gnome body armour: the body is far bigger than the armour, thousands of cm^2 poke before the fit) can cost a lot of displacement before the cap stops it, see `needs_review`; deep interior geometry (inner hem walls, double shells; up to 22 cm inside on gnome body armour) is pushed out to the surface and bends the panels around it (see `bend` and the `large displacement` flag), the right fix for those is removing interior faces in the wearable cut, not this tool; a rigid scale opens the cuts between pieces.

## Alignment to the base body (`align_body.py`, 2026-10-25, prototype on two sets; nothing existing is touched)

The placement every wearable gets (`parts.fit`, `face_labels.fit_base`: a trimmed ICP of the base onto the WHOLE Tripo mesh, armour included, uniform scale + translation) leaves the bare Tripo body about 10.6 mm (mean) off the game base (`experiments/alignment_20261025`, 44 modules): Tripo bodies are 5-9 % too deep in Y, about 1 % tall, their feet 6-16 mm high and outward, the whole mesh is yawed by a few degrees, and the arms and legs are posed differently per module (shoulder ~4.5 deg, elbow ~7 deg, p90 13 deg; elf_male studded `body_armor`: left hand 51 mm forward). The marker base and the game base are the same mesh, so this is a Tripo-side error, not a frame error. `align_body.py` produces an ALIGNED wearable: the wearable deformed the way the Tripo body would have to be deformed to sit on the game base. `parts.fit`, the labels, the labelled LODs and every existing output stay as they are; only new files are written.

```bash
blender -b --factory-startup -P tools/preview/export_bases.py          # once: also writes tools/preview/cache/bases/<race>_rig.npz (rig-only refresh; the body cache is not rewritten)
#   re-run with `-- --force <race>` after editing projects/<race>.blend: align_body/body_fit read only this cache
python3 tools/tripo_pipeline/align_body.py <module_dir>... | --all [--match S ...] [--levels 0p4,0p2,0p1] [--jobs N] [--force] [--measure-only] [--variant v2|v1|core]
#   NB --all means every converted module under models/ (not only the two prototype sets): name the module dirs or use --match for a subset
python3 tools/tripo_pipeline/body_fit.py --source aligned <module_dir>... [--jobs N] [--force]     # fit the aligned wearable / pieces to the body (method full by default)
python -m unittest tools/tripo_pipeline/test_align_body.py                                            # venv python; synthetic body + rig, ~20 s
```

* **Body frame = concept base frame.** Wearables are stored relative to the concept marker base, then scaled onto the cached body by its height `H` (`tools/outfit_studio/core/transform.py`). So the cached body must be built from the same meshes as the marker base. `export_bases.py` `EXTRA_OBJECTS` joins the meshes the marker base got from `build_marker_base.py --add`. For the gnome (since 2026-10-27) that is `base` + `location head` as `head.x`, H 1.30. Its `feet`, `head` and `Nose` stay separate, as in its marker base.
  * Before this, the cache still held the old full mesh: feet plus the tall head, H 1.9. Gnome wearables landed 1.45x too big. Alignment error was 53-109 mm with "stage 1 scale at its bound", against 5-9 mm for the other races; after the fix it was 5.7 mm.
  * The old cache is in `tools/preview/cache/bases/archive_gnome_female_hathead_20261024/`. It still matches the 12 superseded hat-head gnome jobs in `completed/`, which were never aligned.
  * Outfit Studio's importer (`base_rest_mesh`) still takes only `base`, so its gnome frame is H 0.92 (not fixed yet).
* Every hat-head gnome is being redone on the footless base (user, 2026-10-27). The old gnome race folders stay in their completed multi-race jobs. The Models tab (`serve.py newest_jobs`) and Outfit Studio (`pipeline_source.latest`) show only the newest conversion per set, race and module.
* **Evidence**: the bare-body faces (role base, white anchors included) of the high-poly labels (`wearcut/prep/prep.npz` in the review frame + `wearcut/labels.npz`, 0.5-1 M faces; face order and areas checked equal) or, without them, of the labelled LOD (`reduced/lod_error_0p2_colors.npz`, one ring). Left out: faces within `EXCLUDE_MM` = 8 mm (rings = 8 mm / mean edge, at least 1; 3 on a 1 M-face mesh) of any garment face, and faces whose label source is `prior`, `off_body`, `riser` or `mirrored`. The fit set is balanced per body part (budget proportional to sqrt(area) per (part, white anchor) group, at least 40 samples; the white anchors head, hand.l, foot.l count double); a second, area-proportional set (9000 samples) is only for the reported numbers. 20 % of the spatial cells (6 cm) are held out of both stages and reported separately. Everything is measured in the current game world frame (`native_to_world` with the manifest and `parts.fit`).
* **Stage 1, global placement** `T1(x) = c + t + R S (x - c)` (the wearable / pieces use S = I in the default variant, see "Wearable stage 1 without the per-axis scale" below; the bare evidence keeps S): per-axis scale S in 0.80-1.15 (a weak ridge toward 1), rotation R <= 5 deg per axis, translation <= 10 cm; a trimmed (85 %) robust (soft-L1, 2 cm) point-to-plane ICP (tangential residual weight 0.3, 25 outer iterations) of the fit set onto the game base surface. Typical result: scale about (0.98-1.0, 0.89-0.99, 1.01), rotation 0.2-4 deg (mostly yaw).
* **Stage 2, skeletal un-posing**: `tools/preview/cache/bases/<race>_rig.npz` (made by `export_bases.py` from `projects/<race>.blend`, read-only; same freshness rule as the other cache files, and a missing rig file refreshes only itself) holds the rest rig (`bone_names`, `bone_parent`, `bone_head`, `bone_tail`, `bone_matrix` (n,4,4, world), `bone_deform`, `bone_group`, `rig_world`) and the per-vertex skin weights of mesh `base` (`weights` (vertices, groups) in the order of the cached `V`, `group_names`). The Auto-Rig Pro deform bones are merged into 12 limb channels (arm, forearm, hand, thigh, leg, foot x left, right; twist / stretch halves and toes belong to their limb; spine, neck, head, shoulders and the root are static): pivots are the rest joints (shoulder = `c_arm_twist` head, elbow = `c_forearm_stretch` head, wrist = `hand` head, hip = `c_thigh_twist` head, knee = `c_leg_stretch` head, ankle = `foot` head), the pose of a channel is a rotation about its pivot in its parent's frame (hierarchical: arm -> forearm -> hand, thigh -> leg -> foot). The 36 rotation-vector components are fitted by robust (soft-L1) least squares so that the linear-blend-skinned base matches the bare skin in the stage-1 frame: correspondences are the closest points on the POSED base (re-found 12 times), with box limits (arm 45, forearm 50, hand 40, thigh 40, leg 45, foot 30 deg per component) and a prior toward rest (`LAMBDA_SWING` 2e-4 per rad^2 of rotation off the bone axis, `LAMBDA_TWIST` 2e-2 about it, so twist, which is hardly observable, stays near zero). A bone without bare evidence is carried by its children (elbow / forearm / hand position); a bone with no evidence in its subtree either (the right forearm, hand, shin and foot under a gauntlet and boot) is moved only by the garment shell as a weak proxy (4 % of the data mass, the shell offset of the stage-1 frame kept) and otherwise stays at rest. Every bone gets a confidence: `high` (at least 400 bare samples whose dominant skin channel it is), `medium` (carried by children), `low` (proxy or none). The spine / neck are not fitted (no clear gain in the first measurements).
* **The deformation field** `D(x) = unpose(T1(x))` is a function of the world position only. `unpose` takes the skin weights of a point from the POSED base surface (20 k surface samples, every sample p_s counts with exp(-(|x - p_s|^2 - d0^2) / (2 sigma^2)), d0 = distance to the nearest sample, sigma = 2 % of the body height, 320 nearest samples: a Gaussian around the foot point that is continuous in x, also across the medial axis between two limbs) and applies the inverse of the blended LBS transform to bring the point into the REST pose. Because D is a pure function of the position, rigid pieces of one module that share boundary vertices stay together by construction (checked on every module: `gaps.max_gap_mm` 0).
* **Baking**: D is applied to the welded vertices of the wearable GLB / every piece GLB and written back into the NATIVE frame with the ORIGINAL manifest and `parts.fit` (`transform.world_to_native`), through `body_fit.Surface.apply` / `Glb.patched`: only POSITION (and NORMAL: exact face normals for flat-shaded primitives) change, JSON, indices, primitives, materials, node names and the face order stay identical, so the existing sidecar arrays, clearance sidecars and `native_to_world` (the preview's Body checkbox, Outfit Studio) work unchanged. Corners that do not move stay bit-exact.
* **right_gauntlet_boot**: the left piece (faces flagged in `wearable_mirrored_glb_order`) is the exact reflection of the right one across the wearable's OWN mesh plane (the cut's fitted plane, `mirror_plane_normal` / `_offset` of the colours npz mapped review -> world; refined on the vertex pairs, kept only if it fits to < 1e-3 mm). The right piece is aligned with D; the left one is re-created as `reflect_base(D(reflect_current(left)))`, i.e. the exact reflection of the aligned right piece across the GAME base's sagittal plane (`transform.mirror_plane`). Measured mirror error (reflected left vs nearest right vertex): 2e-4 mm (float32), same as before the alignment.
* **Outputs** (beside the originals): `reduced/lod_error_<lv>__wearable_aligned.glb`, `<pieces dir>/lod_<lv>_aligned/<piece>.glb` (segment-first `pieces/` of `body_armor` where present), `<module>/fit/align.json` (code version, evidence counts, `stage1` {center, scale, rotvec_deg, translation_mm, at_bound, rms}, `stage2.bones.<limb>.<side>` {rotvec_deg, angle_deg, swing_deg, twist_deg, bare_samples_own / _with_children, proxy_samples, confidence, at_limit}, `residuals.{current,stage1,stage12}` {mean / p95 / rms, held-out mean / p95, per simplified part}, `anchors` (head, hand.l, foot.l: offset of the anchor centroid from the projected base centroid, per stage), `levels.<lv>.wearable` {displacement, bend, `strain` (edge length change, total) and `strain_stage2_only`, `mirror_plane_current`, `mirror_error_current / _aligned`}, `levels.<lv>.pieces` {per piece strain, `gaps`}, `low_confidence_bones`, `warnings`). `Field.from_record(record, body, rig)` rebuilds the field. `body_fit.py --source aligned` then fits the aligned files and writes `reduced/lod_error_<lv>__wearable_aligned_fitted.glb`, `<pieces dir>/lod_<lv>_aligned_fitted/`, their `.clearance.json` and `fit/body_fit_aligned.json` (`source: aligned`; per level before / after, displacement incl. `median_moved_mm`, and a `compare_to_current` block: poke area and displacement next to the existing `fit/body_fit.json`); fresh outputs are reused unless `--force`. The existing `_fitted` files are never written by it.
* **Preview** (`tools/preview/serve.py` + `app.js`): the variants `aligned`, `aligned + fitted`, `aligned pieces (n)` and `aligned + fitted pieces (n)` appear in the Variant menu only when the files exist and are not older than what they were made from (aligned vs the wearable / pieces, aligned + fitted also vs the aligned file); the Body checkbox and the Clearance overlay work on them like on any module GLB. The "Red body" checkbox is described under "Red body overlay" below.
* **Red body overlay** (preview checkbox "Red body", 2026-10-25): compare the converted model's OWN body with the game base (the "Body" checkbox). `align_body.py` (a normal run, after it wrote `align.json`) and `align_body.py --bodies-only <module_dir>... [--jobs N] [--force]` (from an existing `fit/align.json`, no refit; skips fresh outputs, respects module locks) write, per level with a labelled `reduced/lod_error_<lv>.glb`: `reduced/lod_error_<lv>__tripo_body.glb` (the base-role faces as converted, native frame) and `reduced/lod_error_<lv>__tripo_body_aligned.glb` (the same faces deformed), plus `fit/tripo_body.json` (faces, anchor faces, colour note, mean / max displacement per level). The faces are the primitive of the labelled GLB whose material is named `base` (the red body AND the white anchors; taken from the GLB itself so a GLB / `_colors.npz` face-count mismatch does not matter); flat-shaded, red #E61923, the white-anchor faces #EDEDED when `glb_face_order` of the colours npz matches the GLB (same face count, every base face has material_id 0 there), else the whole body is red (15 of 822 levels). **Transform of the aligned overlay**: exactly the one the wearable got, `Field.from_record(fit/align.json, wearable=True)` (stage 1 without the per-axis scale in v2 + the stage-2 un-posing, baked through the ORIGINAL manifest / `parts.fit` like the wearable); the mirrored left copy of `right_gauntlet_boot` is not special-cased (the body faces are all deformed by the field). The preview offers the overlay only for the variants that do not contain the body (wearable, fitted, old fitted and their pieces use `__tripo_body`; aligned, aligned + fitted and their pieces use `__tripo_body_aligned`; full labelled and highpoly disable the checkbox) and only when the file is not older than the labelled GLB (and, for the aligned one, the aligned wearable): re-run `--bodies-only --force` after rewriting a labelled LOD or `align.json`. It is placed like the variant (the same `/api/on_body` matrix with Body on, native placement otherwise), drawn 80 % opaque with a polygon offset toward the camera so it wins over the game base where they coincide (where the Tripo body is deeper than the base the base shows), and is not markable, not exploded, not part of the clearance overlay.
* **Distortion**: the stage-1 per-axis scale is a deliberate global (non-rigid) deformation (p50 edge strain about 0.5 %); the un-posing alone is near rigid per limb: stage-2-only edge strain p50 0.03 %, p99 about 1.5 %, rare maxima 5-8 % at the pelvis / thigh blend zones (see `strain_stage2_only` per module). Dihedral angles of flat edges change by < 1 deg at p95. No remeshing, nothing closed or cut.
* **Measured** on `studded_leather_09_guardsman_studded_cuirass` + `breastplate_07_hand_me_down_cuirass` (all races, both modules, 44 modules): see `experiments/alignment_20261025/stage_results.md` (per module and per race), `aligned_sheet.png` (wearable, current fitted vs aligned + fitted over the grey base) and `aligned_bare_sheet.png` (the bare Tripo skin, current vs aligned).
* **Wearable stage 1 without the per-axis scale (default variant `v2`, since the first prototype run `v1` made the unfitted poke grow)**: on `body_armor` the unfitted poke area often GREW after the alignment (breastplate dwarf_female 1742 -> 4821 cm2, dwarf_male 1734 -> 4205, orc_female studded 3670 -> 5502; fit displacement median 13.3 -> 23.4 mm). Cause: stage 1's Y scale of 0.89-0.95 is fitted on limbs / head (body armour hides the torso) and, applied to the armour, compresses its depth onto the base torso, which the pipeline's whole-mesh ICP had already matched to the armour. So `v2` keeps the per-axis fit for the BARE evidence (measuring, stage 2, residual tables: identical to v1) but gives the wearable and the pieces `Field.wearable(WEAR_SCALE)`: stage 1 with rotation + translation and no scale (`WEAR_SCALE = 'none'`), then the same stage 2 / un-posing. The record keeps both: `stage1.scale` (per-axis, body evidence), `stage1.wearable_scale_mode` / `stage1.wearable_scale` (what the garment got); `Field.from_record(rec, body, rig, wearable=True)` rebuilds the garment's field (records without the key are v1: per-axis). A geometric-mean uniform scale was measured worse than none (dwarf_female poke 3130 vs 1619 cm2, human_male 976 vs 278: the garment frame is already at base scale), a uniform scale REFITTED on the body evidence is between the two. v1 (`--variant v1`) stays available; the first run's records are kept as `fit/align_v1.json`, `fit/body_fit_aligned_v1.json` and `experiments/alignment_20261025/stage_results_v1.*`. Numbers v1 vs v2: `stage_results.md` ("v1 vs v2" tables), `poke_variants.py`.
* **`--variant core` (experimental, off by default)**: stage 1 sees only bare head / neck / torso / pelvis (never limb skin or the hand / foot anchors); with less than 0.08 m2 of bare torso (body armour) it is a pinned translation (scale 0.985-1.015, rotation <= 1 deg), else per-axis scale 0.90-1.10 / rotation <= 3 deg with ridge priors; stage 2 adds a length scale along each bone (+-6 %) and a chain-root offset at the shoulders / hips (+-15 mm), both regularised. Measured on 8 modules (`core_first_eval.py`): the Y scale no longer fits limbs and the yaw of elf_male studded goes into the arm rotations, but the bare-skin residual is mostly equal or worse (halfling_female 5.9 -> 8.3 mm, dwarf_male 9.0 -> 11.2) and the un-posing strain is higher (p99 3-6.5 % vs 1-1.6 %), so it was not made the default.
* **Limits**: the field assumes the base's limb proportions: it moves and rotates, it does not scale limb lengths or thickness (dwarf / orc / gnome bodies keep 8-15 mm of shape residual); a gnome body armour's torso "bare" faces are unreliable evidence (stage 1 improves its mean residual but not its upper arms); right-hand gauntlet / boot bones are constrained by the garment proxy only and stay within 1-6 deg of rest (confidence low); the weights come from the posed base surface, so a wearable part far from every limb (a long cape) is carried by the nearest limb; nothing aligns the base spine / neck. `convert_job.py` runs it (and `body_fit.py --source aligned`) automatically after the split ("Align step" above; `--no-align` or `config.json` `align.enabled` false skips it); `--all` backfills older modules.

## Flipped faces (`fix_winding.py`, 2026-11-22)

Generated / reduced low-poly meshes occasionally contain a face wound against its neighbours, or a small closed piece that is inside-out.
With back-face culling (Godot) such a face is invisible from outside, i.e. a pin-hole; the review page's "inside colour" shows it red.
`convert_job.py` runs `fix_winding.py <module> --apply` after the align step (record `module_conversion.<race>/<module>.winding`, detail
`<module>/reduced/winding.json`, log `<module>/winding_step.log`; never fails the conversion). Per GLB (reduced/*.glb and the rigid pieces;
the red-body preview overlays are skipped) it welds the vertices, walks each edge-connected piece over its manifold edges, keeps the winding
of the larger part of the piece by area and turns the rest round; a closed piece with negative volume is turned round unless it lies inside
another part of the mesh (a cavity). A piece whose disagreeing part is over 20 % of its area is not changed but counted as
`pieces_needing_review`. Only the corner order of the flipped triangles changes (and normals of corners no other face uses are negated): face
and vertex order, colours, UVs and every sidecar array stay valid. The original of each changed GLB is kept once as `<name>.glb.prewinding`.

    python tools/tripo_pipeline/fix_winding.py <module dir | glb> ...       # report only
    python tools/tripo_pipeline/fix_winding.py <module dir> --apply         # fix
    python tools/tripo_pipeline/fix_winding.py --all [--race R] --apply     # backfill (skips modules a conversion worker holds)

Survey of 60 random modules (1576 GLBs): 19 GLBs affected, 9 faces wound against their neighbours, 10 inside-out slivers (~3 mm2), 10
inward-facing closed cavities correctly left alone. Not handled: a garment layer poking through another layer (a double-walled skirt's inner
wall showing through the outer wall is consistently wound and harmless with culling) and geometric fold-overs.
