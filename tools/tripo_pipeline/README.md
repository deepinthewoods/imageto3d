# Front concepts → four views → Tripo Studio → low-poly materials

This is the current parent-project workflow. The user chose the **studio plain paper** source-image look and local cleanup plus geometry reduction at **0.4% of body height** as the default. Also retain **0.2% and 0.1%** variants so a reviewer can switch when a garment or armor panel needs more detail. None of these settings asks for a polygon count. On the reference character the results were 436, 626 and 1,352 triangles, with about 0.45–0.49 seconds of simplification and about 0.17–0.19 seconds of measurement/export per variant after shared preparation. New assets will have different counts and times.

The selected reference and decision record are at `pipeline_decisions.json`; the eight-scene comparison and metrics are under `../../experiments/tripo_method_gallery_01/`. Studio's original reference model version is unknown. New submissions use confirmed H3.0, 2K texture, PBR off, Remove Lighting on, and **Triangle by default**; `config.json` records those choices.

## Folder states

```text
concepts/<batch_id>/<NN>_<slug>__<module>.png + <NN>_<slug>.json   (flat batch for browsing; no rejected attempts kept)
              │ workflow.py promote concepts/<batch_id> <NN> [--set <set>] [--race <r>] [--approve]
              ▼   (copies the chosen concept; never overwrites; --approve = straight to approved/ when the user said so)
concepts/<set>/<race_gender>/{body_armor,right_gauntlet_boot}_front.png   (per-set layout, side by side)
concepts/<set>/<race_gender>/outfit_front.png
              │ user moves a complete chosen set
              ▼
approved/<set>/... same flat <module>_front.png layout
              │ chat request: process approved outfits
              ▼
processing_views/<set>--<job-id>/<race_gender>/<module>/ front.png + generated other views
              │ (claim unflattens the fronts; notes/rejects go to <race_gender>/.concept_notes/)
              │ all four views verified per module
              ▼
multiview_ready/<set>--<job-id>/... four views + frozen hashes
              │ Firefox Playwright submit/collect; queue watcher pending
              ▼
processing/<set>--<job-id>/... website conversion in progress
              │ Tripo GLB + 0.4/0.2/0.1% low-poly GLBs + flat material review
              ├── models/<set>/<job-id>/<race_gender>/<module>/...
              └── completed/<set>--<job-id>/... images, prompts, job record
```

An armor set has **both** `body_armor` and `right_gauntlet_boot` fronts for each character. A regular outfit has one `outfit` front. They are separate jobs/set types; do not combine them into a single image. The outfit leaves head, both hands and anatomical left foot bare. Headwear and hoods await a later decision. Use large, matte garment color regions (up to four: primary green, secondary blue, tertiary yellow, accent magenta; never white) plus the unchanged exposed base so the generated texture can later be assigned to engine materials.

Concept generation produces fronts in `concepts/`; it does not move anything to `approved/`. The user approves by moving the whole set. The assistant processes approved sets when asked in chat. It preserves each selected front, generates the three other views from corresponding base views, checks all images, and stages the completed set with `workflow.py ready`. The active base views (all races) are native 1254 × 1254 studio-plain semantic-marker renders with the `white_anchor_v2` palette: red body and ONE shared white anchor on the head, anatomical-left hand and anatomical-left foot (the former yellow/magenta/cyan anchors, scheme `tricolor_v1`, are archived at `archive/base_views_markers_tricolor_20261022/`). The prior 1024 set is archived at `archive/base_views_studio_plain_markers_1024_20261021/human_male/`. The old brown views and other races are archived at `archive/base_views_kraft_20261021/`; since 2026-10-22 all eleven races have matching active marker views (`build_marker_base.py` + `render_marker_base.py`). The user chose conversion to run automatically after the four views exist, without a second review stop. `studio.mjs` now provides reusable Firefox Playwright submission and collection for a four-view module. It is not yet connected to a background queue watcher; `multiview_ready/` jobs remain staged until that connection and its recovery rules are tested. The approved arcane plate mail job has not yet been uploaded.

Past Pixal3D results remain in `models/` and `completed/`. The Pixal3D user service was disabled and stopped before this contract was installed. Do not reactivate it while `approved/` has front-only Tripo selections.

## Validator and staging commands

From the parent project directory:

```bash
python3 tools/tripo_pipeline/workflow.py status
python3 tools/tripo_pipeline/workflow.py check approved/<set>
python3 tools/tripo_pipeline/workflow.py promote concepts/<batch_id> <NN> [--set <set>] [--approve]   # batch concept -> per-set layout
python3 tools/tripo_pipeline/workflow.py claim <set>
# Generate the three other views for each module in processing_views/<set>--<job-id>/.
python3 tools/tripo_pipeline/workflow.py ready <set>--<job-id>
# Convert: moves the job to processing/, then per module Tripo submit -> collect -> reduce.
python3 tools/tripo_pipeline/convert_job.py <set>--<job-id>            # --dry-run: fill Studio's form only
```

Before generating or staging views run `python3 tools/check_framing.py <base view> <image...>` (palette-aware: white-anchor blobs or legacy hue markers, see `PROMPTING_GUIDE.md`) and open every imagegen prompt with `python3 tools/framing_lock.py <base view>`; both read `palette.json` beside the base view. `tools/test_check_framing.py` checks all 44 active base views against themselves.

**Optional backend:** `convert_job.py <job> --backend hyper3d` swaps the Tripo submit/collect for Hyper3D Rodin (high-poly textured GLB, no Smart Low-poly, credit-guarded, no free-retry loop); Tripo stays the default and is unchanged. Setup, flags and what is still unverified: `../hyper3d_pipeline/README.md`.

`convert_job.py` runs modules strictly one at a time (Studio greys out Generate while another model of the account is generating; `studio.mjs` waits up to `TRIPO_QUEUE_WAIT_MIN`, default 30). Collection polls until Studio shows the finished model (`TRIPO_COLLECT_WAIT_MIN`, default 30) and retries a blocked export click. It is resumable: a module with a submission record is only collected, a reduced module is skipped. It leaves the job in `processing/` with state `converted` and lists the levels needing review; move it to `completed/` after that review.

**Split step (2026-10-22).** After the reduction a `piece_colours` `body_armor` module (job records say so, or `--piece-colours`) is cut into rigid pieces by **segment-first** (section "Segment first, simplify second" below): `segment_first_prep.py` in Blender -> `<module>/segment_first/prep/` (skipped when `prep.npz` exists), then `segment_first.py` with the venv python (numpy + scipy + Pillow: `$SEGMENT_FIRST_PYTHON`, else `config.json` `segment_first.venv_python`, else `<imageto3d>/../.venv/bin/python`; a clear message when none exists) -> `<module>/segment_first/{levels,pieces,segment_first.json}` (skipped when `pieces/pieces.json` exists). Cameras, regions and palette are the ones `reduced/manifest.json` records, so prep sees exactly what `reduce_model.py` saw (the palette is frozen as `segment_first/palette_used.json`). Logs: `segment_first/prep.log`, `segment_first/segment_first.log`. If segment-first fails for any reason the step falls back to `split_pieces.py <module>/reduced --rigid auto` (output `<module>/pieces/`, log `pieces_per_face.log`), prints a WARNING and records why; the split step never fails the conversion. `--split-method segment-first|per-face|none` overrides the choice (default segment-first for `piece_colours` `body_armor`, `none` for every other job; joint-band separable jobs are not split by `convert_job.py`, run `split_pieces.py --rigid bands` by hand). The method used is recorded in `.tripo-job.json` `module_conversion.<race>/<module>.split` (`requested`, `method`, `status` done|fallback|failed|skipped, `outputs`, `fallback_reason`) and in `<module>/split_step.json`.

**Redo a bad Tripo result with a free retry first.** Every Studio project offers "Free Retry (×3)": it regenerates from the same inputs and settings without charging credits (verified 2026-10-22: balance unchanged, counter 3 → 2; the previous version stays in the project's model history). `node tools/tripo_pipeline/studio.mjs retry <previous_output_dir> <new_output_dir>` clicks it (the click starts the retry immediately, no confirmation; `TRIPO_DRY_RUN=1` only reads the counter) and writes a submission record that `studio.mjs collect <new_output_dir>` then fetches; collect waits while the retry is still generating. Keep the failed attempt beside the module (e.g. `<module>_attempt01_<reason>/`), put the retry in the module folder, and reduce it. `convert_job.py` does this automatically for a broken mesh (currently a doubled interior shell): it keeps each failed attempt as `<module>_attemptNN_interior_shell/` and retries until the mesh is clean. When all three free retries are used it does **not** pay for another generation: the last attempt stays as the module output, the module is flagged `free_retries_exhausted` / `needs_manual_review` in `.tripo-job.json`, the job state becomes `converted_with_errors`, and the script prints an ERROR line and exits 1. A paid resubmission is a manual decision after looking at why every attempt failed.

The validator requires matching native base and generated-view dimensions, nonempty RGBA with transparency, and either both armor modules or one outfit module. Newly approved sets use active `base_views/<race_gender>/`; claiming freezes all four base views (plus transforms/regions/parts/clearance/**palette.json**) in the job’s hidden `.base_views/<race_gender>/` snapshot. `claim` first checks which base the approved fronts were drawn on: the share of the base's bare-anchor pixels that are still anchor-coloured in each concept front (`workflow.anchor_match`, threshold 0.5). A front made on the old tricolor base is therefore snapshotted with `archive/base_views_markers_tricolor_20261022/<race>/` (an archived set is eligible only when it carries a `palette.json`), never with the white base; several different matching archives, or a front matching nothing, is an error (fail closed). `claim <set> --base-views <folder of race bases>` overrides the detection. The job record keeps `base_view_sources` (path, scheme, scores). Ready/staged jobs validate against that snapshot, so a later active-base resolution change cannot invalidate an older set. It rejects symlinks and extra/missing PNG views. Claiming records SHA-256 hashes of user-approved fronts. Staging verifies those hashes again and writes hashes for all four views before the folder move. The tool never generates images, invokes Tripo or marks a job completed. Preserve prompt/color records alongside the images. Do not edit an active/frozen job behind the worker's back.

## Conversion and material contract

The planned queue worker will use one Tripo multi-image conversion for each `race_gender/module`, with the tested H3.0, no-PBR, 2K texture and Triangle settings. Export the original high-poly GLB unchanged. Apply the same local-cleanup + geometry-error reduction at 0.4%, 0.2% and 0.1% of normalized body height and keep all three. Audit boundaries, non-manifold edges, winding, duplicate/degenerate faces, significant components, and geometric/silhouette changes. Flag any failed option for manual review rather than silently selecting it. Do not force an alternative algorithm merely because an asset has more detail; first inspect the finer 0.2%/0.1% outputs. Normal-aware reduction remains an experiment because it introduced odd arm geometry on the reference.

Then label each reduced face from the original texture (`face_labels.py`, 2026-10-21):

- **Palette** (`palette.py`, `palette.json` beside the base views, copied into job snapshots): `white_anchor_v2` = red body + one achromatic anchor #EDEDED (head, left hand, left foot) + garments primary green #19D228, secondary blue #1E41EB, tertiary yellow #F5DC14, accent magenta #E119DC; legacy `tricolor_v1` = red body + yellow/magenta/cyan hue anchors + green, blue. Class 0 is `base` (body and every anchor), classes 1..K the garments in palette order (K = 2 or 4), K+1 unusable. A base, snapshot or swatches file without `palette.json` is legacy `tricolor_v1` and labels exactly as before (verified: re-reduction of the plain plate mail modules is face-for-face identical). Achromatic anchors: a sample is anchor (class 0) when saturation < 0.25 and value > 0.45 (weight fades in from value 0.45-0.6 and out from saturation 0.15-0.25); the red bounce light on the red surfaces next to the white anchors stays saturation >= 0.25 and is still base by hue. The garment materials are named by role (`primary`, `secondary`, `tertiary`, `accent`) in the review/wearable/high-poly blends, then `uncertain` (orange) and, in `highpoly_detected` only, `off_body`.
- **Hue, not chromaticity distance.** Each texture sample takes the nearest swatch hue within 20°. The earlier r:g:b-ratio distance rejected Tripo's body red for being *more* saturated than the swatch (0.131 vs a 0.13 cutoff), which produced the orange patches on bare torsos and most "uncertain" counts. Averaging a face was dropped too: green+blue straddles average to teal and read as cyan.
- **Sample weight** ramps with saturation (0.2→0.45) and brightness (0.08→0.25), so murky pixels count little and grey/black ones nothing.
- **Visibility.** With `--cameras` (the `transforms.json` the concept views were made with) and `--regions`, every high-poly face gets its best unoccluded view angle; texture on unseen surfaces counts 5% (Tripo invented it). Note that the diagonal views do see the spread inner legs at a steep angle, so visibility alone does not fix inner-leg bleed.
- **Module prior** (`--module`): soft base/wear bias from body zones. `body_armor`: forearms, lower legs and head lean base. `right_gauntlet_boot`: right forearm and right lower leg lean wear, right thigh stays possible (tall boots), everything else leans base. `outfit`: head, hands and left foot lean base. Clear visible texture can override it. The zones (forearm = `forearm_stretch.*` + `hand.*`, hand = `hand.*`, head = `head.x`, lower leg = `leg_stretch.*` + `foot.*`, thigh = `thigh_stretch.*`, right = `.r` parts, left foot = `foot.l`) come from the **body parts** below when a `parts.npz` exists, so A-posed orcs and the legless gnome work; without one they fall back to the T-pose landmarks of `regions.json` (`face_labels.landmark_zones`), which are wrong for those bases. The module formulas are the same either way.
- **Body parts.** Every marker base scene (`assets/marker_bases/<race>.blend`, `build_marker_base.py`) carries a FACE attribute `body_part` (names in the mesh property `body_part_names`: `head.x`, `hand.l`, `forearm_stretch.r`, `spine_01.x`, ...). `base_parts.py` writes it with the vertices in the normalized frame to `base_views/<race>/parts.npz` (`blender -b --python tools/tripo_pipeline/base_parts.py -- <marker_scene.blend> <out parts.npz>`; `human_male` uses `assets/marker_bases/human_male.blend`, vertex-identical to the frozen render scene). `reduce_model.py` finds `parts.npz` next to the resolved `regions.json` (job snapshot first, then `base_views/<race>/`; `--parts` overrides, `--no-parts` disables). Transfer: (1) trimmed ICP of the base onto the high-poly mesh with uniform scale + translation only (15 iterations, closest 70% of correspondences in both directions; identity is kept when no iterate improves the residual), because armour bulk shifts the mesh's bounding-box normalization; (2) each face takes the part of the nearest base surface (centroid plus three corner points for low-poly levels), with a flipped normal costing 0.04 of extra distance; (3) cleanup merges isolated faces and small islands into the neighbouring part they share most edges with. Left/right is never mirrored. The prior's zones use a distance-weighted vote of base surface samples within 0.07 (height 2) of each face, so the boundaries stay soft. The fit (scale, translation, trimmed residual before/after, in % of height) and the parts file's hash are recorded in `manifest.json` under `parts`; per level `body_parts` lists the part area shares of the full and wearable meshes. Every reduced level in `review.blend`, `wearable.blend` and the high-poly objects in `highpoly.blend` carry the FACE int attribute `body_part` (+ mesh property `body_part_names`); `review.blend` also has one `<level>_parts` object per level (one colour per part, placed below the level) and `highpoly.blend` a `highpoly_parts` object. GLB files cannot hold face attributes: each level's `_colors.npz` has `body_part` (review mesh face order), `body_part_names`, and the parts in each GLB's face order (`body_part_glb_order` for the full GLB, `wearable_body_part_glb_order` for the wearable GLB; the GLB exporter groups faces by material slot, stable, so `glb_face_order` / `wearable_face_order` give the review-mesh index of GLB face `i`).
- **Off-body faces cannot be base.** Tripo bakes the body's red onto thin armour-edge slivers (the hems of cuisses at the knees), and hue alone calls them base. A face that reaches clearly **outside the fitted base body** is not bare skin: `face_labels.off_body_excess` takes the largest signed distance over a face's corners and centroid to the ICP-fitted base surface and compares it with a per-part threshold = the p99.9 of the same part on the **bare** Tripo mesh of that race (`base_clearance.py`, stored as `base_views/<race>/clearance.json`, copied into job snapshots by `claim`) + 0.02 (1% of height; never below 0.03); the base role then loses score (up to 3, more than clear texture, ramping over a further 0.02) and the face takes primary/secondary from its other texture votes, mirror face or neighbours. The rule only applies where the module prior is at least 0.4, so head, hands, feet, forearms and lower legs of `body_armor` (and everything but the right limbs of `right_gauntlet_boot`) stay base however far Tripo's reconstruction strays from the marker base. It needs a module and a parts file; without a `clearance.json` it is off (`human_male` has none until it gets a bare Tripo base, so neither off-body rule runs for it). Flipped faces get the label source `off_body` (`label_source`, `_colors.npz`, manifest `material.off_body`); `highpoly.blend` marks such high-poly faces magenta (`off_body`). A second, conservative **hem riser** rule (`face_labels.hem_risers`, label source `riser`) handles slivers flush with the skin: a base face that shares an edge with a wear face, lies where the prior is at least 0.4, and whose normal differs from the nearest base normal by more than 60 degrees (it faces along the limb, not out of it) takes the neighbouring wear role, at most 2 rings deep. Limits: a flush sliver that still faces outward is not caught; Tripo reconstructions of the same character differ in pose, which is why the thresholds are per part and not one number.
- **Mirroring one-sided wear (wearable only).** The concepts keep the anatomical-left hand and foot bare as alignment anchors, so the wearable would carry a shoe/gauntlet on the right only. `face_labels.mirror_wear` (called by `reduce_model.py` per level, after labelling) copies the right-side wear faces whose mirror position on the left is bare base onto the left: the parts come from `config.json` `mirror_to_anchor_side` (default `outfit`: foot, `right_gauntlet_boot`: hand + foot, `body_armor`: none; `--mirror foot,hand|off` overrides per run; foot = `foot.r` + `leg_stretch.r`, hand = `hand.r` + `forearm_stretch.r`). Mirror plane = sagittal plane of the base (mean x of its `.l` and `.r` part samples) mapped through the ICP fit (scale + translation, normal stays X); the manifest `mirror` records it with the base symmetry (reflected right samples vs the base surface: all 11 races measure p95 <= 0.4% of height with >= 98% landing on the matching left part; a base that fails the check (share < 0.8, p95 > 2% of height or right not -X) is not mirrored and the reason is recorded). Candidates: wear faces (any garment role) on those parts where the module prior allows wear (>= 0.4), skipped when a wear face lies within 0.05 (2.5% of height) of the mirrored centroid on the labelled mesh (a robe hem on both shins is not duplicated), patches under 3 faces dropped, then grown over 2 rings into neighbouring right-side wear faces that are not worn on the left. Copies are reflected vertices with reversed winding (normals face out), the same material/garment role, the left counterpart `body_part`, label source `mirrored` and the FACE attribute `mirrored` (`wearable.blend`; the npz has `wearable_mirrored_glb_order`, `wearable_label_source_glb_order`, `mirror_source_face`, `mirror_left_part`, `mirror_plane_x`, and `wearable_face_order` = -1 for copies). The full labelled level, review.blend and every label array are unchanged; only the wearable GLB/blend, `wearable_triangles`, and the `wearable_*` arrays grow. Measured 2026-10-22 at 0.4%: Tripo robe 57 faces copied (2.5% of area; 202 shin/hem faces skipped because the left already had them), Hyper3D robe 38 (1.9%), plate-mail `right_gauntlet_boot` 186 (18%; 93% of its wear), `body_armor` none.
- **Resolution.** Weighted votes + prior + mirror face (body armour only) + crease-aware neighbours, iterated; each face records its deciding source (`label_source` face attribute and `_colors.npz`). A level is flagged when more than 20% of its area was decided by prior/neighbours. The prior only says garment-or-base, so a wear face nothing else decides (unseen, no decided neighbours) takes the **garment with the most seen area on that mesh** (`default_garment` in the manifest's `material`; a 1e-6 tie bonus, so texture/symmetry/neighbour evidence always wins); legacy `tricolor_v1` keeps `primary`, as the old tie-break did. `manifest.json` records the `palette` (scheme, hexes, source), `material.palette_scheme/garment_roles/default_garment`, and each `_colors.npz` has `palette_scheme`, `palette_garment_roles`, `palette_garment_hex`. Known and unchanged: `material.uncertain_faces` is always 0 (no face ever gets the uncertain class in this mode), so the `uncertain_share > 10%` review trigger cannot fire; fixing it would alter the review flag of already converted legacy modules, so it was left (`no_texture_evidence_faces` is reported instead, informational).

With the standard `models/<set>/<job-id>/<race>/<module>/source.glb` layout no flags are needed: the module comes from the folder name, the palette from `--palette`, else `swatches.json` beside the source (legacy), else the job's frozen `.base_views/<race>/palette.json` (a snapshot without one is legacy `tricolor_v1` even after the active base was recoloured), else `palette.json` of the folder the regions come from (for a source outside `models/`, the folder of `--regions`, else `base_views/<race>/`), else legacy defaults from `config.json`'s `marker_palette_srgb`; regions (and `parts.npz` beside them) from the job snapshot or `base_views/<race>/regions.json`, and cameras from the job's frozen `.base_views/<race>/transforms.json` (`workflow.py claim` freezes it). For jobs claimed before that, the cameras come from whichever active/archived base set has the same three-quarter view hashes as the job's frozen images. The manifest records each choice under `input_sources`. The repaired source mesh is put into a canonical order before reduction, so runs are reproducible. `base_regions.py` measures `regions.json` for a marker base (`base_views/human_male/regions.json` from `assets/studio_plain_input.blend`). Use semantic roles `base` and the palette's garment roles only where the source colors make that assignment reliable; keep `uncertain` visible for review. Red body and every anchor (white head/left hand/left foot; legacy yellow/magenta/cyan) classify as `base` for removal; yellow `tertiary` and magenta `accent` garment faces are kept in the wearable. Preserve the original texture, per-face evidence, source GLB, each low-poly option and materials in `models/`. The reducer reuses area-weighted texture sampling from `../lowpoly/polygon_materials05.py` and reads the palette described above (`polygon_materials05.py`'s own 6-colour PALETTE is stale and not used here).

**Interior (enclosed) surface.** Some Tripo exports contain a second, inward-facing copy of the body welded to the outer skin (the first elf_female `right_gauntlet_boot` attempt: 42% of its area enclosed, 31 components, two layers in wireframe, 2,460 triangles at 0.4% vs ~740 for a clean module). `reduce_model.py` audits every source: it casts 14 rays over the outward hemisphere of each of 5,000 area-weighted faces (first ray along the normal, none flatter than 20°) and counts a face as enclosed when none escapes the mesh, which concavities (inner thighs, armpits) do not trigger. The manifest `interior` block holds `interior_area_share` (all rays blocked), `interior_area_share_loose` (at most one escapes), `normal_blocked_share` (the simple normal-ray test) and the median gap. Calibration over 30 sources (2026-10-22): bare bases 0.000-0.005, plate-mail modules 0.0002-0.044, the double-shell source 0.415, so `INTERIOR_THRESHOLD` is 0.15. `--interior auto` (default) strips the enclosed faces from the welded working mesh before reduction when the share is above the threshold (the source GLB is never changed; the removed faces are kept in `interior_removed.npz`, the texture lookup ignores them too) and marks every level for review with the reason in `source_review_reasons`; `--interior strip` always strips, `--interior flag` only measures and flags. Stripping a fold leaves open edges where the outer layer continued into the inner one, so check boundary edges after a strip.

The reusable three-level Blender processor is now `reduce_model.py`. It was run on the selected studio plain paper GLB and reproduced the 436 / 626 / 1,352 triangle results with mesh checks passing. It preserves an exact imported backup, exports three native-coordinate full-model GLBs with flat face materials, stores sampled face-color evidence, and saves an editable `review.blend`. With recorded swatches, it also removes all `base` marker faces **after** classification and exports a `__wearable.glb` at each level; these intentionally open garment surfaces need fitting review. Its no-swatch fallback uses neutral `COLOR_00/01/02` labels and cannot safely remove the body. For production the palette comes from the base (`--palette <palette.json|base dir>` overrides it). The legacy `swatches` form still works, e.g. `{"base":"#E61923","base_markers":{"head":"#F5DC14","left_hand":"#E119DC","left_foot":"#14DCEB"},"primary":"#19D228","secondary":"#1E41EB"}`, as a second positional argument or beside the source; it means legacy `tricolor_v1`. The original three-color swatch form still works for older inputs. Example:

```bash
/usr/local/bin/blender -b -t 6 --python tools/tripo_pipeline/reduce_model.py -- \
  models/<set>/<job-id>/<race_gender>/<module>/source.glb \
  models/<set>/<job-id>/<race_gender>/<module>/reduced \
  [swatches.json] [--cameras transforms.json --regions regions.json --module <module> --parts parts.npz --palette palette.json --interior auto|strip|flag]
```

Each run also writes `reduced/wearable.blend` (the three `__wearable` levels side by side, base and anchors removed, one-sided wear mirrored onto the bare left side (see Mirroring), with the garment-role (primary, secondary, tertiary, accent)/uncertain face materials). `make_wearable_blend.py -- <reduced_dir>` rebuilds it from existing wearable GLBs. With swatches it also writes `highpoly.blend` beside the source GLB: the full Tripo mesh twice, `highpoly_detected` (each triangle's material detected from the texture at its UV centre, orange = uncertain) and `highpoly_textured` (original texture, packed); `make_highpoly_blend.py -- <source.glb> <swatches.json>` backfills it and never overwrites. The output directory must be empty to protect earlier attempts. The processor currently expects one textured mesh with direct base-color UV texture; it stops with a clear error for an unfamiliar Tripo export. It records material review status when swatches are absent, more than 10% of faces are uncertain, texture projection is too far from the original surface, or no confidently labeled primary/secondary faces remain. A bare-base sample with the four-marker palette correctly produced no confident wearable faces and was flagged for review. Color-role thresholds, body removal and fit on genuinely new outfit textures still need visual validation before automatic completion. Automatic queue invocation of the browser script and processor is the remaining integration step.

## Splitting body armour into rigid pieces (pauldrons)

`split_pieces.py` cuts a reduced `body_armor` **wearable** into three independent meshes by face colour label: `pauldron_l` (anatomical left, +X), `pauldron_r` (-X) and `rest`. Plain python3 (numpy + Pillow); the `.blend` step starts Blender itself (or runs in-process under `blender -b --python`). Faces are only split, never closed, remeshed or moved; the pieces share no vertices.

```bash
python3 tools/tripo_pipeline/split_pieces.py models/<set>/<job>/<race>/body_armor/reduced [--style roles|rim] [--levels 0p4,0p2] \
  [--output-dir DIR] [--roles accent,tertiary] [--region-parts shoulder,arm_stretch] [--seed-in-region] [--min-island 6] \
  [--close-rings 1] [--max-field-share 0.2] [--plane-x X] [--no-blend] [--no-render]
python3 -m unittest tools/tripo_pipeline/test_split_pieces.py   # synthetic armour + the plate-mail orc_male, ~3 s
```

Defaults come from `config.json` `piece_split[<module>]` (module from the manifest / folder name). Output goes to `<reduced>/../pieces/` (refuses to overwrite; use `--output-dir` for experiments): per level `lod_<lv>/{pauldron_l,pauldron_r,rest}.glb` (materials/roles kept), `pieces_<lv>.blend` (three named objects, object colour per piece), `pieces_render.png` (front, back, exploded: pauldrons offset 15% of height outward, flat colours L orange / R blue / rest grey), `faces.npz` (per wearable face: piece, side, role, body part, flag bits), plus one `pieces.json` (per piece: faces, area, area share, connected components, bbox, centroid; `symmetry`: plane, L/R area ratio, centroid mirror error in % of height, share of each side's faces that have a mirror twin within 2.5% of height; `absorbed_islands`, `stray_seed_components`, `rim_fields` (every candidate with its accept/reject reason), `ambiguous_faces` (side conflict, centreline, weak label source prior/neighbours, changed by clean-up), `warnings`).

- **roles style** (`S6`, 2+2): pauldron = faces whose garment role is in `roles` (`tertiary`, `accent`); the rest of the armour only has primary/secondary.
- **rim style** (`S4`, `S2`): pauldron = the `accent` rim plus the wear faces it encloses, i.e. connected components (shared edges, welded vertices) of the non-accent wear faces that are not connected to the main body (largest component). A rim with a gap leaks, so a second pass erodes the non-accent faces `close_rings` rings away from the rim, finds the cores that separate from the main body, and floods the eroded faces back to the nearest core. A candidate field must have at least `min_region_share` of its area on the shoulder/upper-arm parts, at most `max_field_share` of the wear area, and `min_enclosure` of its perimeter against rim faces; rejected candidates are listed with the reason. A side with no field faces gets a warning (closed ring missing).
- **both**: a seed component mostly outside `region_parts` (`shoulder`, `arm_stretch`, names without `.l/.r`) stays in `rest` (a stray speck is not a pauldron). Sides come from the body part suffix, `.x`/unknown from the sagittal plane (manifest mirror plane, else the base `parts.npz` x mapped through the manifest ICP fit, else the mid of the wearable's `.l`/`.r` faces; all candidates are recorded). Islands under `min_island_faces` go to the neighbouring piece with most shared edges (a 2-face hole inside a pauldron joins it, a speck in the region joins rest), a detached second patch of a pauldron under `extra_component_share` of its main patch goes to rest; each is listed in `absorbed_islands`. More than one remaining patch per pauldron is a warning.
- Body parts of the wearable faces come from the full GLB (`body_part_glb_order`, matched by face **centroid**, since some wearable GLBs have a different face count than the npz `wearable_*` arrays; `body_parts.wearable_array_agreement` reports how often the two agree). Garment roles come from the wearable GLB material names. Without an npz or parts the region test is skipped (warning) and sides use the plane only. GLB frame: X lateral (right = -X), Y up, front +Z.
- Legacy two-colour plate mail has no pauldron colours; as a test use `--roles secondary --seed-in-region` (secondary faces on the shoulder/upper-arm parts). The `human_male` plate-mail reduction predates body parts (no `body_part` in its npz); use e.g. `orc_male`. Dev outputs: `experiments/pauldron_pipeline_20261022/split_dev/`.

### Rigid sections for plate mail (torso / arms / pauldrons), overlap and pose test

`split_pieces.py --rigid zones|snap` additionally cuts everything that is not a pauldron into `torso` (chest, back, upper legs: one piece), `arm_l` and `arm_r` (upper-arm plates down to the elbow edge; `config.json` `piece_split.body_armor.rigid`). Default behaviour (no `--rigid`) is unchanged. Extra output per level: `pose_render.png` (with `--pose-test`) and `rigid` in `pieces.json` (cuts, snap stats, overlap strips, pose metrics); `faces.npz` gets `<piece>__overlap` (per face in GLB order) and the `.blend` objects the FACE int attribute `overlap`.

```bash
python3 tools/tripo_pipeline/split_pieces.py <reduced> --style rim --rigid snap --overlap --pose-test --output-dir <new dir>
python3 tools/tripo_pipeline/compare_rigid.py out.jpg S6=<reduced>:roles S4=<reduced>:rim   # M1 vs M2 + posed sheet (<= 2400 px wide)
```

- **M1 `zones`**: pauldrons first (roles/rim logic), then every other face on the `arm_stretch`/`forearm_stretch`/`hand` body parts (`rigid.arm_parts`, side from the `.l/.r` suffix) is the arm of that side, the rest is torso. Without body parts the arm is everything lateral of the shoulder joint. Islands under `min_island_faces` and detached patches (arm patches under `extra_component_share` of the main patch go to torso, every detached torso patch joins its neighbour) are cleaned up, so each piece is one patch where the mesh allows it (otherwise a warning).
- **M2 `snap`**: M1 is the first guess, then per side the torso/arm boundary is re-cut inside a band of +-`snap.band` (8% of height) around the guess by a minimum cut (own Dinic max-flow, no scipy). Terminals = torso and arm faces outside the band; edge cost = edge length x 0.15 on a colour/label boundary x 1/(1+(dihedral/30 deg)^2) on creases (floor 0.03); a weak pull (`snap.prior`) holds free faces to their zone label, growing with distance from the guess. It keeps open-mesh boundaries (armpit holes) as free cut ends and is skipped for a side with nothing to cut. Cut length, share on colour edges, share on creases and the snap cost are in `rigid.cuts` (M1 values in `cuts_zone_guess`).
- **M3 `seam`** (`--rigid seam [--soft piece|nearest]`): the soft under-layer (`rigid.seam.soft_roles`, secondary/blue) separates rigid plates. Rigid plates = connected components of the other wear faces; each goes wholly to the arm or torso by area-weighted body-part majority (a plate with more than `mixed_share` on the minority side is split by body-part zone). Only blue components with at least `soft_min_arm_share` (25%) of their area on the arm parts count as the shoulder/arm band; other blue (hip cloth) stays rigid (a band joined to other blue regions loses that share, so the concept must keep the band blue-only). `--soft piece` = separate piece `soft` (label 5, to be skinned smoothly; the pose test blends it by inverse-squared distance to the rigid pieces and reports `soft_stretch_max`), `--soft nearest` = each blue face joins the nearest rigid piece by rings (the cut then runs through the middle of the band, no colour edge). Cuts to the soft piece never get strips.
- **M4 `colour`** (`--rigid colour`): the arm plates carry their own garment role (`rigid.colour.roles`, default `quinary` = cyan #14DCEB, palette `experiments/rigid_sections_20261022/palette_cyan5.json`, reduce with `--palette`): arm = those faces plus the wear faces they enclose (same erosion/flood rim logic as the pauldron, `colour.close_rings/max_field_share/min_enclosure`), restricted to the arm body parts (a stray cyan speck stays torso, listed in `rigid.colour.stray_components`). Errors out when the wearable has no such role.
- **Overlap** (`--overlap`, `rigid.overlap`; **off by default since 2026-10-22**: the yellow strips made the visual review hard to read, `rigid.overlap.enabled` is `false`, `--no-overlap` is kept as a no-op; `--pose-test` then only measures the no-strip variants and `pose_render.png` has no strip columns): at every cut between two pieces that move relative to each other one strip is added: the cut loop is stepped `length` (6% of height by default, was 3%) along the other piece's surface, projected back onto it, sunk `offset` (0.4%) below it along its outward normals, one quad per cut edge (2 triangles), attached to the owner's own cut vertices with the material of the adjacent owner face, face attribute `overlap`. **Owner modes (`--overlap-mode`; default `both` since 2026-10-22, config `rigid.overlap.mode`)**: `parent` (the cheaper option, about half the strip faces): the piece that moves less owns the strip and tucks it under the piece that moves more (the strip stays where the mover was and fills the opening); `child`: the mover owns it and tucks it under the static piece; `both`: both pieces own one (a gap sample counts as closed when either bridges it; doubles the strip faces); `cover` (inner piece by `cover_order` tucks under the outer one) is kept for comparison: a strip that rotates with the moving piece cannot fill a hinge opening unless it is longer than the cut's distance from the pivot, and measured worse. **Pauldron convention (`--pauldron-convention`, `pose.convention`)**: `half` (default since 2026-10-22: a clavicle/shoulder parent that turns half the arm angle about the same pivot), `arm` (pauldron follows the arm), `torso`; the old cheaper combination is `--pauldron-convention arm --overlap-mode parent --overlap-length 0.03`. Strip owners follow the motion hierarchy `piece_depth`/`piece_body` (pelvis < chest, thigh < arm, pauldron by convention).
- **Pose test** (`--pose-test`): rigid rotation about the shoulder joint (centre of the arm_stretch ring shared with the torso part, from `parts.npz` mapped through the manifest ICP fit into the GLB frame; `--joint-l/--joint-r x,y,z` override) around the frontal axis, arms down 45 deg and up 30 deg, pauldrons following the arm or the torso, with and without strips. Metrics per cut (`rigid.pose.variants`): `separation` = plain motion of the cut, `gap` = distance of the boundary points of the piece the strip tucks under (cut vertices and edge midpoints, in their own pose) to the strip owner's posed surface including its strip; `gap_max`/`gap_mean` in % of height. `pose_render.png`: rows = pauldron follows arm / torso, columns = down/up x without/with strips (yellow).
- **Measured, M1 vs M2** (0p4; outputs `experiments/pauldron_pipeline_20261022/*/pieces_rigid_m1|m2/`, sheet `experiments/rigid_sections_20261022/compare_m1_m2.jpg`, numbers `compare_m1_m2.jpg.json`): M2 lowers the torso|arm snap cost 5-8x on S6/S2 (S6 cut on colour edges 61/41% -> 82/100%, cut 22.6/25.5 -> 19.8/21.1% of height) and equals M1 on S4, where the part boundary already lies on a colour edge. Strips (parent, 3%) cut the mean gap for arms up 30 deg by 28-61% and for arms down 45 deg by 1-35%; the max gap (4.6-7.2% of height down, 2.5-3.3% up) is the pauldron|torso opening.
- **Measured, M3/M4** (outputs `experiments/rigid_sections_20261022/<concept>/pieces_rigid_<method>/`, sheets `compare_m3_m4.jpg` and `compare_m3_m4_pose.jpg`): see the report in the task log; the numbers are in `compare_m3_m4.jpg.json`.
- **Closing the arms-down pauldron|torso gap** (45 deg; max/mean gap in % of height, no strips -> strips; gap scan over S6/S4/S2/M3/M4 at 0p4): pauldron following the arm with parent 3% strips 4.6-7.2 max (baseline); `half` + `parent` 2.8-7.1 with strips (mean down about a third); `arm` + `child` (pauldron-owned) 3.1-4.5 on S6/S4/S2 but 7.2-8.7 on the M4 armours; `half` + `both` (3% strips) 5.0 -> 3.9 (S6), 4.7 -> 2.8 (S4), 5.6 -> 3.7 (S2) with mean 0.8-0.9; with 6% strips `half` + `both` gives max 1.9-4.5 and mean 0.45-1.35 over all seven armours. Cost: `both` doubles the strip faces (about 15-30% extra faces at 6% length), so use `parent`/`half` when the face budget matters. Recommended when the pose range matters: `--pauldron-convention half --overlap-mode both --overlap-length 0.06`.

### Separable mode: cyan joint bands, all joints (chest / pelvis / thighs / arms)

Palette: every `base_views/<race>/palette.json` carries an optional block `"separable_garments": [{"role": "joint", "hex": "#14DCEB"}]` (fallback `config.json` `separable_garments` for old job snapshots). It is ignored unless a reduction is run with `reduce_model.py --separable` (`Palette(..., separable=True)` appends the garments after the normal ones, scheme gets the suffix `_joint`) or `convert_job.py --separable`; `convert_job.py` also switches it on for a job whose `.tripo-job.json` / `prompts.json` / `<module>_prompts.json` (beside the views or in `.concept_notes/`) has `joint_bands: true`, `separable: "joint_bands"` or the words "joint band". Without the switch nothing changes (regression 2026-10-22: re-reduction of the orc_male plate-mail `body_armor` gives identical `material_id` at 0p4/0p2/0p1, and `--separable` on that cyan-free source changes no label). A hand-made palette that already lists the role (`experiments/joint_bands_20261022/palette_joint.json` `joint`, `experiments/rigid_sections_20261022/palette_cyan5.json` `quinary`) is left as it is; `quinary` is the old name of the cyan role (the M4 data: cyan rerebrace plates, cut with `--rigid colour`), `joint` means joint bands.

Adaptive hue fit (2026-10-22): `Palette.fit_hues(colors)` fits each palette colour's hue centre to the model's own texture. A weighted (saturation x brightness) hue histogram of the 0.4% level's 80k samples is smoothed; peaks above 0.3% of the weight are matched to colours greedily by increasing hue distance (at most 30 degrees, one peak per colour, so a hot-pink peak at 329 degrees that is as near the body red as the magenta accent goes to the accent because the body has its own peak at ~357); shifts under 8 degrees are ignored (a calibrated model is classified by the nominal palette); a peak that a colour without a peak of its own sits within 6 degrees of is flagged `ambiguous` and left nominal. The shifted centres (`Palette.with_hue_shifts`) label all three levels, are written to `manifest.json` `hue_fit` (per colour: nominal, peak, share, shift, note; plus `review`) and `palette.hue_shift`, and are used by the high-poly blend. `reduce_model.py --adaptive-hue auto|on|off`: `auto` (default) is on only for separable palettes (`--separable` or a palette listing a `joint`/`quinary` role), so ordinary reductions are bit-identical to before. Regression (2026-10-22, `experiments/joint_bands_20261022/regress/adapt*`, `--adaptive-hue on` against the old reductions, `material_id` per face at 0p4/0p2/0p1): orc_male plate mail, human_male plate mail, S2, S4, S6, M4_15, M4_46: 0 changes (all fit nominal); Tripo robe (secondary +12.2 degrees): 12/27/42 faces of 1196/2024/3870 changed (accent/tertiary to secondary on violet-blue samples); Hyper3D robe (accent +13.5): 1/4/18 of 1842/3484/7702. J_09 (accent +27.5 degrees): 133 accent faces at 0p4 instead of 1, the pauldrons are found (85/120 faces instead of 0/0). Concept side: `tools/check_concept_colours.py <image> [--palette dir] [--separable] [--max-drift 12]` measures each palette colour's hue in a concept image and reports drift beyond 12 degrees (J_09 front: accent +19 degrees, DRIFT); it is a tool only, nothing calls it.

Band continuity: `compare_rigid.py --continuity <out.json> <name>=<reduced> ...` (`split_pieces.band_continuity`) reports per joint and LOD the fraction of the joint ring covered by joint-role faces (azimuth arcs around the joint axis), the largest gap, the number of edge-connected pieces and the band width. Coverage is a property of the source texture, not of the LOD: 0p4/0p2/0p1 give the same coverage within a few percent (J_09 waist 100%, arms 96-97%, hips 69-81%; J_21 arms 90-99%, waist and hips 100%; J_47 waist 100%, hips 78%, arms 52%); what changes with the LOD is whether the band touches both neighbouring plates (contact edges) and whether a plate spans the joint, so finer levels do not keep bands better.

`split_pieces.py --rigid bands [--soft piece|nearest]`:
- Pieces: `chest` (id 0, everything not below), `pauldron_l/r`, `arm_l/r`, `pelvis` (`root` part), `thigh_l/r` (`thigh_stretch`, `leg_stretch`, `foot`; `rigid.part_groups`), plus, with `--soft piece`, one skinned `soft_<joint>` piece per banded joint (`soft_arm_l/r`, `soft_waist`, `soft_hip_l/r`). Pauldrons are cut first by the `--style` logic.
- Band = joint-role faces (components under `bands.min_band_faces` are dropped); rigid plates = connected non-band wear faces, each wholly assigned to its body-part zone majority. A band component belongs to the joint whose two pieces it touches with at least `bands.min_contact` edges each. **A joint is `band` only if such a component exists and no plate with at least `mixed_min_faces` faces and more than `mixed_share` (3%) of its area in another zone spans it**; otherwise it **falls back**: the plate is split by zone and the cut is re-cut by the M2 snap min-cut (`snap_cut`, now general for any pair: waist = chest|pelvis, hip = pelvis|thigh). Joints with no faces on one side (no legs in the armour) are `absent`. `rigid.bands.joints` / `fell_back` / `absent` in `pieces.json` report this per joint.
- `--soft nearest`: band faces join the nearest rigid piece (rings), the cut runs through the middle of the band and gets overlap strips; `--soft piece` leaves the band skinned (no strips at its cuts, `soft_stretch_max` reported).
- `--rigid auto` (the default for a reduction whose manifest palette has a `joint`/`quinary` garment and no explicit `--rigid`; `--rigid none` switches it off): `bands` when there are at least `bands.auto_min_faces` `joint` faces, `colour` (M4) when there are only `quinary` faces, else `snap` on all joints (`--joints all`; zones/snap default to arms only). `pieces.json` records `auto` and `default_rigid_reason`; overlap strips are NOT added by this default any more (`--overlap` adds them).
- Pose test scenarios (`--pose-test`, each with and without strips): arms down 45 / up 30 about the shoulder joint, `thigh_flex` 45 (forward) and `thigh_abd` 20 (outward) about each hip joint (thighs rotate, pelvis fixed), `spine` 20 (chest, arms and pauldrons pitch forward about the waist joint relative to the pelvis). Hip and waist joints come from `parts.npz` (thigh ring shared with the pelvis; ring between `root` and `spine`), overridable through the spec keys `joint_l`, `joint_r` (shoulders, CLI `--joint-l/--joint-r`), `joint_hip_l`, `joint_hip_r`, `joint_waist`. Gap = opening of rigid-rigid cuts that move relative to each other; banded joints show `soft_stretch_max` instead (the largest edge stretch of the soft piece blended by inverse-distance-squared weights).
- First real joint-band data (2026-10-22, `experiments/joint_bands_20261022/`): at 0p4 the cyan bands survive only as small partial rings (J_09 94 joint faces, J_21 106), so most joints fall back to snap (J_09: waist and right hip banded; J_21: none), which still follows the band edges because they are colour edges; both concepts lost the magenta pauldrons in the labelling (hot-pink hue ~322 deg is outside the 20 deg tolerance of #E119DC at 304 deg: accent 1 / 0 faces). `attach_parts` now aligns an exported GLB that lost a few invalid faces with the npz by face area (`body_parts.aligned_by_area`).
- `compare_rigid.py --bands <out.jpg> <name>=<reduced> ...` builds the static and pose sheets (snap on all joints vs bands with soft pieces vs bands nearest) and `<out>.jpg.json`.

## Rigid sections with per-piece base colours (`split_pieces.py --rigid regions`, 2026-10-22)

The replacement for joint bands (thin cyan bands did not survive Tripo as closed rings, see the bands section above): each rigid
section has ONE large main colour, neighbouring sections differ, so every joint is a boundary between two large colour regions
(`PROMPTING_GUIDE.md` has the concept rules). Standard 4-colour palette; the separable `joint` role is not used (the code stays).
Expected main colours are `config.json` `piece_split.body_armor.rigid.regions.expected`: chest `primary`, arm `secondary`,
pauldron `accent`, pelvis `secondary`, thigh `primary` (CLI `--expect arm:quinary,chest:primary` overrides it, e.g. to sanity-check
data with other colours).

Steps (`sections_regions`; thresholds in `rigid.regions`):

1. **Pauldrons first**, with the rim style (expected pauldron colour = accent seeds + the wear faces they enclose = field and
   decoration), unless `--style` was given. The rest is the candidate set.
2. **Regions**: connected same-role components of the candidates whose role is an expected section colour and whose area is at
   least `min_region_share` (2.5%) of the candidate area. Each is assigned to the section holding most of it by body part (the zone
   guess of M1: arm parts, thigh parts, `root`, else chest; sides from the part suffix) or, when that section expects another colour,
   to a section with at least `role_resolve_share` (25%) of the region whose expected colour is the region's (`whole (role decides)`).
   A second section that holds at least `min_span_share` (4%) of the region with its 90th-percentile face farther than `span_depth`
   (5% of height) from the main zone means the region spans joints (e.g. chest and thigh green joined because the pelvis colour is
   missing): it is split by the zone guess and each such cut is re-cut by `snap`. Spill within `span_depth` of the zone boundary is
   treated as zone-guess error and the region stays whole.
3. **Everything else**, as same-colour components, largest first: enclosed by one section (at least `min_enclosure` = 60% of its
   perimeter on it, counting already-assigned faces) = decoration, absorbed into it; a same-role component of at least
   `min_minor_share` (0.4%) that is not enclosed (a detached tasset) is assigned like a region; anything else goes face by face to the
   nearest assigned section by shared-edge rings. Decoration that ends up on two sections is listed in
   `decoration_touching_two_sections` with its centroid. Components with no assigned neighbour keep the zone guess.
4. **Joints** (arm_l/arm_r = chest|arm, waist = chest|pelvis, hip_l/hip_r = pelvis|thigh): `region` when at least
   `min_boundary_share` (60%) of the cut length lies on a colour boundary; `fallback` (cut re-made by `snap_cut` around the zone guess)
   when it does not, when the two sections do not touch, or when both lie in one spanning region; `absent` when a piece has no faces.
   Reported in `pieces.json` `levels.<lv>.rigid.regions` (regions with zone shares and how they were assigned, other components,
   joints with colour-boundary share, `fell_back`, `absent`) and warned when a region's colour is not the expected one for its section.

`--rigid auto` (the default for a reduction whose manifest has a joint role in its palette or `hue_fit.active`, i.e. separable /
piece-colour jobs) decides per level, in this order: `bands` when at least `bands.auto_min_faces` (10) joint-role faces exist;
`colour` when at least that many `quinary` faces exist; `regions` when the non-pauldron faces hold at least `auto_min_regions` (3)
large same-colour regions of expected section roles that together cover at least `auto_min_share` (50%) of their area; otherwise
`snap` on all joints. The numbers are in `rigid.auto` (`large_regions`, `region_area_share`, `region_roles_present`, `chosen`).
`convert_job.py` runs jobs that say `piece_colours` / `rigid_sections` (or the words "per-piece base colours" in their records, or
`--piece-colours`) with `reduce_model.py --adaptive-hue on` (the hue fit, see above), without `--separable`.

**Clean piece shapes (all rigid methods, after the joints are cut).** (1) Detached patches and islands: besides the shared-edge vote, a patch that hangs on by
corners only (no shared-edge neighbour of another section) goes to the section sharing most vertices, pauldrons included (`vertex_votes`; P_11's chest patches
enclosed by a pauldron, P_40 0p4's arm island on the shoulder top; `absorbed_islands` says "attached by vertices only"). (2) **Flap / spike pruning**
(`prune_flaps`, `rigid.flaps`, `--keep-flaps` to skip): a triangle that hangs off the wearable by ONE edge (or none) and whose free tip stands more than
`min_height` = 6% of the height off that edge is dropped from the exported pieces (chains peeled leaf by leaf, `max_passes` 4; a leaf face opens no hole; the
piece labels are unchanged, `Sections.dropped` / `faces.npz` piece = -1; reported in `rigid.flaps` and as a warning). Cause of the user's "spiky triangle on arm_l"
(P_29, face 630 / 908 / 1638 at 0p4 / 0p2 / 0p1): the reduction leaves a single blue cuff triangle (body part `forearm_stretch.l`, 10-12.5% of the height off
its edge, 3 x 10^-3 H^2) stretched out over the bare forearm; its only neighbour is in arm_l, so there is no other section to give it to. The next largest
single-edge leaf in the three models is 4.5% (P_11 neck), so 6% separates the flaps cleanly; P_29 0p1 arm_r has one too (9.1%), P_11 / P_40 none.

Outputs, overlap (off by default; with `--overlap` mode `both`, 6%; convention `half`) and the pose scenarios (arms, thigh flex, thigh abduction, spine) are
the same as for the other rigid methods (`pieces/lod_<lv>/*.glb`, `faces.npz`, renders, `pieces.json`). Comparison sheets:
`compare_rigid.py --regions <out.jpg> <name>=<reduced>[@<concept front.png>] ...` writes `<out>.jpg` (concept, reduced colours,
regions front/back/exploded, snap front/exploded), `<out>_pose.jpg` and `<out>.jpg.json`; each sheet is scaled to at most 2400 px both ways.

Exercised on data that was not designed for it (2026-10-22, `experiments/piece_colours_20261022/regions_dev/`): S6, S4 and S2 pick
`regions` under `auto`; arms are `region` joints on S2 (left) and S4, the waist on S6, the rest fall back (their pelvis/thigh colours
are not per-section); M4_15/M4_46 with `--expect arm:quinary` find the cyan arm regions, but all five joints fall back (small chest/arm regions merge or the cuts are not colour boundaries).

Real piece-colour concepts (2026-10-22, `experiments/piece_colours_20261022/P_11_knight_errant`, `P_29_hawk_helmless_champion`, `P_40_celestial_orrery`, reduced with `--adaptive-hue on`; `pieces_auto/`, `pieces_snap/` (roles style), `pieces_snap_rimstyle/`, sheets `compare_regions.jpg`, `compare_regions_pose.jpg`): `--rigid auto` picks `regions` on all three at every level. Three rules were added after the first run on this data, no threshold was changed: (1) the rim pauldron step no longer absorbs a large section-colour region as a pauldron field (the blue arm is open at the cuff, and the open mesh boundary does not count against enclosure, so the rim style had swallowed the whole arm); (2) a section that already has a region of its own expected colour never takes part of a region of another colour (blue tassets reaching over the thigh zone stay pelvis; a green plate edge over the pelvis zone stays chest); (3) an arm joint whose arm and chest do not touch (the pauldron sits between them) is `region` when the arm|pauldron cut lies on a colour boundary. Colour-edge share of the joint cuts: regions 100% (P_29 0p1 84%) against snap 13-56%. Mean pose gaps with overlap are about the same as snap (arms, thighs); the spine is worse than snap on P_29 and P_40 (about 1.3 against 0.4-0.9 % of height mean).


### Cross-joint (fringe) reassignment: shelves / caps, and the older plane rule (2026-10-22)

Colour alone can leave faces on the wrong section. `split_pieces.reassign_cross_joint` runs inside `build_sections` for every rigid method that has a
pelvis (and on the high-poly graph in `segment_first.py`, before the reduction). On by default (`rigid.cross_joint.enabled`); `--no-cross-joint`
(split_pieces and segment_first) switches it off; the `given` method (labels computed elsewhere) skips it. `rigid.cross_joint.mode` picks the rule:
`shelf` (default), `plane` (the first rule, described further down) or `both` (shelf, then plane).

**Shelf / cap rule (`mode: shelf`, default).** The user's ground truth (`experiments/segment_first_fringe_20261022/user_truth_P29_chest_ledge.json`): 19 faces of the
P_29 0p4 chest form an up-facing ledge at the very bottom of the chest (2-17 mm above the pelvis top, meeting the chest wall along its inner edge at a 77-96
degree fold, colour boundary along its outer edge); as part of the pelvis they close it into a clean shape, left on the chest they are a disc-like flange.
For a joint between sections A|B (the axis points from A into B; both directions are tried, so a down-facing lip on top of the pelvis goes to the chest):
faces of A whose outward normal points along the axis into A's side (within `shelf.axis_deg` = 35 degrees; up-facing at the bottom of the chest) and that
lie within `shelf.band` (3% of height; distance of a vertex to the A|B boundary polyline) are grown into connected groups over edges up to
`shelf.crease_deg` (45 degrees dihedral). A group that touches B moves to B when it is at most `shelf.max_share` (10%) of A, has at least `shelf.min_faces`,
borders B along at least `shelf.min_contact` (25%) of its outline and is separated from the rest of A by a fold (mean dihedral of its neck at least
`shelf.min_fold_deg` = 30). There is no distance-past-the-plane test, so vertical bands (abdomen, baldric) can never move. `shelf.joints` (default
`["waist"]`) lists the joints it runs on (the cross_joint `joints` list still limits them first): on P_29 the armpit / hip candidates were inward-facing
single faces and a crotch face, no ledges, so they are off by default. `pieces.json` `rigid.cross_joint` lists every move and near miss (`rule: shelf`, faces,
area / share of the section, angle of the normals to the axis, contact share, neck length and dihedral, offset from the pivot, `rejected_because`).
Results (`experiments/piece_colours_20261022/<concept>/pieces_shelf/`, `pieces_shelf.log`; `--rigid auto --pose-test`): P_29 0p4 moves exactly the 19 ground-truth
faces (recall 19/19, no extra; the plane rule moved 66 faces, 19/66), 0p2 / 0p1 move 26 / 32 faces (2.8% of the chest, y 0.540-0.548, all up-facing);
P_11 moves 3 / 8 / 17 single-face to 5-face ledges (0.4-0.6% of the chest), P_40 2 / 4 / 7 (0.2-0.3%); nothing else, in particular no abdomen band or baldric.
Because the abdomen band now stays on the chest, the spine-bend gap is not reduced as it was by the plane rule (P_29 mean 2.19 -> 2.36 / 2.21 -> 2.05 / 2.33 -> 2.11 % of height;
plane rule 0.9).

**Plane rule (`mode: plane`; wrong on real data: it moved P_29's abdomen band, 18% of the chest, and P_11's baldric).** Kept for comparison.
Original description follows.

- Joints (`rigid.cross_joint.joints`): `waist` chest|pelvis (axis down), `hip_l/r` pelvis|thigh (hip -> knee), `armpit_l/r` chest|arm (shoulder ->
  elbow); `shoulder_l/r` pauldron|arm exists but is off (pauldrons legitimately cover the upper arm: on P_29 it would move 21-23% of the pauldron). Pivots are the
  pose-test pivots (base `parts.npz` through the ICP fit). Every joint is checked in both directions (`directions: both`).
- For a direction `from -> to` every face centroid gets a signed distance `s` (fraction of height) along the axis from the pivot, positive = into
  `to`'s side. The section `from` is cut into **planar patches** (`planar_patches`: region growing, flattest faces first, normals within
  `patch_deg` = 30 degrees of the seed normal). Per-edge dihedral thresholds were tried first and do not work on the Tripo high-poly meshes: their
  folds are bevelled over several faces, so at 25 / 35 / 50 degrees the whole P_40 chest stayed one 99.5% patch.
- A patch (patches joined through the small bevel patches beyond the plane form a group) moves when: >= `beyond_share` (85%) of its area has `s > 0`
  and its area-weighted mean `s` is >= `margin` (per joint family: waist 2.5%, hip / armpit 4%, shoulder 5% of height; this is the guard that keeps
  legitimate overhang, a breastplate edge just over the fauld or tassets just over the thighs, where they are); it is not the largest patch and a plate
  that continues across the plane is one patch that is only partly beyond it, so it stays (that is the "distinct from the main body: bounded by a
  fold or flange" test); the group is >= `min_share` (0.5%) / `min_faces` and <= `max_share` (30%) of the section; it touches the target section along
  >= `min_contact` (10%) of its boundary. `complete_to_cut`: the rest of the section beyond the group's own upper edge (5th percentile of `s`) that hangs together with it
  (side walls, bevels) moves too, so the seam is one clean line instead of a ragged one.
- `pieces.json` `rigid.cross_joint` lists every move (faces, area, share of the section, mean / max distance past the plane, neck dihedral,
  mean angle of the patch normals to the joint axis, contact share, cut level, completed / bevel faces) and every near miss with the reason
  (`rejected`); `segment_first.json` / `pieces.json` carry the same record for the high-poly run.
- Results (`experiments/segment_first_fringe_20261022/<concept>/{before,after}` = `--no-cross-joint` / default, 0p4 / 0p2 / 0p1, no overlap strips;
  mean / max gap in % of height of the 20 degree spine bend about the waist pivot, convention `half`, mode `parent`, no strips):
  P_40 chest -> pelvis 42,852 high-poly faces (3 patch groups, 26% of the chest area, 5.6% H^2; mean 2.5-3.5% of height past the plane): spine mean 2.16 / 1.88 / 1.95 -> 0.73 / 0.60 / 0.70, max 3.52 -> 3.03-3.05.
  P_29 chest -> pelvis 34,724 faces (18% of the chest; the same plain abdomen band below the pivot; not "nothing"): spine mean 2.48 / 2.57 / 2.55 -> 0.93 / 0.73 / 0.85, max 3.66 -> 2.92.
  P_11 chest -> pelvis 5,120 faces (4.5%) and pelvis -> chest 17,660 faces (13.6% of the pelvis: the diagonal baldric / sash painted in the pelvis
  colour, 9% of height above the waist plane, now on the chest where it lies): spine mean 2.18 / 2.11 / 2.07 -> 0.96 / 1.43 / 1.43, max 3.14 -> 2.63.
  Arm and thigh gaps do not get worse (P_29 0p4 thigh abduction max 1.74 -> 1.80, 0.1% H; everything else within 0.1: arms down, arms up, thigh flexion).
  The per-face path on the reduced wearable (`experiments/piece_colours_20261022/<concept>/pieces_nofringe|pieces_fringe/`): P_29 and P_40 find the
  band (P_29 spine mean 2.19 -> 0.91, P_40 0p4 2.05 -> 1.55 and 0p1 1.95 -> 1.06; the low-poly patches are coarse, so P_40 0p2 and P_11 are
  borderline and stay unchanged).
- `pieces_gallery.py` (Blender, `blender -b --python tools/tripo_pipeline/pieces_gallery.py -- <out.blend> [--png <overview.png>]`) builds the review

## Segment first, simplify second (default rigid split for piece-colour plate armour, 2026-10-22; `reduce_model.py` untouched)

`reduce_model.py` reduces the whole geometry colour-blind and labels each low-poly face afterwards, so 4-10% of the wear area sits in
mixed faces on section borders and the right edges do not exist in the LOD. The prototype cuts first:

1. `segment_first_prep.py` (Blender, ~30 s): the same front matter as `reduce_model.run` (import, normalise, interior audit, weld, local repair,
   canonical order, ICP fit of the base parts), then for every cleaned face (0.74-0.92 M) three texture colours (nearest source triangle, no
   projection search), its body part (`face_labels.transfer_parts`) and the concept-camera visibility cosine -> `prep/prep.npz`.
2. `segment_first.py` (plain Python with numpy + scipy, e.g. `characters/.venv`): classify every high-poly face (palette + adaptive hue fit on
   the seen faces; evidence = vote mass of its three points); clean the labels on the high-poly face graph (`potts`: iterated conditional modes,
   data term = evidence x visibility weight, lambda 0.5 per neighbour, module prior for body_armor: base kept bare on forearm / hand / lower leg /
   foot / head at cost 1.2, so only a large neighbouring wear region can keep wear there); regions mostly unseen by the concept cameras are
   re-flooded from the surrounding seen faces (`reflood_unseen`, Tripo invents those); specks, pin-holes and flecks under 0.05% of the area are
   absorbed (`absorb_small`); the wearable (non-base faces) is cut by `split_pieces.sections_regions` on the high-poly graph (scipy components,
   k-d tree nearest centroid patched in; the snap re-cut is skipped there) into chest / pauldrons / arms / pelvis / thighs.
3. Every section is reduced on its own with meshoptimizer (the same call as `reduce_error`, absolute error 2 x fraction on the whole model's
   normalised height) at 0p4 / 0p2 / 0p1. Section borders are simplified first as polylines (Douglas-Peucker, tolerance half the level error);
   the kept border vertices are locked (`vertex_lock`) in both neighbouring sections and dropped border vertices are merged into their kept
   neighbour, so neighbouring sections share exactly the same border vertices (they weld; `split_pieces` cuts / overlap strips / pose test work
   unchanged via the new `--rigid given` method). Each reduced face takes the garment role holding most of the high-poly area it covers.
   **Seam clean-up (2026-10-22, on by default; `--no-fill-slivers`, `--no-smooth-cuts`, `--cut-band PCT`, `--no-smooth-border` switch the steps off / tune them).**
   The first prototype left holes and a ragged chest|pelvis seam on P_29 (`experiments/segment_first_seam_20261022/`). Causes: (a) a 569-face sliver of base
   (0.5% of the height wide, 0.08% of the area, just over `absorb_small`'s limit) between the breastplate and the fauld was removed with the base, so the
   chest|pelvis seam was an open arc with a slit beside it (P_40 has the same at the shoulder; the shared borders themselves were already identical, 0 vertices
   of one piece missing on the other along the seam after welding); (b) the cut followed the high-poly colour boundary, a staircase of triangle edges and
   Tripo's own paint wobble, and Douglas-Peucker with tolerance half the error keeps every tooth bigger than that (20-85 turns of more than 90 degrees per
   100% of height on the reduced seams); (c) the cross-joint reassignment (`--no-cross-joint` off) adds its own spiky cut on top. Fixes, all before the reduction
   so that both neighbouring sections still share one border: `fill_slivers` (base components that touch no bare zone, are under 2% of the area and
   under 1% of the height wide, mean width 2 x area / perimeter, take the labels of their border ring by ring from both sides); `mincut_sections` (for every pair of
   neighbouring sections the faces within `--cut-band` = 1.5% of the height of their interface are re-split by a scipy max-flow minimum cut of the dual
   graph: cost = edge length x (0.15 + 0.85 exp(-(dihedral / 15 deg)^2)), so the cut is the shortest closed path in the band, teeth and zigzags vanish and it settles on a
   fold within the band; a pull of the area toward the current section keeps it from leaving the band; faces outside the band never change; new tiny islands are
   undone); `smooth_border_vertices` (after the reduction the kept border polylines are Laplacian-smoothed, ends / junctions fixed, no vertex farther than 0.35 x
   the level error from its place, triangle flips undone; the vertices are shared so the sections still weld exactly). `seam_metrics.py <out> [--prep-dir DIR]`
   measures any run (welded boundaries of every piece pair: gap vertices = boundary vertices in the seam zone of A|B that are not on B's boundary, with their distance;
   T-junctions; seam jaggedness = length / Gaussian-smoothed length, rms / max deviation, reversals; thin holes = closed free boundary loops narrower than 1% of the height;
   border mixing; distance of the cuts to the high-poly colour boundary); `process()` stores the same numbers per level in `segment_first.json` `levels.<lv>.seams`
   (`highpoly_seams`, `fill_slivers`, `smooth_cuts`).
   Results (`experiments/segment_first_seam_20261022/<concept>/`; `baseline/<concept>/` = the same code with the three steps off, `--no-cross-joint` in both; levels

   gap at the left shoulder front stays: 1.3% wide in the high-poly, over the 1% limit), P_40 1 -> 0 (the 543-face sliver at the shoulder), P_11 0; border mixing (area share of triangles whose top
